# Changelog

All notable changes to Noren are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses
[Semantic Versioning](https://semver.org/).

## [Unreleased]

### Fixed

- **The theme and the window effect change while a browser pane is open**: changing the theme (which also sets the Mica, Acrylic or vibrancy effect behind the window) was refused with "current webview is not a WebviewWindow" while a browser pane was open, because Tauri stops calling a window a webview window once a web view is a child of it. The command now takes the window that calls it as a window.
- **The main window is found while a browser pane is open**: quitting from the tray icon, "Open Noren", a `noren://` link or a second launch bringing the window up, and the focus read that decides whether a notification is shown all missed the main window while a browser pane was open, because Tauri stops calling a window a webview window once a web view is a child of it. They now look the window up as a window.

### Added

- **The v1 performance targets are measured, and the renderer is evaluated**: `node scripts/perf.mjs --only-app --app-tabs 100` runs the many-tabs side of the real-app measurement with 100 tabs instead of 30 (the default and the labels of the 30-tab rows are unchanged; the wait for the report grows with the tabs; the pure parts are tested in `scripts/perf-app-lib.test.mjs`); `docs/PERF.md` has the new section 7: 100 tabs use 467.5 MB of total memory (target 800 MB, met) and the first prompt takes 478 to 526 ms in four series of 5 (target 500 ms, not met, borderline) with the split by process and the hypotheses for a cut; `docs/RENDERER.md` compares native rendering (libghostty) and WebGPU with the xterm.js WebGL renderer in use and recommends keeping the current one for version 1. No code of the app changed.
- **Package manifests for winget, Scoop and the AUR**: `pnpm packages:generate` reads the NSIS and MSI installers that `pnpm desktop:build` left, the deb of the release (passed with `--deb`) and the version of `tauri.conf.json`, and writes a multi-file winget manifest, a Scoop manifest (it unpacks the MSI, so no administrator rights and no window) and the `PKGBUILD` and `.SRCINFO` of `noren-bin` under `target/packages/<version>/`, with the sha256 of each file and the address of the release it will be attached to. An installer of another version or a missing one is refused with a sentence that says so. It only writes files; nothing is submitted, and there is no Homebrew cask while macOS is undecided. Steps for the maintainer who publishes: `docs/PACKAGES.md`.
- **Check for updates and install them from the settings**: the settings have a new **Updates** section with a **Check for updates** button, and the command palette has **Check for updates**, which opens the section and checks. Noren only looks when you ask: if a newer version exists the section says so, with the release notes and the date, and a **Download and install** button; nothing is downloaded or installed until you press it. Before the installer starts, Noren saves your tabs and their output the way it does when you close the window, because on Windows the installer ends the app. The download shows a progress bar, and each refusal has its own sentence, in English and Brazilian Portuguese: this build has no update key yet, the signature does not match the package, the package was signed for another version, the release has no package for this computer, the server cannot be reached, took too long or answered an error, the list of releases is not readable, and there is nothing new. A refused update installs nothing. Also fixed: in Brazilian Portuguese the test buttons of the AI section now start with the words they show ("Testar conexão"), so a screen reader hears the name that is on the button.
- **The app can find and install its own updates (no screen yet)**: Noren now has the machinery to check the latest GitHub release for a newer version, download the installer and install it, and only when it is asked to: nothing checks at start, nothing downloads or installs by itself. The download is limited in time and size, goes over `https` only, and nothing is installed unless the signature of the package matches the public key set in `tauri.conf.json` and was made for the version the release announces (so a release page cannot pass an old signed build off as a new one). Until the maintainer puts the real public key there, a check or an install is refused with a sentence that says so. It is tested against a local server with a package signed by a key made for the tests: a valid update is accepted, and a wrong key, a package changed by one byte, a signature for another version or none, an equal or older version, a release with no package for the platform, a package that is too large and a package address that is not `https` are refused with nothing installed. The button, the palette command and the notice of a new version come next. New dependencies: `tauri-plugin-updater` and `minisign-verify` (and a few small crates they bring), MIT or Apache-2.0. (NOR-F20-02a)
- **Accessibility checks on the panels and panes, and a test script for a screen reader**: the automated check now also runs on the Ask, Agents, Library, Sync, Gallery, Providers, Models and Bench screens, the plugin panel, the browser, diff and preview panes, the favorites grid, the project actions header, the live groups, the quick terminal and the windows you drag a tab into, in each state (empty, with data, with an error), and fails on a problem of any size. It found, and Noren fixed: the headings of an answer from the AI could skip a level (they now start one level under the panel's title and never skip); the path on top of a file preview is now a heading; the buttons of the Agents and Library lists were named with other words than the ones on screen (now the name starts with what you see); gray text on a hovered or selected row, on the New tab button of a window and on the exit code of a failed command was too faint (now darker); and a window's own sidebar and terminals now have names of their own ("Window sidebar", "Window terminal"). The new file `docs/ACCESSIBILITY.md` is the script for testing by hand with NVDA and Narrator on Windows (what to do, what should be read, the screen reader mode, the spoken announcements, dialogs, the palette, splits); it has not been run with a real screen reader yet. (NOR-F20-01c)
- **A check for accessibility problems on the main screens, menus and dialogs, and what it found**: an automated check (axe-core) now runs on the window, the command palette, every section of the settings, the shortcuts screen, the tab menus, the dialogs (spaces, picture, paste, link, ask the AI for a command, profile import, worktrees, project actions), the search over the tabs, the Ctrl+Tab switcher, the peek and the quick terminal, and it fails on a problem of any size. It found, and Noren fixed: terminals in a split tab, and the Terminal section of the settings, had the same name for a screen reader (a split terminal is now "Terminal 2 of 3", the section "Terminal options"); the window had no main heading; "Store key" and "Remove key" were read with other words than the ones on the button (now "Store key of work"); the space, picture and worktree dialogs were built on a form, which may not be a dialog; the small gray text on the selected tab, on the selected row of the Ctrl+Tab switcher and on the last command of a tab was too faint (now darker); and the peek of a tab was outside the main area of the page. The panels and the manual test script come next. (NOR-F20-01b)
- **Screen reader mode and spoken announcements**: a new setting, `terminal.screenReaderMode` (off unless you turn it on), gives a screen reader the text of the terminal and reads new output as it arrives; it has a check box **Screen reader mode** in the Terminal section of the settings and a palette command **Toggle screen reader mode**, and a change reaches the terminals that are open at once, without starting a shell again. Whatever that setting says, Noren now also tells a screen reader, through one live region, when you switch tab or space, when a command ends (with its exit code), when the bell rings, when a shell ends and what a Pull or a Push did; errors interrupt, the rest wait their turn, and the same announcement is not repeated in a burst. The texts are in English and Brazilian Portuguese. The review of every screen is the next task.
- **Sync of settings through a secret GitHub Gist: the Sync section, the palette and the push on close**: the Sync section of the settings has a list **Sync through** (a git remote, the default, or a secret GitHub gist; a new setting, `sync.method`). With the gist you save a GitHub token (a password box; it is kept in the system keychain and never shown again, the section only says whether one is stored; **Remove token** takes it out), connect to a gist by its id or press **Make a secret gist**, see where the sync stands, and Pull and Push. A gist that anyone can read gets a warning, a new gist says that secret is not private (not listed, but open to whoever has the link), a conflict names the files and says nothing changed, and a status that cannot be read (a file over 1 MiB, say) shows the reason without hiding the rest of the section. **Pull settings**, **Push settings** and the push when Noren closes use the method you chose. Each method keeps its own connection. No API of the app changed; tests use an in-memory GitHub and keychain, never the network.
- **Sync of settings through a secret GitHub Gist: the core, with no screen yet**: the app can now keep `config.jsonc`, the themes, the mods and the spaces in one secret gist of your own, as a second way to carry the same files the sync through git carries (nothing else ever travels: not `state.json`, the scrollback, `gallery.json` or the plugins). A gist has no folders, so `themes/x.json` is stored as `themes--x.json`; a file of the gist whose name does not map back to one of the allowed files is ignored and never written. The GitHub token (a personal access token with the gist permission) is kept in the keychain of the system under a name no AI provider can have, never returned to the page and never written to a file, a log or an error message. You connect to a gist by its id, or have a secret one made from your files; Push refuses, and sends nothing, when the gist changed since this computer last synced; Pull writes the files the gist changed, and when a file changed on both sides it writes nothing at all and lists the paths. Only the commands and the backend are in this version: choosing git or Gist, the token field, the palette commands and push on close come next. The real GitHub API and the real keychain have not been exercised by the tests, which use a fake local server and an in-memory vault.
- **Push when Noren closes**: a new setting, `sync.pushOnClose` (off unless you turn it on; a check box **Push when Noren closes** in the Sync section writes it). With it on, closing Noren pushes first, the same as the Push button (the spaces are written as files and everything that changed is sent), when a remote is connected and something is waiting to be sent. It waits 4 seconds at most and never keeps Noren from closing: a push that fails or is too slow is skipped and the reason is logged. Closing the window to the tray icon does not close Noren, so it does not push. While the option is on, a close can take up to 6 seconds in the worst case (2 for the saves, 4 for the push), and the app waits 8 seconds for a page that stopped answering, up from 4.
- **Spaces travel with the sync**: Push now writes each of your spaces as `spaces/<name>.noren-space.json` first (named after the space; two spaces with the same name get `-2`, `-3`... after it) and sends them with the rest, and Pull makes spaces of the files that came in: a file you have not seen is a new space (the pull does not take you to it), a file that changed on another computer makes its space again in the same place (the tabs it had are in the closed tabs), and a file that is not a space file is named and skipped. The same space is never made twice: a small file next to `config.jsonc` (`sync-spaces.json`, which never leaves the computer) remembers which space each file stands for, so a space you pushed does not come back on the next pull and a second pull does nothing. Where you were looking (the tab shown, the pane focused, a folded group) is not part of the file, so switching tabs on one computer does not close the tabs of the same space on another. Pull also writes the spaces that already have a file before it merges, so a change made here is one side of the merge. A space that cannot be written (a page address holds a secret) is named after the answer and the others still go; what an export left out because it looks like a secret is named too. Removing a space does not remove its file, on the remote or on your other computers, and the Sync section says so. The Pull settings and Push settings commands do the same. Behind it: `spaces/` files and their record in `noren-core` (`sync_spaces.rs`: only names of the closed list, 1 MiB and 500 files at most, a batch with one bad name writes nothing), four commands (`sync_spaces_list`, `sync_spaces_read`, `sync_spaces_write`, `sync_spaces_link`) and the `Backend` methods for them on the three backends, the action `space/reimport` (in the property test of the reducer), and `exportFileName` now never gives a name the sync would skip (a name starting with a dot, a reserved device name with an extension, a control character).
- **Sync of settings through git: the Sync section and the Pull and Push commands**: the settings screen has a Sync section where you type the address of a git remote and press Connect, see where the sync stands (not connected, up to date, how many files are waiting to be sent, or that the remote has changes to pull) and press Pull or Push. An address with a password or a user name in an https address, `http`, a helper transport or something that looks like an option is refused with the reason and nothing is connected. Pull says which files it brought; if a file changed here and on the remote in different ways it stops, lists the paths and says that nothing changed on this computer; a failure of git is shown with the text git gave. Connecting reminds you that all of `config.jsonc` is sent (keep nothing secret in it) and that Noren cannot ask for a password or an ssh passphrase, so git must already work with the remote in a terminal. "Pull settings" and "Push settings" in the command palette do the same for the remote already connected and answer in the notice, or say where to connect when there is none. A pull that brings themes or mods puts them in use at once. Spaces and push on close come later. English and Portuguese. (NOR-F19-01b)
- **Sync of settings through a git repository: the core, with no screen yet**: the app can now keep `config.jsonc`, the themes, the mods and the spaces (`spaces/*.noren-space.json`) in a git repository of the person's own, using the `git` installed on the computer. It clones the remote into a `sync/` folder next to `config.jsonc`, copies in and out only those names (never `state.json`, the scrollback, `gallery.json`, plugins or any other file; keys stay in the keychain), pushes what changed, and pulls with a merge: on a conflict the merge is aborted, nothing in the config folder is overwritten and the conflicting paths are listed. A remote address with a password, one that starts with `-`, or one that uses an `ext::` or `fd::` transport is refused before git starts; git never asks for a password. New commands `sync_status`, `sync_connect`, `sync_pull` and `sync_push` and `Backend.syncStatus`, `syncConnect`, `syncPull` and `syncPush` (the in-memory `FakeBackend` keeps a remote and can make a conflict). Deletions do not travel yet.
- **Export space and Import space in the command palette**: "Export space" saves the active space as `<name>.noren-space.json` (a download; characters a file name cannot hold become `-`) and says which variables, tab return commands and profiles it left out because they look like secrets. "Import space..." opens a file picker and makes a new space from the file with new ids and the same tabs, splits and groups, and it becomes the active space. The profiles the file brings are added to `profiles` in `config.jsonc` (its comments stay) when you do not have them; one you already have as it is is not repeated, and one that clashes with a profile of yours or with a shell of this machine is not added, and the notice names it (the space keeps using the profile with that id). If the settings file cannot be written, nothing is imported. A file that is not a space file (not JSON, a version this build does not read, a field the format does not have, too large) says why and changes nothing. English and Portuguese. (NOR-F18-03b)
- **The file of a space (core only)**: `@noren/model` can now turn a space into the text of a `.noren-space.json` file and turn such a text back into a new space. The file holds the name, icon, color, theme, mods, AI and scrollback switches, defaults (profile, folder, environment, git identity), pinned tabs, the tree with its groups (live ones too), every tab with its splits and panes (kind, profile, folder, page, file), the place a pinned tab returns to, and the profiles of the user that the space uses. It leaves out what only means something on this run or on this computer: sessions, the running and last commands, scrollback, the unread marks, when a tab was last used, the background picture and a title a program asked for. Nothing that looks like a secret is written: a variable whose name says token, secret, password or API key, or whose value is recognized as a credential, is left out and listed; so is the command a pinned tab returns to, and a profile that runs a secret; a page address with a secret refuses the export. Reading a file answers with a short reason and never throws: a version this build does not read, a field the format does not have, an id used twice, split sizes that do not make 100, a tab placed twice or not at all, a text over 1 MiB. The new action `space/import` adds the space with fresh ids for the space, its tabs, groups and panes (so a file can be imported twice) and no session, and keeps every invariant of the workspace; `planProfiles` says which profiles of a file to add, which you already have and which clash with one of yours. There is no command in the palette yet: exporting and importing from the interface is the next task (NOR-F18-03b). Roadmap splits F18-03 into 03a (this) and 03b, and F19-01 now waits for 03b. (NOR-F18-03a)
- **The gallery in the settings screen**: a Gallery section lists the themes and mods of the gallery index next to what is installed (version of the index, version installed, and whether the item is new, has an update or is up to date), with an Install button for a new item, Update for one with a newer version and no button for one that is up to date. A download or a hash that fails is said on the row of the item and nothing is installed; after an install the themes or mods of the app are read again, so a new theme shows in the palette at once, and a theme that is not usable (its content does not pass the theme schema) is said so on the row instead of silently missing from the list. English and Portuguese.
- **The gallery of themes and mods: the core, with no screen yet**: the app can now read the index of a gallery (one JSON file listing themes and mods, each with an `https` address, a sha256 and a size), download an item, refuse it when its sha256 is not the one the index declares, and install it: a theme as `themes/<id>.json` and a mod as `mods/<id>.css`, with the id, kind, version and sha256 recorded in `gallery.json` next to `config.jsonc`. A wrong hash, a file larger than the index says, a redirect, an address that is not `https`, a file that is not text or a theme that calls itself something else installs nothing and leaves the installed version as it was; installing a newer version replaces the file and the record. Comparing the index with what is installed tells new, updatable and up to date. There is nothing to click yet (the settings section comes next), the address of the official gallery repository does not exist yet, and every test serves the gallery from `127.0.0.1`. New dependency: `sha2` (MIT OR Apache-2.0, already in the tree). (NOR-F18-02a)
- **A plugin can open a panel of its own, and the plugin API is documented**: a plugin that asks for the `panel` permission can now open a panel beside the terminal with a title and the HTML text of its content (up to 20,000 characters), and the example plugin has a second palette action, "Show the panel (sample)", that does it. The panel is shown in a frame with an empty sandbox, so it has an origin the app cannot read, no scripts, no forms and no windows, and its page lets nothing load; it can draw text and inline styles and nothing more. The panel closes with its button or Escape, and goes away if its plugin fails. A plugin without the `panel` permission is answered `permission_denied` and no panel appears. The content security policy did not change. The new `docs/PLUGINS.md` describes `plugin.json`, the permissions, the messages and methods of API version 1, the limits and the isolation. (NOR-F18-01d)
- **Plugins run in a Worker and put actions in the command palette**: each valid plugin of the `plugins/` folder now runs in a Worker of its own, tied to the permissions of its `plugin.json`: a request the manifest does not allow is answered `permission_denied` and changes nothing. The actions a plugin registers appear in the palette under "Plugins", with the label of the action and the name of the plugin, and choosing one tells the plugin, so the example plugin opens a new tab. A plugin that is invalid or fails is only recorded; the app and the other plugins go on and no dialog is shown. To allow this the content security policy now has `worker-src blob:` (it was `'none'`); scripts still come from the app alone, with no `eval` and no frames, and the page may start a Worker in one file only. The plugin's own panel and `docs/PLUGINS.md` come next. (NOR-F18-01c)
- **Plugins: loading the `plugins/` folder (core only)**: the app can now read the folder `plugins/` next to `config.jsonc`, where each plugin is a folder with a `plugin.json` and the script its `main` names. For each folder it hands over the text of both files or a short reason (`plugin.json not found`, not valid JSON, `main` missing, a `main` that is absolute, uses `..` or leaves the folder by a link, a file over 256 KiB or not UTF-8 text); at most 50 folders are read and the folder is never made. The manifest is then checked and its `id` must be the name of the folder, so a plugin is either loaded or listed with the reason it is not. `examples/plugins/new-tab-action/` is an example that asks for `palette.actions` and `tabs.create`. Nothing runs and nothing shows on screen yet (plugins run in a Worker in the next task). (NOR-F18-01b)
- **Plugins: the manifest and the permissions (core only)**: `@noren/model` now has the pure side of the plugin system. The manifest `plugin.json` is checked (`id` of `a-z`, `0-9` and `-`, `apiVersion` 1, a `main` that stays inside the plugin's folder with no `..`, no drive and no leading slash, and `permissions` without repeats among `terminal.read`, `tabs.create`, `palette.actions` and `panel`; any other field is an error, with the path of each one). The messages of version 1 are a request `{ version, id, method, params }` and an answer with the same `id` and a `result` or an `error`. One broker per plugin looks at the permission of each method before it does anything: a method the manifest does not hold is `permission_denied` (with the permission that was missing) and the app is not touched; a wrong version is `unsupported_version`, another method `unknown_method`, wrong parameters `invalid_params`. Reading a terminal and making a tab go through the same code as the local API; the palette actions and the panel a plugin asks for are only kept in a registry the app reads. Nothing loads or runs a plugin yet and nothing shows on screen. Roadmap splits F18-01 into 01a (this), 01b (the `plugins/` folder, a Worker per plugin, palette actions and an example) and 01c (the panel in a frame and `docs/PLUGINS.md`). (NOR-F18-01a)
- **A live group of running containers**: the new palette command "New group of running containers" makes a group whose entries are the containers `docker ps` lists; clicking one opens a tab that types `docker exec -it <container> sh`. Only names made of letters, digits, `_`, `.` and `-` (starting with a letter or a digit) are listed, since the name is typed into a shell. With Docker not installed, not running or too slow to answer, the group stays empty and shows the quiet line "Could not update" with the reason (`docker not found`, the first line of what Docker said, or `docker ps took too long`). (NOR-F17-04d)
- **A live group of SSH hosts**: the new palette command "New group of SSH hosts" makes a group whose entries are the hosts of your `~/.ssh/config`; clicking one opens a tab that types `ssh <host>`. Only the `Host` lines count (any capitalization, `Host=a`, several names on a line), names with wildcards are left out, and so is any name that is not plain letters, digits, `.`, `-` or `_` (it is typed into a shell). `Include` and `Match` are not followed, so the hosts of an included file are not listed. No `config` file is an empty group, not an error.
- **Live groups in the sidebar**: the entries of a live group show under it, one row each named by its label (for worktrees, the branch), and clicking one opens it: the tab of the group that already stands for it is shown, or a new one is made in the group in the folder of the entry. The command palette has "New group of worktrees", which makes a live group with the worktrees of the repository of the folder of the focused pane; a worktree made or removed from the palette shows up (or goes) at once, without waiting for the ten-second round. If the source fails, a quiet line says "Could not update" and the last list stays. The entries are not tabs: they are not dragged, not counted in the group and not in the tab switcher, and the arrow keys walk into them. Ordinary groups look the same as before. (NOR-F17-04b)
- **Live groups (the engine)**: a group can now be live (`GroupNode.live`, saved in `state.json` together with `Item.liveKey`; a file saved before them is read as it was). An updater asks the source of every live group when the app starts and every ten seconds, keeps the last list of entries (`key`, `label`, `cwd`, `command`) of each group and tells its subscribers when one changes; a source that fails keeps the last list and records the error, and a group that is removed or stops being live is no longer asked. An entry that goes away never closes a tab. `openLiveEntry(groupId, key)` of the workspace store shows the tab of the group that already stands for the entry or makes one in the group with the folder and command of the entry, outside the routing rules. The first source lists the git worktrees of a folder. There is no sidebar for the entries yet (nothing changes on screen).
- **New tabs of the window follow the routing rules**: a new tab made in the window (Ctrl+T, the new-tab button, the profile and folder entries of the command palette, a worktree) now goes where the first rule of `routing.rules` that matches says, with the same choice as the local API (`destinationOfNewTab` in `@noren/model`, which `items.create` now uses too): the folder is the one the tab asks for, else the start folder of the active space, and the command is the profile it asks for, else the profile of the active space, else the default one. A tab sent to another space makes that space the active one and is the tab shown; one sent to a group goes into the group. With no rules, no match, a rule whose space or group is gone, or settings that cannot be read, the tab goes to the active space as before. The first tab of a new space and a terminal taken from the quick window ignore the rules. The rules are read at every new tab. `docs/CONFIG.md` says so. (NOR-F17-03c)
- **Routing rules for the API and the CLI**: `items.create` of the local API no longer needs a `space`. Without one, the first rule of `routing.rules` that matches the folder (`cwd`, or the default folder of the active space) and the profile of the call decides the space and the group in it, and the answer says the `space` used and the `group` when the tab went into one; with no rules, no match or a rule whose space or group is not there, the tab goes to the active space. A `space` in the call is used as it is. The rules are read at every call, so a change in the settings counts at once. `noren-cli new-tab` takes `--space` as optional and, without it, makes no lookup and leaves the choice to Noren; its help and `docs/AGENTS.md` say so. An empty `space` is still `invalid_params`. The new tabs of the window itself use them too (NOR-F17-03c). (NOR-F17-03b)
- **Routing rules in the settings file (core only)**: `config.jsonc` accepts `routing.rules`, a list of rules that say which space (and which group in it) a new tab belongs to, by the folder it starts in (`cwd`, a glob with `*`, `**` and `?`, `~` for the home folder) or by the command it runs (`command`, a regular expression), or both. The file is checked as it is read: a rule with neither, a field that does not exist, an empty name, more than 100 rules and a regular expression that does not compile are errors of the file with their line and path (`routing.rules[0].command`), and the last valid settings stay in force. `routeNewTab` in `@noren/model` is the pure choice: the first rule in the order of the file that matches wins, with the space and the group found by name in the workspace; a rule whose space or group does not exist is skipped. A glob has to match the whole folder; on Windows `/` and `\` are the same and case is ignored, elsewhere not; the home folder and the kind of system are arguments, never read from the machine. The glob is matched by hand, in time proportional to the glob times the folder, so a glob cannot make the matcher slow. Nothing uses the rules yet: the new tabs of the window, `items.create` and `noren-cli new-tab` come next (NOR-F17-03b). `docs/config.schema.json` and the descriptions of the fields (English and Brazilian Portuguese) have the new key; `docs/CONFIG.md` has a Routing section. (NOR-F17-03a)
- **A command line for the running app (`noren-cli`)**: a console program with no window that drives a running Noren through its local API: `noren-cli new-tab --space <id or name> [--cwd .] [--profile]` (the name of a space is turned into its id with `spaces.list`; a name two spaces share, or none, is refused and no tab is made; `--cwd .` becomes the absolute folder you run it in), `split --item <id> --direction right|down`, `send --terminal <id> [--text] [--key ...]` (the text and the keys exactly as given; nothing, not even an Enter, is added), `read --terminal <id> [--lines N]` and `notify --title [--body] [--terminal]`. The answer of Noren is printed as one line of JSON; exit code 0 is done, 1 is an error answer of Noren, 2 is a wrong command line (nothing is sent) and 3 is Noren not reachable (not running, no token file, token refused), each with a clear message on standard error. ## [0.1.0] - Unreleased

First MVP. Noren is a terminal organized like a modern browser. Windows is the first platform
(NSIS and MSI installers); the Linux build is an AppImage and a deb. The build is not signed and
has no automatic updater yet.

### Added

- **Terminal core**: real PTY sessions through `portable-pty` with batched reads, xterm.js with the
  WebGL renderer, shell profiles detected on the machine (PowerShell, cmd, bash, zsh and others),
  and a typed backend interface with a fake backend for tests.
- **Spaces, groups and tabs**: a workspace model with checked invariants; spaces with their own
  icon, color, theme and background image; a space wheel and git identity per space; groups, pinned
  tabs and favorites (a grid) with their origin and a "reset" action.
- **Sidebar**: a tree of spaces, groups and tabs with a second line of live metadata (folder, git
  branch, last command), unread marks and a bell, drag and drop between groups, spaces, pinned and
  favorites, and side, width, density and compact settings.
- **Layout modes**: sidebar or top tabs, switchable from settings and from the command palette.
- **Splits**: panes inside any tab, split by shortcut or by dragging, swap and detach panes, pane
  headers with zoom, and splits shown in the sidebar.
- **Command palette and shortcuts**: tabs, spaces, actions, profiles, recent folders and themes in

- **Shell integration**: OSC parsing and integration scripts for PowerShell, bash, zsh and cmd for
  live folder, branch, last command and tab title; command marks; system notifications for
  finished commands in background tabs.
- **Project actions**: an `actions.json` in a project lists commands that run from the interface;
  `noren://` links open a folder in Noren (the installer registers the scheme).
- **Customization**: a commented `config.jsonc` with hot reload and a published JSON schema;
  a settings screen (appearance, shortcuts, notifications, terminal, profiles, auto-archive, AI);
  eight built-in themes, a theme per space, and import of color schemes and shell profiles from
  other terminals; user CSS mods; window material (Mica on Windows) and background images; fonts
  and terminal options.
- **Session life**: restore of tabs with scrollback after a restart, reopen closed tabs, auto-archive
  with a library that searches inside terminal content, peek at a tab without opening it, and a
  quick terminal window with a global shortcut that can be promoted to a normal tab.
- **Optional AI, local by default**: pluggable providers with keys kept in the system keychain,
  a preview of exactly what is sent (secrets redacted) before anything leaves the machine, an Ask
  panel, and explain-error and explain-command. Nothing runs without a user action.
- **Accessibility and languages**: the sidebar is an ARIA tree driven by the keyboard, visible
  focus rings, reduced motion, and no serious axe-core violation on the main screens; the interface
  speaks English and Brazilian Portuguese and follows the system language.

### Security

- Strict content security policy (no eval, no remote content), minimal Tauri capabilities per
  window, links open only as http(s) after a confirmation, and file names from mods, themes and
  backgrounds are checked against path escapes. See `docs/SECURITY_REVIEW.md`.
