# Changelog

All notable changes to Noren are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses
[Semantic Versioning](https://semver.org/).

## [Unreleased]

### Fixed

- **A terminal no longer shrinks to 2 columns while it is hidden or the window is minimized**: the fit of a terminal ran whenever the box that holds it changed, also when the box had no room (the tab hidden, the pane folded away, the window minimized), where the fit addon answers its minimum of 2 columns; the terminal took that size and so did the session, and from then on a Windows shell broke everything a program wrote into lines of two characters, which stayed broken after the window came back. A fit now changes nothing, in the terminal and in its session, while the view is not shown, the page is hidden (`document.visibilityState`), the box has no width or no height, or it would give fewer than 20 columns or 3 rows (`planFit` in `fit-limit.ts`): the terminal keeps its last good size. One fit with the real size runs when the view is shown again, when the page becomes visible or when the window leaves the minimized state. A pane made narrow on purpose (a dragged split) still shrinks, but never below 20 columns: under that the pane cuts the picture instead of shrinking the session. Vitest for the decision (a box 0 and 10 pixels wide, a hidden page, a view that is not shown and its return, and a session that is never given fewer than 20 columns or 3 rows).
- **A pane row with no name and no program title keeps its whole folder in the glass style**: in the sidebar the row of such a pane (a split pane that runs a command) had one line, so the folder was cut to `/srv…` and the duration touched the state (`<1s` against `ocioso` or `em execução`, in Portuguese). The row has two lines now, like the rows of a named pane: the folder, then the command, its duration and the state. The dense style is unchanged
- **The Projects section lights the action whose command is running, wherever it runs**: the state of an action followed its tab, so a tab opened by one action, split, with another loop started in the new pane and the first pane closed, still showed the first action as running and the second as idle. The state follows the pane the command was typed into now: the action runs while that pane exists and its session is alive, **Stop** and **Stop now** end only that session, and closing the pane (or its session ending) makes the action idle while the tab stays open with its other panes. A pane that comes from splitting another does not take its action or its name. A terminal pane of any space that is running the command of the action (a loop typed by hand, or one that was running when the app was closed and kept by the session daemon) lights the action too, compared with the command line the shell reports, spaces trimmed and collapsed, and **Stop** ends that pane; with the command in two panes the one the action started wins, else the one seen last. A **Start** after the pane closed types the command in a free pane of the tab, else opens a new tab. Nothing new is saved in `state.json`: after a restart the pane is found again by its command. Vitest for the executor (the case above, a split that inherits nothing, the pane closed with the tab open, a command started by hand, a command in two panes) and an end-to-end test of the case. The process tree is not used for this: it only identifies agents.
- **The end-to-end tests load the page without a network connection**: a full run opened about 12000 TCP connections to the preview server and Windows refused some of them (`net::ERR_ADDRESS_IN_USE`), so now and then a page arrived without its stylesheet or a script and the test failed for a reason that had nothing to do with what it checks. `e2e/test.ts` makes each browser context answer the requests for the page from `apps/desktop/dist` (marked with `x-noren-e2e: disk`), and every spec takes `test` and `expect` from there; `e2e/served-from-disk.spec.ts` proves that the document, every script and every stylesheet come that way. 480 of 480 runs of the window browser spec pass with 8 workers, with no connection left in `TIME_WAIT` on the port of the server. No assertion changed.
- **The picture chooser test waits for the preview to be decoded**: the preview of a chosen picture is on screen (and visible) a moment before its bytes are read and decoded, and the settings test read its size at once, so it saw 0 by 0 instead of 48 by 32 now and then (1 failure in 1949 in a full strict run; 0 in 880 alone). A helper in `background-picker.spec.ts` waits for the size, as the dialog test did, and all three uses share it; with the address of the picture held back 300 ms in a probe the old reads fail 20 of 20 and the new one passes 110 of 110. The app is unchanged.
- **A terminal can no longer grow past its window**: the fit of a terminal reads the size of the box that holds it, and when the page did not get its stylesheet (a request for it that failed) that box took the size of the terminal inside it, so every fit made the terminal taller than the one before: canvases from 25 600 to 972 048 pixels high that changed with every frame, a page that could not be used (a "Close" button that never held still, a click that always landed on a canvas). The fit now cuts the grid to the cells the window holds (`fit-limit.ts`), so the loop reaches a fixed point at once whatever the page does; a terminal inside a styled page is not touched (its box is never larger than the window). Two end-to-end tests put the page in that state, one with the stylesheet refused and one with the parts of the terminal back in the flow (0 of 80 pass without the change, 80 of 80 with it), and Vitest covers the limit.
- **The web page of a browser pane sits exactly on its pane after the space slides in**: the area of the pane moves a fraction of a pixel while the space slides in (after a reload or a switch of space), and the watch for a move did not see an animation end a fraction of a pixel from where it had last looked, so the web view stayed a pixel off (x 750 for an area at 749 in the browser, 3 in 5 runs with the slide slowed down). The pane looks again, and watches from the new place, when an animation or a transition above it ends (`observeSettle` in `observe-move.ts`). The space button with a mark (unread output, bell) hides the words it is described by from the tree, as the group row does, so its visible text is no longer counted against its name. Tests: the intermittent ones of the family now wait for what they need (the focus of the terminal before the bar takes the keyboard, the animations to end before a measure, the wheel events together), with no fixed wait.
- **The tests of the command palette no longer fail now and then**: the property test of the reducer played random sequences with a new seed on every run and its coverage checks (each action applied for real, a split over the limit) failed about one run in fifteen without saying which sequences did it; it plays a fixed seed now (`NOREN_PROPERTY_SEED=<number>` plays another one, and a failure names its seed), with a test that the same seed plays the same sequences. The specs that open the palette pressed its shortcut as soon as the tab list was on screen, a little before the shell had its keyboard listener (about 60 ms later in a loaded run), so the key reached no one, and an Enter in the next palette could lose the keyboard to the terminal that the previous close handed it back to one frame later; one helper (`e2e/palette-fixture.ts`) now waits for the listener, lets that frame go by, presses the shortcut once and waits for the dialog, and every spec that opens the palette uses it (48 files; the app is unchanged). The six specs that failed 18 times in 1600 runs (`--repeat-each=40 --workers=8`) pass 1600 of 1600.
- **The first prompt with one tab comes under 500 ms with room to spare**: in three series of 5 cold starts it came in 432, 421 and 460 ms (median 433 over the 15; it was 511 and 536 in two series before, 430 against 407 ms on the same day with the two builds started in turn), and the window and the terminal look the same (the pictures of the real app are the same file, byte for byte). Four cuts, none of them changes what is drawn: the shell of the tab on screen starts without waiting for `wsl.exe` to list its distros (about 70 ms, which the shell had waited for), the web view's browser process starts on a thread from the first line of `main` instead of after the builder (about 15 ms), the page asks for the settings, the themes, the mods and the saved state as soon as its script runs instead of one after the other when its boot reaches them (the boot went from 64 to 22 ms), and `index.html` names the scripts of the app so they are fetched with the entry script. Measured and dropped: loading the dialogs and panels the first terminal does not draw only when they are opened (no change in the first prompt, once the scripts of the app are fetched ahead). Numbers and the table of steps in `docs/PERF.md` (section 9).
- **Starting the app with many tabs saved no longer waits for all of them**: the first prompt with 100 saved tabs came after 3.9 s (about 35 ms per tab: the restore started the shell of every tab and mounted a terminal for each one before the first showed). Now only the tab on screen gets its shell and its terminal first (539 ms with 100 tabs, 494 ms with 1); the shells of the other tabs start in the background, 12 at a time, once the first prompt is on screen, or at once when you open their tab, and a restored tab shows everything its shell printed while it was out of sight and takes typing as before. Shells kept by the session daemon are taken back the same way, and the ones no tab claimed are ended once every tab has had its turn (`restore-settled`); closing the app before a tab's turn keeps that tab's shell for the next start. The whole start (the last prompt) is about 10 % slower (4.5 s with 100 tabs) and the memory with 100 tabs 88 MB higher (594 MB), both measured and written in `docs/PERF.md` (section 8).
- **The tests no longer take the whole PC**: a full `pnpm e2e` opened about 16 browsers and froze the machine. Vitest now uses at most 8 workers, Playwright at most 8 and cargo `CARGO_BUILD_JOBS=8`, always; while the maintainer is playing (game mode) the three drop to 4. A smaller `CARGO_BUILD_JOBS` already set is kept. `scripts/game-mode.mjs` is the only place that decides.
- **The names of the sections are one line in the dense settings screen, in Portuguese too**: the column of sections of the dense screen broke **Arquivamento automático** onto a second line (the wide font of the style, JetBrains Mono, left the 192 px column too little). The column is 220 px now, each name is one line with its number in front, every name of both languages fits, and in a window narrower than 760 px (the column is 168 px) a name that does not fit is cut by an ellipsis inside its own row instead of breaking or leaving it.
- **The highlight of the window stays the color of the space when the interface style is switched**: the theme sets its accent on the root again whenever the style changes (it did before, too, switching to or from glass), and the color of the active space that the window takes for its highlight was only put back when the space or the theme changed, so after a switch the ring of the pane in focus, the active row and the mark of the space were the accent of the theme (coral in the default theme) until the next time the space changed. The shell puts the color back after every switch of the style. Seen in the picture of the real app taken after a switch; two end-to-end tests hold it.
- **The long names of the dense sidebar are cut inside their rows**: the rows of the dense sidebar spent their 200 px on a second line (the folder and the branch) and on a Start button, and the wide font (JetBrains Mono) left little for the name, so names came out cut short (`Dev serv…`, `~/projects/no…`). The rows are one line now, and every name that does not fit (a tab, a group, a space tab, a favorite, an agent) is cut by an ellipsis inside its own box, from the narrowest sidebar (180 px) to the widest (480 px), with nothing leaving the sidebar or scrolling it sideways.
- **The Ligatures switch of the theme editor is the size of a switch**: it was 2 by 2 px (its knob 0 px), so the box that turns the ligatures of the preview on and off was a dot. The switch is drawn in a unit (`--su`) that only the settings dialog defined, and the editor is not inside it (it is drawn over it), so every size of the switch was invalid there. The editor defines the unit now, in both interface styles: its switch is 40 by 24 px with a knob of 16 (20 under glass), and the settings screen is unchanged.
- **The Portuguese interface has one name for the favorites**: the region of the bar and the button that opens it said _Favoritos_, while the menus, the announcement of the drag and the line of the empty bar said _favoritas_ ("Adicionar às favoritas", "Remover das favoritas", "Opções da favorita", "Adicionar esta aba às favoritas"). It is _Favoritos_ everywhere now ("Adicionar aos favoritos", "Remover dos favoritos", "Opções do favorito", "Adicionar esta aba aos favoritos", and the line of the empty bar), and the sentence of the auto-archive setting that said "favoritas" says "favoritos" like the schema text does.
- **The settings screen no longer scrolls to the side in Portuguese**: the **Sync through** selector (_Sincronizar por_) of the Sync section was 22 px wider than the dialog, so in the real app a horizontal scroll bar showed under the screen. The cause was the narrow third column of the old screen: a label and a selector side by side did not fit it. The new screen puts every control in one column of its own, with room for the labels, and a test measures the dialog and its content in English and Portuguese, in the dark and the light theme, at 1280 and 900 px wide: it fails if anything is wider than the content or if the screen scrolls to the side.
- **The terminal is no longer a black block over a background picture**: with a picture behind the window (or an interface that lets the window through) the terminal was solid black and hid it, in the app and in the browser build alike. The cause was not the WebGL renderer: xterm.css gives the scrolling box of every terminal a solid black background, and the version of xterm.js the app uses paints the color of the theme only on the element inside that box, so a terminal drawn with a see-through background showed the black behind it. The style of the app now gives the box no color, and each terminal over a picture is a pane of glass (the color of the terminal at the opacity of the interface), so the picture shows through the sidebar and the terminals and the text keeps its contrast. A browser test reads the pixels of the page to prove it and fails without the fix; the pictures of the real app (`pnpm shot`) show it for the Dusk and Paper themes and for a tab split in three
- **The background picture named in the settings file shows when the app starts**: a picture in `appearance.background.image` was asked for as soon as the settings were read, a moment before the app had given the part that reads the picture its way to the files, so the ask failed with "No backend is available to read the image" and was never made again; the window started with no picture (and a notice) until the setting was changed. The ask now waits for that and is made when it is possible. Found by starting the real app with the picture in its settings file.
- **A tab with many panes no longer makes a terminal lose its drawing**: the page can hold 16 WebGL contexts and the browser takes the oldest away past that. A split draws the pane that was split again, so a tab grown to 8 panes made 21 terminals (21 contexts) over its splits, and 5 contexts were taken away from terminals in use when measured in a browser; each terminal now frees its context when it goes away, and the same tab makes 21 and loses none.
- **A new tab opens in your user folder, not in the folder Noren is installed in**: a tab with no folder of its own (a new tab, a profile that names no start folder) opened in `C:\Users\<you>\AppData\Local\Noren`, because the app sent its own current folder to the session daemon with every session that had none. Now the session manager of the core gives such a session the folder of the user (`USERPROFILE` on Windows, `HOME` elsewhere) in one place, and falls back to the folder of the process, with no error, only when that folder is missing or cannot be read. A folder that is given (a profile, a project action, a `noren://` link) and the last folder of a restored tab open where they did. `pnpm smoke` now prints `SMOKE first shell cwd: <folder>` for the first shell and fails when it is not the folder of the user; new tests open real shells with the process in another folder.
- **No test run of the app takes the focus of the computer**: the hidden window of the app could still become the window in front of the system a moment after the program started (about once in five runs when measured with the picture mode), which drops a game in full screen. Every test mode of the app (`--smoke`, `--smoke-deeplink`, `--smoke-quick`, `--smoke-window`, `--smoke-api`, `--smoke-persist`, `--smoke-perf`, `--smoke-shot`) now makes all its windows without the focus, not focusable and off the taskbar (the main window, the second window, the quick window and the web view of a browser pane), never asks for the focus, and watches the window in front of the system from the first instruction of the program: each mode prints `SMOKE focus never taken: <n> look(s)` before its OK line and fails, saying which window and when, if a window of the app was ever in front. `pnpm smoke` and `pnpm perf` require the proof. A normal start is unchanged: the window is shown and has the focus.

- **The theme and the window effect change while a browser pane is open**: changing the theme (which also sets the Mica, Acrylic or vibrancy effect behind the window) was refused with "current webview is not a WebviewWindow" while a browser pane was open, because Tauri stops calling a window a webview window once a web view is a child of it. The command now takes the window that calls it as a window.
- **The main window is found while a browser pane is open**: quitting from the tray icon, "Open Noren", a `noren://` link or a second launch bringing the window up, and the focus read that decides whether a notification is shown all missed the main window while a browser pane was open, because Tauri stops calling a window a webview window once a web view is a child of it. They now look the window up as a window.

### Added

- **Each pane of a split can have a name of its own, so the panes of a split of project loops are told apart**: the header of a pane (glass and dense) and its row in the sidebar write the name in bold before the folder, where every pane used to show only the same folder. Rename a pane with **Rename pane** in the menu of the pane header, in the right-click menu of the terminal and in the right-click menu of its row in the sidebar, or press F2 on the row; a blank name takes the name away and the pane shows its folder as before. A pane that a project action opens is named after the action (for example **Loop**), the name follows the pane when its tab is merged into a split or the pane is taken out of one, and it is saved in `state.json`, so it survives a restart. English and Portuguese; app: `Pane.name`, the action `pane/rename` and `MAX_PANE_NAME` in the model, `PaneNaming` in the sidebar tree, `PaneName` in the pane header bar; Vitest for the action, the state file and the project action, and an end-to-end test of a split of two panes opened by different actions
- **A pane with no name of its own is shown by the title its program sets in the terminal**: a program that names its window (`OSC 0` or `OSC 2`, as a shell prompt, an editor or a build tool does) now names its pane, in bold before the folder in the pane header (glass and dense) and on its row in the sidebar; a name you give the pane still wins, a blank name brings the title back, a program that clears its title brings the folder back, and a title that only repeats the folder is not written twice. The title is as long as a name at most (80 characters), belongs to the running program and is never saved, so a pane restored after a restart starts with its folder.
- **A project action can wait for its session to end when it is stopped (`"stopWaits": true`)**: with the field, the `stop` command runs as before and, when it ends with code 0, Noren no longer ends the shells of the tab. The action reads **Stopping** (an amber dot, an hourglass and the word on its button, in the Projects section) until the session of its tab ends on its own, and then goes back to idle. A click on the button of a stopping action offers **Stop now**, which ends the sessions at once without running the `stop` command again (the context menu of the tab offers **Stop <label> now**); the tile of the action in the Favorites bar keeps showing its tab meanwhile. A failing `stop` command still leaves the action running, and without the field, or with `"stopWaits": false`, nothing changes. A value that is not `true` or `false` makes the file invalid, as for `main`. English and Portuguese; documented in `ACTIONS.md`; Vitest for the file and for the executor, and end-to-end tests with `FakeBackend` (`e2e/project-actions.spec.ts`, `e2e/projects.spec.ts`).
- **A Projects section in the sidebar lists every space that has project actions, so you can start and stop each project without switching spaces**: above the tabs, one block for each space (in the order of the space switcher) that has a valid `.noren/actions.json` with at least one action. A closed block is one line: a state dot (lit while any action of the space runs), the name of the space and the Start or Stop button of its main action, the one marked `"main": true` in the file, else the first. A click on the name opens the block, which lists the other actions, and whether it is open is kept for each space. The button runs the action in its own space, opening its tab there when needed, and the space on screen does not change; the first run still asks first. The space on screen is highlighted, and the actions are no longer drawn a second time in a header (the header of the active space, and the actions at the right of the bar under the title bar in the dense style, are gone). The menu of a space has **Show in Projects**, on by default, to take it out of the list. English and Portuguese; a saved state from before opens as it did. Files read again every 2 seconds like the Favorites bar; docs `ACTIONS.md`, `THEMING.md` and `ARCHITECTURE.md`; Vitest for the main action, the list and its filters, the two new actions and the old state, and end-to-end tests with `FakeBackend` (`e2e/projects.spec.ts`) in both styles and languages.
- **A tab of a WSL distro shows its folder, its branch and its commands, and the Agents panel sees the agent that runs in it**: the profile of a distro (`wsl.exe -d <distro>`) used to start the shell of the distro with nothing of Noren in it, so its tab never knew where it was, what ran, or which branch, and the Agents panel could not see `claude` (the process tree of Windows ends at `wsl.exe`). Now a small launcher starts the login bash of the distro with the same script as the other bash shells (a login shell, as `wsl.exe` starts it, so `/etc/profile` and the profile of the user load first), and a shell that is not bash (zsh, fish) starts as it did, with no integration. The path of the script goes in `WSLENV` with the `/p` flag, so WSL translates it for the way that distro mounts its drives, and the `WSLENV` you have is kept. The folder is reported the way Windows names it: `//wsl.localhost/<distro>/home/ada/proj` for the files of the distro and `D:/Projetos/noren` for a drive seen from inside (`/mnt/d/...`), so the branch of both is read from the files like any other folder, and the sidebar and the name of the tab show it as the distro knows it (`/srv/api`, and `/` for the root of the distro, not the name of the distro). The agent comes from the line of the command (`OSC 633;E`), as it already did for any shell. A tab restored in the folder it was last in starts there again: `wsl.exe --cd` refuses the `\\wsl.localhost\...` form, so the folder of the profile's own distro is turned back into its Linux path (`--cd /home/ada/proj`) after Noren checked it exists, and a folder on a drive stays the folder of the process. A profile with `inject_integration` off, and one whose arguments choose a command, a shell type or a management option, start exactly as before. The real shell was tried in a distro that was already running, in a folder made and removed by the test; the distro was neither started, stopped nor changed. App: `wsl.rs` in the core (`is_wsl`, `scan_wsl_args`, `wsl_integration_args`, `wslenv_with_script`, `folder_in_distro`, `Profile::place_wsl_folder`, `WSL_LAUNCHER`), the WSL branch of `spawn_spec_with_integration`, `spec_with_options` in the bridge, `__noren_wsl_folder` in `noren.bash`, `wslFolder` in the model for `shortCwd` and `folderName`; `cargo test` for the spec, the folders and the script, `tests/wsl_integration.rs` for the real distro, Vitest for the model, the tracker, the restored tab and the agent, and 5 end-to-end tests with FakeBackend and axe (`e2e/wsl-tab.spec.ts`); docs.
- **A tab nobody named is called after its folder, and after its command while one runs, instead of "Tab 1" and "Tab 2"**: the name of a tab with no title the person typed is the last part of the folder its shell reports, from the first one (a fresh tab in your home folder is `~`; `C:\Users\ada\proj`, `/home/ada/proj/` and the like are `proj`; a root is shown as it is) and, while a command runs, `·` and its program after it (`api · npm`); the number (`Tab 3`, `Aba 3`) stays only while no folder is known (a shell with no integration). One rule in the model (`tabLabel`) gives the name to the sidebar, the bar of the top tabs, the favorites, the breadcrumb of the dense window, the palette, the search and the switcher, so they can no longer disagree; the title the person typed always wins, the window title a program sets is not read, and leaving the box of the name as it was shown no longer locks the title; app: `tab-label.ts` in the model (`tabLabel`, `autoTabTitle`, `paneTitle`, `folderName`, `commandName`, `shortCwd` and `speakingPane` moved there), `Pane.shellCwd` and the action `pane/set-shell-folder` (the tracker tells the folder at once through `onFolder`), `itemLabel` in the sidebar, the tab bar, the drag announcements and the rename box, `FakeBackend.reportFolder` and the web key `noren.web.folder-report`; Vitest for the rule over Windows, POSIX, root and trailing-slash paths, the tracker, the action and the store; end-to-end tests with `FakeBackend` and axe in both styles and languages (`e2e/tab-names.spec.ts`, 21 tests) and `e2e/command-meta.spec.ts` rewritten for the new names, 12 specs that tell tabs apart by `Tab N` keep a shell that tells no folder (`e2e/numbered-tabs.ts`) and 3 that need the folder (library, reopen-closed, palette) read `~`; docs; roadmap F20-12 ticked

The page stays out of view while its tab is not shown, closes with its tab, and comes back to the main window with its tab (loaded again from the address the pane holds); a window the person closes leaves no page behind. A window used to refuse any tab with a browser pane, saying it stays in the main window; it does not any more.
- **Preview and diff panes in a window of their own**: a tab with a file preview or a git diff pane (with or without terminals beside it) can now go to a window, by dragging it out or with "Move tab to new window" in the palette, and the window draws the pane: the file with its path on top (markdown, JSON, text, pictures) or the changed files with the picked one side by side, with the refresh button of the diff. A window page cannot read files or run git, so the main window reads for it: the page asks, the main window checks that the pane is one of the window's and that the path or folder is the pane's own, reads it and answers that window; any other request is ignored. A file that is gone or a folder that is not a repository is said in the window, as in the main window. A tab with a browser pane still stays in the main window (the web view of a browser pane moves in the next step). `window-sync.ts` (`window-read`, `window-read-result`, `readOfWindowRequest`, `followWindowReads`, `createWindowReads`), `WindowApp.tsx`, `windowCanShowTab`, `/?window-preview` (its panels now get a backend that refuses the two reads, as the real window does), `e2e/window-panes.spec.ts` (9 tests, they fail without the new code) and `docs/ARCHITECTURE.md`.
- **Sidebar in a window of its own**: the window made for a tab now has the sidebar of its space, the same tree the main window has (the pinned tabs, the tabs, the mark of the one on screen and the unread and bell marks), in place of the row of tab buttons. The button New tab opens a tab with a new shell in the space of the window (the main window starts the shell, with the profile, folder and environment of that space, and the window takes its output over), Delete or Close in the menu of a tab closes it and ends its shell (closing the last one closes the window, and the space made for it goes away), and dragging a tab up or down puts the tabs in order, with no shell started or ended. The window asks the main window for each of these and the main window checks it (the window it comes from, a tab of that window's space, a new tab only in that space and only up to 64 tabs) and carries it out, so the main window is still the only one that owns the workspace and writes `state.json`. A tab that is read in a window loses its unread mark (the tab each window shows is read, as the one of the main window is), and the terminal of a tab brought to a window, or back to the main window, shows what its shell had printed instead of starting blank, when the shell runs in the session daemon (the daemon keeps a megabyte of it). Closing a window no longer loses what the shell printed before the main window took it back. Browser, preview and diff panes in a window are still to come: a tab that has one stays in the main window.
- **Tab in a window of its own**: dragging a tab out of the window (letting go of it beyond the edge of the window) or "Move tab to new window" in the palette makes a window with a space of its own and takes the tab there, with its shells untouched (the same session and process). The window draws the tabs and the splits of terminals of its space, with the state coming from the main window, which is still the only one that holds the workspace and writes `state.json`; a click on a tab, a click on a pane and a resize of a split in the window are carried out by the main window. Closing the window gives the tabs back to the space they came from, with their shells attached to the main window again. The windows come back when the app is opened again. A tab with a browser, preview or diff pane stays in the main window for now. In a browser (`/?window-preview`) each window is drawn as a panel, for the tests.
- **Windows (groundwork)**: the workspace can now have windows besides the main one, each showing a space of its own that no other window shows (`windows` in `state.json`, absent when there are none, so older files read as they are). The main window is the one owner of the state and the only one that writes `state.json`; a second window loads a small page that draws only the tabs moved to it, and is granted nothing of the state, the settings or the files. A tab moves to a window with its shells untouched (the same session and the same process; only the place the output goes changes). Nothing in the interface makes a window yet (dragging a tab out of the window is the next task); `noren --smoke-window` makes one hidden and moves a running shell to it.
- **Diff pane**: a pane that shows the `git diff` of a folder (the working tree and the index against `HEAD`, against the empty tree in a repository with no commit), with the changed files in a list and the picked one side by side: added, deleted, renamed and binary files, a change of mode, hunks with the line numbers of both files and the end-of-file marker. "Show git diff beside this pane" in the palette opens one beside the focused pane, on its folder (the start folder of the space when it has none), and says so in a notice, making no pane, when there is no folder, git is not run in it, or the tab is full. The pane is saved as a folder in `state.json`, starts no shell, asks git when it is on screen and again from its refresh button, and says in English and Portuguese why there is no diff (not a repository, no git, too large, git refusing). Git is run read-only, with no program from the repository's own settings. Untracked files are not listed.
- **Preview pane**: a pane that shows a file on this computer, inside a split: markdown (drawn by the same parser as the answers of the AI, so a picture, a link or a tag in the file is text and loads nothing), JSON written out with an indent (invalid JSON is shown as text with a warning), plain text, and a png, jpeg, gif or webp picture. The path is on top; a file that cannot be shown says why (a relative or network path, a folder, a missing file, a binary file, text over 1 MiB or a picture over 10 MiB), in English and Portuguese. A preview pane is saved in `state.json` by its path and comes back after a reload; it starts no shell. Ctrl+click (Cmd+click on a Mac) on a file path in the output, full or relative to the folder of the pane, with or without `:line:column`, opens one beside the terminal and leaves the keyboard with the terminal; a click without Ctrl does nothing. A path that cannot be opened (a folder on the network) or a tab with no room says so in a notice and opens nothing. A tab left with only a preview pane is named after the file.
- **Browser pane**: a pane that shows a web page, with an address bar, inside a split. Ctrl+click (Cmd+click on a Mac) on an `http` or `https` address in the output opens one beside the terminal; a click without Ctrl asks first, as before. The address bar refuses `file`, `javascript` and the rest with the reason; the page is saved with the tab and comes back after a restart. The web view is opened when the pane is first seen, follows the pane, steps out of sight under a dialog, in another tab or space or while another pane is zoomed, and is closed with the pane, the tab or the space.
- **Launch README and media**: `pnpm media` drives the web demo with a script (spaces, a tab dragged into a split, the palette, a theme change, Ask with the fake provider) and writes ten screenshots and a webm video to `docs/media/`; the README is the launch README, `docs/ROADMAP.md` is the public roadmap by version, and `pnpm readme:check` (part of `pnpm verify`) fails when a relative link or image of the README is missing.
- **Web demo**: `pnpm demo:build` builds a static copy of the interface into `dist-demo/` with a
  simulated shell, a script of example spaces, a group, a split and themes, and a strip that gives
  the download address; `pnpm e2e:demo` tests it; `pages.yml` deploys it by hand (`workflow_dispatch`).

## [0.1.0] - Unreleased

First MVP. Noren is a terminal organized like a modern browser. Windows is the first platform
(NSIS and MSI installers); the Linux build is an AppImage and a deb. The build is not signed and
has no automatic updater yet.

### Added

- **Terminal core**: real PTY sessions through `portable-pty` with batched reads, xterm.js with the
  WebGL renderer, shell profiles detected on the machine (PowerShell, cmd, bash, zsh and others),
  and a typed backend interface with a fake backend for tests.
- **Spaces, groups and tabs**: a workspace model with checked invariants; spaces with their own
  icon, color, theme and background image; a space wheel and git identity per space; groups, pinned
  tabs and favorites (a grid) with their origin and a "reset" action.
- **Sidebar**: a tree of spaces, groups and tabs with a second line of live metadata (folder, git
  branch, last command), unread marks and a bell, drag and drop between groups, spaces, pinned and
  favorites, and side, width, density and compact settings.
- **Layout modes**: sidebar or top tabs, switchable from settings and from the command palette.
- **Splits**: panes inside any tab, split by shortcut or by dragging, swap and detach panes, pane
  headers with zoom, and splits shown in the sidebar.
- **Command palette and shortcuts**: tabs, spaces, actions, profiles, recent folders and themes in
  one palette; a shortcut registry with a screen to review and rebind them; a most-recently-used
  switcher and a search across every tab.
- **Shell integration**: OSC parsing and integration scripts for PowerShell, bash, zsh and cmd for
  live folder, branch, last command and tab title; command marks; system notifications for
  finished commands in background tabs.
- **Project actions**: an `actions.json` in a project lists commands that run from the interface;
  `noren://` links open a folder in Noren (the installer registers the scheme).
- **Customization**: a commented `config.jsonc` with hot reload and a published JSON schema;
  a settings screen (appearance, shortcuts, notifications, terminal, profiles, auto-archive, AI);
  eight built-in themes, a theme per space, and import of color schemes and shell profiles from
  other terminals; user CSS mods; window material (Mica on Windows) and background images; fonts
  and terminal options.
- **Session life**: restore of tabs with scrollback after a restart, reopen closed tabs, auto-archive
  with a library that searches inside terminal content, peek at a tab without opening it, and a
  quick terminal window with a global shortcut that can be promoted to a normal tab.
- **Optional AI, local by default**: pluggable providers with keys kept in the system keychain,
  a preview of exactly what is sent (secrets redacted) before anything leaves the machine, an Ask
  panel, and explain-error and explain-command. Nothing runs without a user action.
- **Accessibility and languages**: the sidebar is an ARIA tree driven by the keyboard, visible
  focus rings, reduced motion, and no serious axe-core violation on the main screens; the interface
  speaks English and Brazilian Portuguese and follows the system language.

### Security

- Strict content security policy (no eval, no remote content), minimal Tauri capabilities per
  window, links open only as http(s) after a confirmation, and file names from mods, themes and
  backgrounds are checked against path escapes. See `docs/SECURITY_REVIEW.md`.
