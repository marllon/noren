# Architecture

Noren (暖簾) is the curtain split into panels that hangs in the doorway of Japanese shops. It is the name and the metaphor of the product: a space divided into panels, each one leading somewhere.

## Principles

1. **Your way.** Sidebar on the left, on the right, hidden, or tabs on top; nested groups or a flat list; a theme per space; your own CSS. No layout is imposed.
2. **Windows is a first-class platform.** Developed and tested on Windows first (ConPTY, PowerShell, Git Bash, WSL, Mica). macOS and Linux are guaranteed by CI.
3. **Light.** Tauri 2, no Electron. Opens fast, uses little memory.
4. **Keyboard and mouse.** Everything has a shortcut, and everything also works with click and drag.
5. **Optional, safe AI.** Off until the user configures it; local (Ollama) by default; never runs a command on its own; shows what it is about to send.
6. **No account, no telemetry.** Everything is local. No data leaves the machine without an explicit user action.

## Layout of the repository

```
noren/
  apps/desktop/                 Tauri 2 app
    src/                        React 19 + TypeScript interface
    src-tauri/                  thin Rust layer: commands, events, window, menus, global shortcuts
  crates/noren-core/            Rust library without Tauri: PTY, profiles, config, persistence, git, AI client, session daemon (server and client)
  crates/norend/                the session daemon as a program, which the app starts and keeps its sessions in (see DAEMON.md)
  packages/model/               pure TypeScript: data model, operations, invariants, Backend interface, FakeBackend
  e2e/                          Playwright in web mode (FakeBackend)
  docs/                         ARCHITECTURE, THEMING, CONFIG, PERF (English)
  themes/                       built-in themes (JSON)
```

- **pnpm workspaces** (`apps/*`, `packages/*`) and a **Cargo workspace** (`crates/*`, `apps/desktop/src-tauri`) at the root.
- **`noren-core` does not depend on Tauri.** It is tested quickly with `cargo test -p noren-core` and is designed to later become a standalone daemon.
- **`Backend` interface** (in `packages/model`): `listProfiles`, `setUserProfiles`, `createSession`, `reattachSession`, `setKeepSessions`, `write`, `resize`, `kill`, `onOutput`, `onExit`, `onSessionLink`, `retrySession`, `loadState`, `saveState`, `quarantineState`, `loadScrollback`, `saveScrollback`, `listScrollback`, `deleteScrollback`, `loadConfig`, `saveConfig`, `watchConfig`, `listUserThemes`, `saveUserTheme`, `saveBenchResult`, `listBenchResults`, `listMods`, `watchMods`, `setWindowEffect`, `readBackgroundImage`, `listMonospaceFonts`, `readHardware`, `gitInfo`, `scanAgents`, `openBrowserPane`, `navigateBrowserPane`, `setBrowserPaneBounds`, `closeBrowserPane`, `readFilePreview`, `openWindow`, `closeWindow`, `moveTabToWindow`, `onWindowClosed`, and the AI side as the `ai` member (`ai.providers`, `ai.configure`, `ai.setKey`, `ai.listOllamaModels`, `ai.testConnection`, `ai.chat`, `ai.cancel`; see [The AI providers](#the-ai-providers-and-their-settings)). There are two implementations: `TauriBackend` (the app) and `FakeBackend` (tests, end-to-end runs and the web demo). The interface never imports anything from the DOM or from Tauri.
- **Terminal output flow.** A PTY reader thread in Rust gathers bytes into batches (up to 64 KB or 8 ms) and sends them through a `tauri::ipc::Channel` with a binary payload (`ArrayBuffer`). The interface writes the `Uint8Array` straight into xterm. Input goes the other way: xterm's `onData` becomes `invoke('session_write')`.
- **Where the sessions live.** `AppState.sessions` (`daemon_link.rs`) keeps them in `norend`, the session daemon, which the app finds on its endpoint or starts next to its own executable (hidden, as a program of its own), and in a `SessionManager` inside the app when there is no `norend`. The PTY reader thread above then runs in the daemon: the batches travel over a named pipe or a Unix socket to the app, which hands them to the same route and channel as before, so nothing above `Sessions` knows which of the two it has. Typing and resizing use a connection of their own so they never wait behind a session that is starting or ending. See [DAEMON.md](DAEMON.md#the-app-as-a-client).
- **Shells that outlive the window.** With `sessions.keepOnClose` on (the default) and the sessions in the daemon, closing the app leaves the shell of every pane running in `norend` and the next start gives each restored pane its shell back: `createSession` carries the id of the pane, `persist.rs` and `pane_sessions.rs` write down which session and process belong to which pane (`sessions.json` next to `state.json`), `restoreWorkspace` asks `reattachSession(paneId)` before it creates a shell, and the shells no pane came back for are ended once the page is up. Nothing changes with the setting off or without a `norend`. See [DAEMON.md](DAEMON.md#shells-that-outlive-the-app).
- **Staying in the tray.** In that same case closing the window only hides it (`lifecycle.rs` asks `tray::close_outcome`, a pure function of the setting, where the sessions live, whether the tray icon is up and whether the person is quitting) and the app stays in the notification area; the icon's "Quit" is the real quit: `AppState::begin_quit`, then the window closes the normal way and `end_sessions_on_exit` calls `Sessions::quit_for_good`, which sends `Shutdown` to the daemon and waits until it is gone and its endpoint free. The installers carry `norend` next to `noren` (`bundle.externalBin` from a second config file that only `pnpm desktop:build` uses) and stop it before they replace it (`norend --stop`). Everything that has to reach the main window from the Rust side (the quit of the tray, the "Open Noren" entry, a link or a second launch bringing it up, the read of its focus for a notification, the show at the start, the smoke checks) finds it through `lifecycle::main_window`, which looks it up as a `Window`: while a browser pane is open its web view is a child of the main window, and Tauri then stops calling that window a webview window (`get_webview_window` answers `None`, `get_window` still finds it). The same holds for a command: `window_effect_set` (the theme and the effect behind the window) takes its caller as a `Window`, because Tauri refuses a `WebviewWindow` argument from a window with such a child. See [DAEMON.md](DAEMON.md#the-tray-icon-and-quitting-for-real).
- **A daemon on another machine.** `norend --bridge` relays one connection to the daemon of its user over standard input and output, and `SshTarget` (`noren-core`, `daemon/ssh.rs`) runs it through the `ssh` of the system (keys only, no prompt, no window), so a `DaemonClient` speaks the ordinary protocol over the pipes of `ssh` (`DaemonClient::connect_stream`). `ReconnectingClient` (`daemon/reconnect.rs`) keeps such a client up: when the connection breaks it connects again with a bounded backoff and attaches the sessions by their ids, reporting connected, reconnecting and failed; the shells never noticed, because the daemon on the other machine never stopped. See [DAEMON.md](DAEMON.md#the-remote-bridge-ssh).
- **A tab on another machine.** A profile of kind `ssh` (`user-profile-schema.ts`, `UserProfile` in `noren-core`) opens its shell in the `norend` of that machine. `create_session` sees `Profile.remote`, builds the spec from the profile alone (`Profile::remote_spec`: no environment, no folder of this machine) and hands it to `remote.rs` (`RemoteSessions`), which keeps one `ReconnectingClient` per machine and gives each session an id of its own (from `REMOTE_ID_BASE`) so it never meets a local one; `write`, `resize` and `kill` of `Sessions` go where the id says. What a reconnection reattaches is shown without repeating what the tab already has (`daemon/replay.rs`), and the state of the connection reaches the page as the `session-link` event (`Backend.onSessionLink`, with `retrySession` for the `session_retry` command). See [DAEMON.md](DAEMON.md#ssh-profiles-in-the-app).
- **Interface state.** Zustand wraps the pure reducer from `packages/model`; the operations do not know React exists.
- **Interface libraries.** `@xterm/xterm` and its addons (webgl, fit, search, web-links, unicode11, serialize), `cmdk` (command palette), `@dnd-kit` (drag and drop), `react-resizable-panels` (splits), `lucide-react` (icons). All are MIT or ISC.
- **Crates.** `portable-pty`, `serde` / `serde_json`, a JSONC parser, `notify` (config reload), `keyring`, `reqwest` (rustls), `tokio`, `window-vibrancy`, `fontdb` (the monospaced fonts installed on the machine), `sysinfo` (the process tree, for the agent detector; only its `system` feature), `sha2` (the hash of a gallery download), and the Tauri plugins (`global-shortcut`, `notification`, `dialog`, `opener`).
- **App identifier:** `io.github.marllon.noren`. Binary: `noren`.

## Data model

Defined in TypeScript in `packages/model`.

```ts
type Id = string;

interface Workspace {
  // state saved in state.json
  version: 1;
  spaces: Space[];
  activeSpaceId: Id;
  favorites: Id[]; // item ids, global
  favoriteLinks?: FavoriteLink[]; // the profiles and project actions of the Favorites bar; absent in a state saved before them
  closed: ClosedItem[]; // stack, at most 50
  archive: ArchivedItem[];
  windows?: AppWindow[]; // the windows besides the main one; absent when there are none, see "Windows"
}

type FavoriteLink =
  | { kind: "profile"; profileId: string; label: string } // a click opens a tab with the profile
  | { kind: "action"; spaceId: Id; actionId: string; label: string }; // a click runs the action the space file declares under actionId

interface AppWindow {
  id: Id; // names the native window, "window-<id>": letters, digits, - and _, at most 64
  spaceId: Id; // the space the window shows; no other window shows it, and the main window shows activeSpaceId
}

interface ClosedItem {
  item: Item; // without sessions
  spaceId: Id;
  closedAt: number;
  place?: { list: "pinned" | "tree"; groupId?: Id; index: number }; // where it sat; absent in a state saved before this field
}

interface ArchivedItem {
  item: Item; // without sessions
  spaceId: Id;
  archivedAt: number;
  place?: { list: "pinned" | "tree"; groupId?: Id; index: number }; // the same slot a closed item keeps
}

interface Space {
  id: Id;
  name: string;
  icon: string;
  color: string;
  themeId?: string;
  background?: { image: string; opacity?: number; blur?: number }; // a picture file on this computer
  modIds: string[];
  defaults: {
    profileId?: string;
    cwd?: string;
    env: Record<string, string>;
    gitIdentity?: { name: string; email: string };
  };
  aiEnabled: boolean;
  saveScrollback: boolean;
  pinned: Id[]; // item ids, visual order
  tree: Node[]; // sidebar below the pinned items
  items: Record<Id, Item>; // every item of the space (pinned and in the tree)
}

type Node =
  | { kind: "item"; id: Id }
  | {
      kind: "group";
      id: Id;
      name: string;
      color: string;
      collapsed: boolean;
      children: Node[];
      live?: LiveSource; // a live group, see "Live groups"
    }; // groups: up to 2 levels

type LiveSource =
  { source: "worktrees"; folder: string } | { source: "ssh" } | { source: "docker" };

interface Item {
  id: Id;
  title?: string;
  titleLocked: boolean;
  layout: LayoutNode; // 1 pane = a tab; 2 to 4 = a split
  focusedPaneId: Id;
  zoomedPaneId?: Id;
  origin?: { cwd: string; profileId: string; command?: string }; // to "reset" a pinned item
  liveKey?: string; // the entry of a live group the tab was opened from
  lastActivityAt: number;
}

type LayoutNode =
  | { kind: "pane"; pane: Pane }
  | { kind: "split"; dir: "row" | "column"; sizes: number[]; children: LayoutNode[] };

interface Pane {
  id: Id;
  type: "terminal" | "browser" | "preview" | "diff"; // 'agent' later
  sessionId?: Id; // terminal panes only
  profileId: string;
  url?: string; // browser panes only: an http or https address
  path?: string; // preview panes only: a full path of a file on this computer
  cwd?: string; // the folder of a terminal pane; of a diff pane, the folder whose git diff it shows (required)
  status: "running" | "idle" | "exited";
  exitCode?: number;
  lastCommand?: { text?: string; exitCode?: number; durationMs?: number };
  unread: boolean;
  bell: boolean;
  scrollbackRef?: string; // file holding the scrollback snapshot
}
```

Invariants (checked with property-based tests): every pane belongs to exactly one item; every item appears exactly once (pinned or in the tree); groups nest at most 2 levels; a split has between 2 and `maxPanes` leaves and its `sizes` add up to 100; ids are unique; no orphan session remains after closing an item, a space or a pane; a browser pane has an http or https `url` and no session, a preview pane has a full local `path` and no session and no `url`, a terminal pane has no `url`, and only a preview pane has a `path`; a window shows a space that exists, no space is shown by two windows (the main window shows `activeSpaceId`), a window id can name a native window, and there are at most 8 windows besides the main one.

## Files, configuration and themes

- `state.json`: the `Workspace` above. Written atomically (temporary file plus rename), debounced by 500 ms, with a `version` field and migrations. In `packages/model`, `serializeWorkspace` and `parseState` (version, migrations, shape check, `checkInvariants`) read and write the text, `StateWriter` does the debounce, and `restoreWorkspace` loads the file and starts one session per pane in its saved cwd. Sessions are never saved. A file that cannot be used (broken JSON, wrong shape, broken invariants, unknown or newer version) is copied by `quarantineState` and the default workspace takes its place.
- `bench-results/<YYYY-MM-DD-HHmmss>.json`: one file per bench run (see [BENCH.md](BENCH.md#the-results-on-disk)), in a folder next to `state.json`. `crates/noren-core/src/bench.rs` (`BenchStore`) names the file from the `startedAt` of the run, never from what the interface sends, writes it atomically and lists the newest first; the Tauri commands are `bench_save` and `bench_list`, and only the main window may call them.
- `scrollback/<paneId>.txt`: a snapshot (xterm serialize addon) of the last 2,000 lines, only when the space and the settings allow it (`terminal.saveScrollback`, see [CONFIG.md](CONFIG.md#saved-scrollback)). It sits in a folder next to `state.json`, and `Pane.scrollbackRef` in `state.json` says which panes have one.
  - **Saving.** `ScrollbackSaver` (`apps/desktop/src/scrollback-saver.ts`) writes the panes that printed since their last snapshot every 60 seconds, on an injected `Clock` (the tests move it by hand; web mode uses the clock of the fake shell), and once more when the window closes. In the app, closing is held by the Rust side (`apps/desktop/src-tauri/src/lifecycle.rs`): once the page has said it listens (`app_close_listening`), a request to close keeps the window, tells the page with the `close-requested` event, and destroys the window when the page answers `app_close_ready` or after 8 seconds; the page (`close-handler.ts`) starts the snapshots and flushes the state, and answers when they are written or after 2 seconds (6 when `sync.pushOnClose` is on, which pushes after the saves; the Rust side then waits 8 seconds). A page that never said it listens, or a second request while one is held, closes at once, as before. A call made from `beforeunload` while the window is torn down may never leave the page, so the page also starts the saves on `beforeunload` and `pagehide`, which is what web mode and a reload have; the snapshots are started before the state is flushed, so the notes they make on the panes are in the state written then. A pane is saved only if `savesScrollback(setting, space)` says so; when it says no, nothing is written and a file saved before is removed. The text is what the serialize addon makes of the normal screen, passed through `cleanSnapshot` (see below) and limited to 2,000 lines and 4 MiB. Saves of one pane never overlap.
  - **The folder.** `crates/noren-core/src/scrollback.rs` (`ScrollbackStore`) keeps text and does not look inside it. The id of the pane becomes a file name, so it must be ASCII letters, digits, `-` and `_` (at most 64, not a Windows device name): a path is refused before the disk is touched, by `load`, `save` and `delete` alike. The write is atomic (the same temporary-file-and-rename path as `state.json`), the size is limited in both directions, and reading or deleting never creates the folder. `ScrollbackStore::list` names the files that are `<valid id>.txt` and ignores everything else (a missing folder is an empty list). The Tauri commands are `scrollback_load`, `scrollback_save`, `scrollback_list` and `scrollback_delete`; the smoke run can read and list and never writes or removes there.
  - **Restoring.** At start, after the shells are restarted in their saved folders, `scrollback-restore.ts` reads the snapshot of each pane that records one and builds the text that shows it again: the saved lines dimmed (SGR 2, put back after every color so a reset in the old text does not end it), then the line `session restored <date and time>`. `TerminalView` writes that text to its xterm before it subscribes to the output of the new session, so it sits above everything the new shell prints.
  - **Closed tabs.** Closing a tab (the tab, its last pane, or its space) pushes it on `Workspace.closed` (50 at most, the oldest drops off) with its `place`: the list it was in (pinned or tree), the group that held it and its position, which `item/close` reads from the space before the item leaves. `state.json` validates `place` and a file without it still loads. `item/reopen` puts the item back in its space, in the same list, group and position (clamped to what the list holds now); a group that is gone, or an entry without a place, sends it to the end of the tree of its space, and a space that is gone to the end of the tree of the active space. The pane comes back clean (no session, the exit code and command of the old shell forgotten), with the same id, profile and folder. The snapshot follows the stack. `startScrollback` watches the workspace (`closed-scrollback.ts`, `closedChanges`): for the panes of the entries that joined the stack it asks their terminals for the lines while they are still alive (before the render that unmounts them) and writes them with `ScrollbackSaver.saveNow` as the action ends, under the same rules as the saves of every minute (`savesScrollback`: the setting of the app and of the space of the tab; an older file is kept when the terminal has nothing to say and removed when the rules say never); the note `pane/set-scrollback` reaches the panes of a closed entry. A pane with a file that is no longer anywhere in the workspace (open, closed or archived) because its tab fell off the stack of 50, its split pane was closed or a reset replaced it, has its file removed (`ScrollbackSaver.discard`). Reopening (`reopen-closed.ts`, `reopenClosed`) reads the snapshots of the entry the same way the start of the app does (`loadScrollbackForItem`), hands the dimmed text and the `session restored` line to the terminals that mount, and only then dispatches `item/reopen` and activates the space; the shell is new, in the folder and profile of the pane. Two reopens in a row are queued, each taking the newest entry left. A setting that has since turned saving off shows nothing and removes the file.
  - **Auto-archive and the library.** An idle open tab goes to `Workspace.archive` (`item/archive`, which keeps its `place` and drops its sessions like `item/close`, without the limit of 50), comes back with `archive/restore` (the same placement rules as `item/reopen`, which share their code in the reducer), and `archive/delete` and `closed/delete` forget an entry for good. `idleItems` (`packages/model/src/archive.ts`) is the pure rule: not pinned, not a favorite, not the tab on screen, no pane with a command running (`runningCommand`, set by OSC 133;C and cleared by 133;D) or `status: "running"`, nothing unread, and no sign of life for `archive.afterHours`. `AutoArchiver` (`apps/desktop/src/auto-archiver.ts`) asks every minute on an injected `Clock`: it keeps the last sign of life of each tab in memory (a pane's output, noted from the terminal; the tab on screen counts as alive at every check), with the moment the app opened as the floor, and dispatches `item/archive` for the idle ones. `Item.lastActivityAt` is not moved by activity (it says when the tab was made, restored or reset), so nothing is written to `state.json` for it. The scrollback files follow the lists with the same subscription as the closed stack (`closedChanges` reads the entries that joined the closed stack or the archive, the panes that left every list): a tab that is archived has its snapshot written as it leaves, and one that is deleted from the library has its files removed. `Library.tsx` lists both with the pure `library-entries.ts` and restores through `reopenClosed({ from: "archive" })`. In web mode the clock of the checks is the one of the fake shell plus the real time (`archiveClock`), so a test that advances it by hours finds every tab hours older. See [LIBRARY.md](LIBRARY.md).
  - **Search and sweep.** The library searches the text of the snapshots of its entries: `loadLibraryTexts` reads them in the background (four at a time), `snapshotSearchText` cleans each one and drops its colors, and `filterLibrary` matches the words against the title, the folder and that text and returns the line that matched (`snippet`, drawn as text). At start `sweepOrphanScrollback` (`scrollback-service.ts`) lists the folder, reads the workspace after that and deletes the ids `orphanScrollbackIds` says no pane of any space, of `closed` or of `archive` claims. See [LIBRARY.md](LIBRARY.md).
  - **Peek.** Resting the pointer on a tab of the sidebar for 400 ms opens a tooltip (`role="tooltip"`, pointed to by the tab's `aria-describedby` while it is up) with the last 15 lines that hold something of the terminal of the tab's focused pane. `PeekController` (`apps/desktop/src/peek-controller.ts`) is the pure rule on an injected timer: the wait starts when the pointer enters a tab and starts again when it moves on it, an open peek stays while the pointer moves on its tab, and leaving the tab, a button press, a click, Escape, the window losing focus, scrolling the list and the start of a drag (`useDndMonitor`, so the keyboard drag counts too) close it; while a drag is under way nothing opens, and after it a peek waits for the pointer to move. `usePeek` and `PeekPopover` (`Peek.tsx`) wire it to the tree: the popover is drawn in `document.body`, fixed beside the tab on the side that faces the terminal, kept inside the window, and has `pointer-events: none` and nothing that can take the focus. `peekLinesOfItem` (`peek-source.ts`) reads the lines: the terminal of the pane when it is mounted (`readTerminal(paneId, lines)` asks the serialize addon for the last 100 lines above the screen, not the 2,000 a snapshot keeps), else the saved snapshot of the pane when it records one. Either one is untrusted, so the text goes through `peekLines` (`packages/model/src/scrollback.ts`): `cleanSnapshot`, then the colors off, the empty lines out, each line cut to 200 characters. The lines are drawn as React text nodes, so output that looks like markup shows as the text it is. A tab with no output shows `No output yet`.
  - **Keyboard and roles.** The sidebar is an ARIA tree. `buildNav` (`apps/desktop/src/tree-keys.ts`) turns the visible rows into the list the keyboard walks (group headers, tabs, and the panes of an unfolded split tab, each with its level, set size and place), `treeKeyAction` says what Up, Down, Home, End, Left and Right do on a row, and `focusAfterRemoval` where the focus goes when rows leave; all pure and tested. `SidebarTree` keeps one row in the Tab order (roving tabindex), handles the keys on the `tree` element only for a plain press with no drag under way, and puts the focus back a frame after a Delete (a terminal that is shown again takes the keyboard in its own effect). Enter is the click of the button; F2 and Space were already there. The mouse-only toggle of the pane list is hidden from assistive technology (the tab itself carries `aria-expanded`). The tab bar is a `tablist`. The sidebar rows are named by their content: the secondary text (folder, branch, command) is `aria-hidden` and read as the description. Keys for the tree and the "Focus sidebar" action are in [KEYBINDINGS.md](KEYBINDINGS.md#the-sidebar-by-keyboard). `e2e/accessibility.spec.ts` runs axe-core on the main screens and fails on a violation of any impact (see Screen reader support).
  - **The snapshot is untrusted.** It is a file that another program could have changed, and a terminal obeys what it is written. `cleanSnapshot` (`packages/model/src/scrollback.ts`) keeps only printable text, tabs, line breaks and SGR color/style sequences, and runs on the way out and on the way in. Everything else is dropped whole: OSC (title, clipboard, notifications), DCS/APC/PM strings, every CSI that is not a color (modes, the alternate screen, mouse tracking, cursor moves, requests that make the terminal answer), single escapes, every control character and the eight-bit controls. The one CSI it uses is the move to the right the serializer writes over empty cells, which becomes blanks.
- `config.jsonc`: appearance (theme, density, sidebar position, compact mode, opacity, background), terminal (font, cursor, scrollback, paste), profiles (detected and user-defined, with `injectIntegration`), shortcuts, auto-archive, notifications, and AI (providers without keys; the key lives in the system keychain). JSON with comments and trailing commas, in the app config folder. The schema is zod, in `packages/model/src/config.ts`, with `docs/config.schema.json` generated from it (`pnpm --filter @noren/model config:schema`; a test fails when it is out of date). `noren-core` reads, writes atomically and watches the file (`notify`); the interface reads it with `Backend.loadConfig`, follows it with `Backend.watchConfig`, applies a valid text at once and, for an invalid one, keeps the last valid settings and shows a notice with the line. The settings screen writes it with `Backend.saveConfig`, after `editConfigText` changed only the settings that differ in the text read a moment before, so the comments of the file stay. See [CONFIG.md](CONFIG.md).

- **The window.** The main window is created transparent (`tauri.conf.json`), so an effect can show through the page; the page paints it opaque unless the opacity says otherwise. `Backend.setWindowEffect(effect, scheme)` asks the system for Mica, Acrylic or vibrancy, painted dark or light like the theme that was chosen (`system` while the theme follows the system), and answers what the window has: a system that cannot paint it answers `none` with the reason and the window stays opaque (the rule is `apply_effect` in `noren-core`, the native calls are `window-vibrancy` in `apps/desktop/src-tauri/src/window_effect.rs`). `appearance.window.opacity` reaches the page as `--nr-opacity`. A background picture comes from the theme, the settings or the space; `Backend.readBackgroundImage(path)` reads a local picture file (the path, the size and the first bytes are checked in `noren-core`, nothing is fetched) and the page shows the bytes from memory. See [THEMING.md](THEMING.md#the-window-effect-opacity-and-background).
- **Terminal options.** `terminal` in `config.jsonc` (font, cursor, scrollback, bell; see [CONFIG.md](CONFIG.md#the-terminal)) is read through `terminalOptionsOf` in `packages/model`, so the defaults are the values `TerminalView` used to hard-code. A terminal that is running takes a changed file, and the zoom of the font (Ctrl+= / Ctrl+- / Ctrl+0, kept in memory and never written), by changing the options of its xterm: its session is not touched. The font names are untrusted text and only names get through (`parseFontFamilies`). `Backend.listMonospaceFonts` comes from `noren-core` (`fonts.rs`, `fontdb`); the Tauri command is `fonts_list_monospace`.
- **The controls and the preview of the settings screen (NOR-F20-10b).** `SettingsFields.tsx` has the controls (`Toggle` is a native check box with `role="switch"`, `NumberBox` takes a `slider`, `PathBox` adds a **Choose...** button, `Choice` draws a row of radio buttons or, as a `SelectBox`, a list) and `settings-controls.ts` is the pure part: `NUMBER_RANGES` (the range and step of each slider, held to `ConfigSchema` by a test) and `CHOICE_CONTROLS` (which control each choice has). `Backend.pickPath({ kind, title })` opens the chooser of the system for a file or a folder and answers a path or `null`; it is the Tauri command `path_pick` (`bridge.rs`), granted to the main window only, and the plugin's own dialog commands stay granted to no window. The `FakeBackend` answers what `setPathPick` queued (`window.__norenTest.setPathPick`). What a draft shows in the window before the file has it goes through `appearance-preview.ts`: `previewOf` (`settings-screen.ts`, with `previewLayout`, `previewPicture` and `previewTerminal` of `settings-sections.ts`) says what the draft tries out, `windowAppearance` lays the opacity, the blur and the picture over the file, `layout-store.ts` the layout and `terminal-options-store.ts` the font and the cursor; closing the screen clears the preview (the file has it by then, see the next item).
- **No Save, every change written at once (NOR-F20-10c).** The draft of the settings screen is only what the file does not have yet: a text on its way, or a value with a reason under its box. `SettingsWriter` (`settings-apply.ts`, pure: it takes the `ConfigManager` and a function that says what a plan needs, so Vitest gives it a fake file; `useSettingsWriter` is the React glue) owns that draft. `edit(update, wait)` changes it and sets one timer: `wait` is 0 for a choice and `TYPING_WAIT_MS` (500) for a box or a slider, and every edit starts the wait again. When the timer fires, `flush` (or `settle` when the screen closes) plans from the file as it is then, with `planSave` (`settings-screen.ts`), and hands only `changes` to `ConfigManager.update`, which edits just those settings in the text of the file (comments and order stay) and saves it; the writes queue, each planned from the file the one before it wrote. A value the schema refuses is in `problems` and stays in the draft (the box draws the reason); every other setting is still written. After a write `settledDraft` takes out of the draft whatever the file has now, part by part (`0.80` is the `0.8` of the file), so the boxes show the file again and a change another program makes to it shows through; a write that fails keeps the draft and says why (`failure`). Leaving a box calls `soon()`, Enter in a box `flush()`, and the X, Esc and a click on the backdrop `settle()` before `onClose`; `settle` also writes a new profile row that was held. Three rules sit in `PlanContext`: `heldProfileRows` (a new profile row the keyboard is still in is reported but not added, because its id comes from its name; `planProfiles` returns the `ids` the rows get and `withSavedIds` turns the rows into the profiles of the file), `picture` (the path of the background picture is written once `useBackgroundThumbnail` says it could be read, and `pictureWaits` keeps it in the draft meanwhile) and `takenProfileIds`. A file with a problem of its own is not edited (`writer` returns `false`, the screen shows `settings-file-problem`), and closing then stays once. A list of profile rows that lacks a profile of the file takes it out of the file, so before every plan the writer gives a row to each profile that came into the file by another program (or by a pull) while the screen was open, and only a profile the person removed (`markProfileRemoved`, called after the question) may be taken out. `NumberBox` and `TextArea` keep the text typed in them until the box is left (`useTyped`), so a text the file writes differently never changes under the fingers. The tests: `settings-apply.test.ts`, the `settledDraft` and held-profile cases in `settings-screen.test.ts` and `settings-profiles.test.ts`, `e2e/settings-apply.spec.ts` and the adapted `e2e/settings*.spec.ts`.

- **Profiles and project actions in the Favorites bar (NOR-F20-11b).** The bar holds three kinds of tile: the favorite tabs (the first letter of the title), shell profiles (a terminal mark) and project actions (a play mark). The profiles and actions are `Workspace.favoriteLinks`, a list of `FavoriteLink` (`packages/model/src/types.ts`) that sits **next to** `favorites` in `state.json` instead of inside it, and the file is **still version 2**: the field is optional, a file without it reads as it is (no migration, `migratedFrom` stays unset) and nothing is written until the bar holds a profile or an action, the same way `windows` joined the state. A version 3 with `favorites` as a list of tagged entries was weighed and left out: the Rust side reads the saved state to start the first shell before the page asks for it (`prespawn.rs`, `STATE_VERSION = 2`, which refuses any other version and then starts nothing ahead), so a bump would have switched that off for everybody without a test noticing, and it would have touched every fixture of the model for no gain the bar needs. The price is the order: the tabs come first, then the profiles and actions in the order they were added, and a profile added before a tab still shows after it. The shape check refuses a link of an unknown kind or without its parts, and `checkInvariants` refuses a link listed twice (`favorite-link-duplicate`) or one with no name, no id or an action of a space the file lacks (`favorite-link-invalid`); `reducer.property.test.ts` plays both actions in its random sequences and holds the list to the same rules (a link goes to the end once, a removal keeps the order of the others, nothing else changes the list but a space that leaves). `resolveBar` (`apps/desktop/src/favorites.ts`) draws the tiles from the workspace, the profiles of the computer (`useProfiles`) and the latest reading of the actions file of each space that has an action in the bar. **What a tile does:** a tab is shown (as before); a profile opens a new tab with it in the active space (`newTab({ profileId })`, the call of its palette row); an action runs through `useProjectActions.runIn`, so the first run of each command in a space asks (`action-consent.ts`, the same remembered answer as its Start button), a command the file changed asks again, and a running action shows its tab instead of typing again (its tile says "Show _name_" and is `data-nr-state="running"`). A tile of an action of another space runs there: the space comes on screen and the named tab opens in it. **What a tile does when its target is gone:** a profile the computer no longer has, and an action the file of its space no longer declares (or a file that is missing, not valid or unreadable, or a space with no folder), stays in the bar as `data-nr-state="unavailable"` (dimmed, `aria-disabled`, described by its reason, which is also its tooltip), and a click says the reason in the notice line and does nothing: no tab, no confirmation, no shell, and above all no other action, because the only way from the tile to a command is the id (`resolveFavoriteAction` finds the action by id in the file and nowhere else). The tile comes back to life when the file has the action again, and it can be taken out like any other. The file of every space that has an action in the bar is watched with the same poll as the header of the active space (`use-favorite-actions.ts`, one watcher per folder, gone with the last action of its space); a click before the first reading reads the file at once (`actionToRun`, `readActionsFileState`). **Where they are put in the bar:** the right click of an action row of the header (`ActionsHeader`, `onMenu`; Shift+F10 or the menu key on its Start button does the same, since the event reaches the row) and the right click of a profile row of the palette (`CommandPalette`, `entryMenu`): the menu opens inside the palette, which stays open, and the keyboard goes back to the search box when it closes; the menu key and Shift+F10 act on the highlighted row (the browser raises `contextmenu` on the search box with a pointer button that is not 2, which is how the palette tells it from a mouse click on the box). ## CLI agents

A tab shows a generic agent icon when a CLI agent (a program that works for you in a terminal) runs in one of its panes. The icon is the same for every agent, its tooltip and its description for assistive technology are `Agent <name>`, and the name is the `id` of the catalog entry, which is the name of the executable: no logo and no product name is shipped in the interface. There are two sources, and the command wins when both know (`resolveAgent`).

**The catalog.** `agents.catalog` in `config.jsonc` (`AgentCatalogSchema` in `packages/model/src/agents.ts`) is a list of `{ id, executables, packages? }`. `id` is lower case letters, digits, `-` and `_`; `executables` are file names without folder or `.exe`/`.cmd` (case does not matter); `packages` are names that identify the agent when it is started through a runner (`node`, `npx`, `bunx`, `python`, `uv`, `pipx`...). A catalog with an id used twice, an executable claimed by two agents, a path or a space in an executable, or more than 64 agents is an error of the file, shown with its line. A catalog in the file replaces the built-in one (`DEFAULT_AGENT_CATALOG`: claude, codex, gemini, opencode, aider and a few more, each named by its executable); the built-in entries name no package except `aider`. `agents.enabled` (on by default) turns the whole detection off, and `agents.scanSeconds` (3 by default, at least 1) is the interval of the look at the process tree. `agentSettingsOf` puts the defaults over the section.

**By the command.** `detectAgentByCommand(commandLine, catalog)` reads the command the shell reported through OSC 633;E, which the reducer keeps on the pane as `runningCommand.text` while it runs. The program is the first word after `NAME=value` variables and the words that only run another command (`sudo`, `env`, `time`...); a folder and `.exe`/`.cmd` do not matter, arguments are ignored, and only whole names match (`claudette` is not `claude`). In a line of several commands (`cd app && claude`) the first one that is an agent counts. A runner (`npx`, `node`, `python`...) counts only when an argument is a package of an entry (`npx pkg`, `python -m pkg`, `node .../node_modules/pkg/cli.js`; whole path segments or `name@version`). When the command ends the pane is back to what the process tree says.

**By the process tree.** `noren-core::agents` (`agents.rs`) has the rule as a pure function: `find_agent(processes, root_pid, catalog)` takes a picture of the process tree (`ProcessInfo`: pid, parent, name, command line) and the pid of the shell of a session, and answers the agent among the descendants of that shell (not the shell itself): the nearest one, then the lowest pid; `None` when the shell is not in the picture (it ended), has no descendants or none is in the catalog. The same matching rules apply to the name of a process (`program_name`, `mentions_package`), and a loop in the parents (a reused pid) cannot make it run forever. The picture comes from the `ProcessSource` trait: `SystemProcesses` reads the real one with `sysinfo` (it keeps its `System` between looks, so the next look only refreshes, and asks for the command line once per process), and the tests feed trees they made up. `scan_sessions` takes one picture for all the sessions. `SessionManager::process_id` is the pid of the shell of a live session. `check_catalog` bounds the catalog again on this side (the page's word is not taken). The Tauri command `agents_scan(sessionIds, catalog)` (`bridge.rs`) runs the look on a blocking thread, off the thread of the interface, and answers `[{ sessionId, agentId }]` for the sessions that have an agent; it only reads the list of processes.

**In the interface.** `AgentScanner` (`apps/desktop/src/agent-scanner.ts`) asks `Backend.scanAgents` for the panes with a live session once at the start and then every `scanSeconds`, on an injected `Clock`, with one look in flight at a time and the settings read at every look (agents off, or an empty catalog, asks nothing and clears the answer). `agent-store.ts` keeps the answer per pane and `agentOfPane(pane)` combines it with the running command and the catalog in force; the sidebar and the tab bar read it through `useAgentOfPane`, `summarizeItem` puts the agent of the focused pane (else the first pane that has one) in `ItemSummary.agent`, and `TabBadges` draws the icon (`Bot` of `lucide-react`, `data-nr-indicator="agent"`). Nothing about an agent is saved. `FakeBackend.setSessionAgent` plays the process tree in tests and in web mode, and `window.__norenTest.setPaneAgent` puts an agent under the shell of a pane and looks at the tree at once; `e2e/agents.spec.ts` covers the command, the tree, the command winning, the switch and the words of the tab in both languages.

**Resuming after a restart.** When the machine restarts, the shells of the panes are gone (a new `norend` has none of the old sessions), so every pane gets a new shell in the folder saved with it. Only if the user turned `agents.resumeOnRestore` on (off by default) is the pane that had an agent running also handed that agent's resume command. The command is data of the user: the optional `resume` of a catalog entry, a full command line such as `claude --continue` (one line, at most 200 characters, no control characters; only `claude` has one in `DEFAULT_AGENT_CATALOG`). The evidence is the `runningCommand` the pane saved in `state.json`, which `restoreWorkspace` hands back as `savedCommands` before it drops it from the new pane. `planAgentResume` (`packages/model/src/agent-resume.ts`, pure) decides which panes get which command: never with agents or the option off, for an agent whose entry has no `resume`, for a pane with no agent, or for a pane in `reattachedPaneIds` (it kept its old shell from the daemon, so the agent is still running). `resume-restore.ts` arms the plan at boot and `resume-service.ts` types the command with an Enter into the session of the pane, once, at its first prompt (OSC 133 A), or, for a shell without the integration, once its first output has been quiet for a second; a pane the person types in first is left alone. Nothing here comes from an AI: the text is the one the user wrote in their own settings, behind a switch the user turned on. An agent found only by the process tree (never by a command line) leaves no trace in `state.json` and is not resumed. Tests: `agent-resume.test.ts`, `restore.test.ts`, `resume-service.test.ts`, `resume-restore.test.ts` and `e2e/resume.spec.ts`.

**The state of the agent.** An agent in a pane is in one of three states: working, waiting for you, or idle. `packages/model/src/agent-state.ts` classifies it with pure functions (`advanceAgentState(memory, signal, now, rules)` and `settleAgentState(memory, now, rules)`, no DOM, no Tauri, no dictionary of the interface) and `AgentStateTracker` wraps them with a `Clock` and one timer for the silence. The signals are plain text of the output (`TerminalTextStripper` in `terminal-text.ts` turns the bytes of a session into text: colors, cursor moves, titles and notifications are dropped, a sequence or a UTF-8 character cut between two chunks is followed), a notification the program raised (OSC 9 and OSC 777 reach the tracker through `PaneLocationTracker.onAttention`, which already parses them), and a key the person pressed (`TerminalView.onInput`, from xterm `onKey`, so a reply the terminal itself sends to a query is not a key). The rules, in order, for a piece of output: a `waiting` pattern means waiting; else a `working` pattern means working; else an `idle` pattern means idle; else any visible text means working, except that a waiting agent stays waiting (a redraw of the question is not an answer) and an idle one that was typed to less than 150 ms ago is not moved (it is echoing the keys). A notification means waiting; a key while waiting means working (the answer went in); silence of `silenceSeconds` while working means idle. Waiting never decays with silence, since it waits for the person. The end of a line of output is kept for the next chunk, so a question cut in two is read whole, and a match uses up what it matched. A chunk is tried on its last 8000 characters only, so a flood of output costs the same as a page.

The patterns are data of the user. An entry of `agents.catalog` may have `patterns: { working?, waiting?, idle? }` (lists of regular expressions, at most 16 of at most 200 characters each, compiled case-insensitive with `^` and `$` at each line; `AgentPatternsSchema` refuses one that is not a regular expression, with its place and line) and `silenceSeconds` (1 to 3600); `agents.silenceSeconds` (8 by default) is the silence for an entry without its own. An entry with no `waiting` list gets `DEFAULT_WAITING_PATTERNS` (yes/no questions, "press enter to continue"); an empty list means none. The built-in entries for claude, codex and aider carry patterns written from the words those programs print (a status line with its interrupt hint, a permission question, the input prompt); they are a starting point that a different version of the program may break, and a catalog in the file replaces them. `compileAgentRules(entry, defaultSilenceMs)` compiles an entry. The regular expressions run in the page on what a program printed, so a pattern with catastrophic backtracking is the user's to avoid; the length limit and the 8000-character window bound the damage.

In the interface, `agent-state-store.ts` keeps one tracker per pane that has an agent. `PaneTerminal` (`App.tsx`) feeds it from `onOutput` (after the bytes went to xterm; a pane without an agent costs one lookup per chunk), from `onAttention` (a notification) and from `onInput`; the end of a command, or the process tree no longer showing an agent found only by it, drops the state. The silence runs on the clock of the fake shell in web mode (a test moves it with `advanceClock`) and on real time in the app (`setAgentStateClock`, set in `boot.ts`). `summarizeItem` puts the most pressing state among the agent panes of a tab (waiting, then working, then idle) in `ItemSummary.agentState`; `TabBadges` draws a dot next to the agent icon (`data-nr-indicator="agent-state"`, `data-nr-agent-state`) and `SplitLayout` draws a ring on the pane (`pane-agent-ring`, `data-nr-agent-state` on the pane frame): working is the accent color and pulses (not with reduced motion), waiting for you is the text color, solid, with a halo, idle is muted and hollow, so the state is not told by color alone. The words are `Agent <name> is working`, `... is waiting for you` and `... is idle` (and the Portuguese ones), in the tooltip of the dot, in the description of the tab (`indicatorLabels`) and in a visually hidden `role="status"` next to the pane. `e2e/agent-state.spec.ts` covers the three states, the silence (global and per entry), OSC 9 and 777, the typed answer, the words in both languages, a split and the switch; the unit tests classify fixtures of the output of three agents (`agent-fixtures.ts`) in the three states.

**The Agents panel.** One list of the agents of all the spaces: `Ctrl+Alt+Shift+G` ("Open agents panel", `agents.open`, also in the palette) opens `AgentsPanel` (`AgentsPanel.tsx`, a dialog like the library). Each row has the name of the executable (no logo, no product name), the state in words and in the dot of the tab, how long the agent has been in that state, the tab and space it runs in, and the last line of its output. `buildAgentList` (`packages/model/src/agent-list.ts`) is the pure part: it takes the workspace, a function that answers the agent of a pane (`AgentInfo`: id, state, `since`, last line), the name of a tab and `now`, and orders the rows waiting for you, then working, then idle; inside a state the one that has been there longest comes first, and a tie keeps the order of the sidebar. The time is `now - since` on the clock of the agent states (the one of the fake shell in web mode, real time in the app), written by `formatElapsed` (`45s`, `3m 05s`, `2h 07m`). The last line is kept by `AgentStateTracker.lastLine` from the same plain text the classifier reads (`advanceLastLine` in `terminal-text.ts`: the last line with something on it, the one still being written included, so a prompt shows; at most 400 characters kept) and `truncateLine` cuts it to 120 characters with `…` for the screen. `agent-state-store.ts` feeds the panel (`agentInfoOfPane`, `agentRows`, `useAgentRows`): it renders again when a state changes, when an agent prints a new last line (a counter apart from the one of the states, so only the panel pays for it) and once a second while it is open, on the clock of the agent states. An agent that printed nothing yet starts its idle time the first time it is asked about. A click or Enter on a row shows its space and tab, focuses the pane and gives it the keyboard; Up and Down move between the rows and Escape closes. A pane with an agent shows nothing different when the panel is closed, and with `agents.enabled` off the list is empty. `Ctrl+Alt+Shift+W` ("Go to the agent waiting for you", `agents.focus-waiting`, also in the palette) goes to the first waiting row (`firstWaitingAgent`: the agent that has waited longest, in any space); with none waiting it moves nothing and shows the notice "No agent is waiting for you." `e2e/agents-panel.spec.ts` plays three agents in three spaces in the three states and checks the list, the order, the time, the last line, the click, the keyboard, the shortcut and the palette in both languages.

What is not there: a runner is matched only through the packages of the catalog, so an agent installed as a script of `node` needs its package in the entry. The patterns of the built-in agents were not checked against a real run of those programs.

## Git worktrees

"New worktree" and "Remove worktree" are two actions of the registry (`worktree.new`, `worktree.remove`, no chord, in the palette). They work on the repository of the folder of the focused pane of the tab on screen (the start folder of the space when the pane has none; with no folder at all a notice says there is no repository to use).

**The core.** `noren-core::worktree` (`worktree.rs`) runs the `git` of the system through `std::process::Command` with separate arguments, never through a shell, so a branch name is one argument whatever it holds; stdin is closed, `GIT_TERMINAL_PROMPT=0` and no window opens on Windows. `GitCli` is that `git` (`GitCli::system()`; a test points it at another program or gives it a scratch `HOME`). `list` is `git worktree list --porcelain`, parsed by the pure `parse_worktree_list` into `Worktree { path, head, branch, detached, bare, locked, prunable }` (the main worktree first). `create(folder, branch)` checks the name first (`validate_branch_name`: not blank, no leading `-`, no control character; then `git check-ref-format --branch`, whose printed answer must be the name itself, so `@{-1}` is refused), puts the worktree in `<parent of the main worktree>/<repository>-<branch with / as ->` (`worktree_destination`; the characters Windows does not allow in a file name become `-` too) and refuses when that folder exists. The branch is made with `-b` from the `HEAD` of the folder when `refs/heads/<branch>` does not exist, and used as it is when it does; git refuses a branch that is checked out in another worktree and its message is the error. `remove(folder, path)` accepts only a path git lists as a linked worktree (the main one is refused), runs `git worktree remove <path>` from the main worktree and never passes `--force`: a worktree with changes, untracked files or a lock is refused with the message of git. The branch is never deleted. A missing `git` ("Install git and make sure it is on the PATH"), a folder that does not exist and a folder in no repository are errors with a sentence a person can read.

**The bridge.** `worktree_list(cwd)`, `worktree_create(cwd, branch)` and `worktree_remove(cwd, path)` (`bridge.rs`, async, on `spawn_blocking` like the others, each with its permission in the capability of the main window) answer `Worktree` (`path`, `branch`, `head`, `detached`, `main`, `locked`, the path in the form of the system) or reject with that sentence. `Backend.listWorktrees`, `createWorktree` and `removeWorktree` are the same three calls; the `FakeBackend` keeps the worktrees over its fake repositories (`setWorktreeDirty` makes it refuse a removal as git does), with the pure `branchProblem` and `worktreeDestination` of `packages/model/src/worktree.ts` naming the folder as the Rust side does.

**The interface.** `WorktreeDialogs.tsx`. "New worktree" is a dialog with the branch field; it reads the repository when it opens (outside one it says so and cannot create), shows the folder the worktree would get as the branch is typed, and on Create asks the backend; a refusal stays in the dialog as an alert with the reason. On success the dialog closes and a new tab of the active space opens with the worktree as its folder. "Remove worktree" lists the linked worktrees (the main one is not offered), asks "Remove this worktree?" with the folder under the question (focus on Cancel; Esc cancels) and only then removes; a refusal of git goes back to the list as an alert with its message, and nothing is offered to force it. A tab that was in the folder of a removed worktree stays open where it was.

What is not there: no way to force a removal, to delete the branch, or to list or prune worktrees whose folder is gone; the tests with the real `git` (`crates/noren-core/tests/worktree_real.rs`) run when `git` is installed and skip with a warning when it is not.

## Live groups

A group can be live (`GroupNode.live`, NOR-F17-04a): its entries are not stored, they come from a source on the machine and are asked again as it changes. `live` is saved in `state.json` with the group, and so is `Item.liveKey`, the key of the entry a tab was opened from; both are optional, so a file saved before them is read as it is (`STATE_VERSION` stays 2, no migration). Today the only source with a query is `worktrees` (the worktrees of the repository of `folder`, through `Backend.listWorktrees`); `ssh` and `docker` are in the union for the tasks that bring them. `group/create` takes an optional `live`, `group/set-live` makes a group live or ordinary again, and `item/create` takes an optional `liveKey`; a source that is not valid (a blank folder, an unknown name) makes no group and changes nothing, and `checkInvariants` refuses one in a saved file (`live-source-invalid`, `live-key-invalid`).

**The updater.** `LiveGroups` (`live-groups.ts` in `@noren/model`) gets a clock, the workspace (a function, read at every round) and the sources, and asks each live group of the workspace when it starts and then every `LIVE_REFRESH_INTERVAL_MS` (10 s). It keeps, per group, the last list of entries (`{ key, label, cwd, command? }`; blank and repeated keys are dropped) and tells its subscribers when a list or an error changes; the same answer twice keeps the very same list and tells nobody. A source that fails keeps the last list, records the message (`error(groupId)`) and calls `onError`; a group that is gone, or is no longer live, or is live on something else, is forgotten and no longer asked, and an answer that arrives after that is thrown away. A group is never asked twice at once. The app starts it at boot (`live-groups-service.ts`) on the clock the auto-archive uses.

**Entries are not tabs.** An entry that goes away closes no tab and no session. `openLiveEntry(groupId, key)` of the workspace store shows the tab of the group whose `liveKey` is `key` (also when the entry is no longer listed), or else makes one in the group (`item/create` with `placement { to: "tree", groupId }`, the folder of the entry, `liveKey`), never through the routing rules; `planOpenLiveEntry` is the pure choice. The command of the entry is handed to `onStartCommand` when the view has started the shell of the new tab, and the app types it when the shell is ready, as it does for the resume of an agent.

**In the sidebar (NOR-F17-04b).** `SidebarTree` draws the entries of a live group right under its header, before its tabs, one button each named by its label (`LiveEntryRows`, `LiveEntries.tsx`), and a quiet line (`Could not update: <reason>`) when the source failed the last time, with the entries it had still listed; a folded group shows none, and a window of a single tab (`WindowApp`) shows none because it gets no `onLiveEntryClick`. An entry is not a tab: it is not a drag source, it is not in `TreeRow` (so not in the order of the tabs, the switcher or the count of the group), and its rows are `treeitem`s of the tree keyboard (`tree-keys.ts`: kind `entry`, key `l:<group>:<key>`; Right on an unfolded group goes to its first entry, Left goes back to the group, Delete does nothing on an entry). Clicking one calls `openLiveEntry`. The list is drawn again when the updater tells something changed: `live-groups-service.ts` re-publishes the notice (`subscribeLiveGroups`, `useLiveGroupsVersion`). The app asks the sources at once, without waiting for the round of ten seconds, after it changes what a source lists: when the palette command "New group of worktrees" makes the group (`group/create` with `live: { source: "worktrees", folder }`, the folder of the focused pane, else the start folder of the space) and after a worktree is made or removed through the dialogs (`refreshLiveGroups`). Tests: `SidebarLive.test.tsx` (server-side render of the tree and of the rows, the click, the notice), `tree-keys.test.ts`, and `e2e/live-groups.spec.ts` with the `FakeBackend`.

**The SSH hosts source (NOR-F17-04c).** A live group with `{ source: "ssh" }` lists the `Host` lines of the `~/.ssh/config` of the user. `noren-core::ssh_config` (`ssh_config.rs`) has the rules as a pure function over the text (`parse_ssh_hosts`) and reads the file apart from it (`read_ssh_hosts_from(path)`; `read_ssh_hosts()` finds `~/.ssh/config` from `HOME`, else `USERPROFILE`): the keyword is read without regard to case, `Host=a` and `Host a b c` (one entry per name) work, a `#` starts a comment, a name is listed once, and a file that is not there is an empty list, not an error (a file larger than 1 MiB or one that cannot be read rejects with a sentence, and the group keeps its last list and shows the error line). A name is kept only if it is safe to type into a shell as `ssh <name>` (`is_safe_host_name`: letters, digits, `.`, `-`, `_`, not starting with `-`), which drops wildcard patterns (`*`, `?`, `!`) and anything with a space, quote or `;`. `Include` and `Match` are not followed or read: the hosts of an included file are not listed. The Tauri command `ssh_hosts_list` hands the list to `Backend.listSshHosts`; `sshSource` (`live-groups.ts`) makes an entry per host (key and label the host, `command` `ssh <host>`, blank `cwd` so the shell opens in the folder of the space) and checks the name again before it becomes a command; the app types the command into the new shell like it does for any entry. `FakeBackend.listSshHosts` answers a fixture (`FAKE_SSH_HOSTS`) or what `setSshHosts` says and never reads the config of the machine. The palette command "New group of SSH hosts" makes the group.

**The containers source (NOR-F17-04d).** A live group with `{ source: "docker" }` lists the running containers. `noren-core::docker` (`docker.rs`) has the rules as a pure function over what `docker ps --format {{.Names}}` prints (`parse_container_names`: one name per line, empty lines and repeated names left out) and runs the program apart from it (`DockerCli`, `list_running_containers()` with the `docker` of the `PATH`; `with_program` swaps it so a test points it at a name that does not exist or at the test binary itself, never at the real `docker`). The run follows `run_capped` of `hardware.rs`: no input, no console window on Windows (`CREATE_NO_WINDOW`), at most 1 MiB of output read (cut at the last whole line), a deadline of 5 s after which the program is killed. Three problems are told apart in `DockerError` and in the sentence the group shows: `docker not found` (the program is not there), `docker ps failed: <first line of the error output, at most 200 characters>` and `docker ps took too long`. A name is kept only if it is safe to type into a shell as `docker exec -it <name> sh` (`is_safe_container_name`: `[A-Za-z0-9][A-Za-z0-9_.-]*`, at most 255). The Tauri command `docker_containers_list` hands the list to `Backend.listDockerContainers`; `dockerSource` (`live-groups.ts`) makes an entry per container (key and label the name, blank `cwd`, `command` `docker exec -it <name> sh`) and checks the name again before it becomes a command. With Docker missing the source rejects, so the group stays empty (or keeps its last list) and shows the error line. `FakeBackend.listDockerContainers` answers a fixture (`FAKE_DOCKER_CONTAINERS`) or what `setDockerContainers(list, error?)` says (the e2e reaches it through `__norenTest.setDockerContainers`) and never runs `docker`. The palette command "New group of running containers" makes the group.

Not verified here (D19): how the entries look next to the tabs on a real window (spacing, the colors of the muted label and of the error line in each theme, the tooltip with the folder); the styles are `.live-entry` and `.live-error` in `styles.css`, built on the pane rows of a split tab, and axe finds no serious violation on the page with a live group.

## Windows

The app can have more than one window. A **window** shows one **space**, and no other window shows that space (the main window shows `activeSpaceId`): a terminal is drawn by one page, so the tabs of a space belong to the window that shows it. The spaces are shared in the sense that they all live in the one workspace and a tab can go from one to another; moving a tab to a window is moving it into the space the window shows. The model keeps this as `Workspace.windows` (`AppWindow`, `packages/model/src/windows.ts`), saved in `state.json` like the rest. The groundwork is NOR-F15-04a. Dragging a tab out of the window to make one, and the page of a window drawing the tabs and the splits of terminals of its space, are NOR-F15-04b; the sidebar in a window (a new tab, closing a tab, putting the tabs in order), what the terminal of a tab brought to a window shows, and the unread marks of a window are NOR-F15-04c; the browser, preview and diff panes outside the main window are NOR-F15-04d.

**In the model.** `window/open { spaceId }` adds a window with a fresh id; it changes nothing when the space does not exist, when the main window or another window shows it already, or past 8 windows. `window/close { windowId }` takes it away and the space keeps its tabs. `window/move-item { itemId, windowId, placement? }` moves the tab into the space of the window, with its panes and sessions as they are, and makes it the tab that space shows. The main window cannot take the space of a window with `space/activate`, and the clean-up that runs after every action (`settleWindows`) drops a window whose space was deleted or ended up in the main window, so the invariants (`window-id-invalid`, `window-space-missing`, `window-space-shared`, `window-overflow`, and `duplicate-id` for an id the workspace uses) always hold. Deleting the space of the main window picks a space no window shows when there is one. A pane in the tab a window shows counts as on screen for the unread marks, and so is read there: the clean-up that runs after every action (`clearViewed`) clears the marks of the tab each window shows, as it does for the tab of the main window, so a marked tab that moves into a window and becomes the one it shows, or that the window shows later, loses its marks (finding 241); that tab is never put in the archive for being idle (`windowShownItems`). A tab dragged out is one action, `window/open-with-item { itemId, name? }`: it makes a space of its own (named `name`, "Window" when left out, with the icon, color and start folder of the space the tab came from), a window that shows it (`AppWindow.returnSpaceId` remembers the space the tab came from) and moves the tab in, as the tab that window shows, so no state in between (a window on an empty space, a tab in a space nobody shows) is ever seen; a pinned tab stays pinned. `window/return { windowId }` closes a window that has `returnSpaceId` and gives its tabs back, each at the end of the space they came from (pinned ones pinned), or of the space the main window shows when that one is gone or another window shows it, and the space made for the window goes away; the main window then shows the tab the window showed. A window without `returnSpaceId` (one on a space that was always the user's) is closed as by `window/close`. A tab goes to a window only if the page of a window can draw every pane of it (`windowCanShowTab`, checked by both `window/open-with-item` and `window/move-item`); every kind of pane there is can be drawn, the browser pane since NOR-F15-04e (its web view is then a child of the window, see below). `mainWindowSpaces` lists the spaces the main window can show, which its space switcher, its drops and `Ctrl+Alt+<n>` use, so the space of a window is not one it can pick. `state.json` keeps `windows` when there are some and leaves the key out when there are none, so a file saved before windows existed reads as it is; `restore` keeps the windows, starts the shells of every pane of every space as it always did, and opens no native window (the interface does, from the state: `bringUpWindows`, below).

**One owner of the state.** The main window loads the workspace and is the only page that writes `state.json`: the `StateWriter` and the store exist there and nowhere else. The page of every other window (`WindowApp.tsx`) is chosen by `main.tsx` from its label before `App` is imported, so it never reads the saved state or the settings and holds nothing but the sessions it was given. Three walls keep it so: that choice; the capability of the windows (`capabilities/window.json`, pattern `window-*`), which grants `session_attach`, `session_write`, `session_resize` and the three event permissions and nothing of the state, the settings, the files, starting or ending a shell, or making a window (a test in `capabilities.rs` holds the file to that list); and `windows::require_owner`, which the state commands (`state_load`, `state_save`, `state_quarantine`) and the window commands call first and which refuses any label but `main`, in case a capability is ever widened by mistake. A window cannot be pointed at a web page: `navigation.rs` names the `window-<id>` labels and lets them go to the pages of the app only, and the web view of a browser pane (`browser-<pane id>`) can never have such a label.

**The Backend contract.** `openWindow(windowId, spaceId)` makes the native window, `closeWindow(windowId)` closes it (the shells it showed go on, with nowhere to send their output), `moveTabToWindow(windowId, sessionIds)` moves the output of the sessions of a tab to it and resolves when the window has taken them all, and `onWindowClosed` reports a window the person closed. `TauriBackend` calls `window_open`, `window_close` and `window_move_tab`, and listens to `window-closed`; `FakeBackend` keeps the windows and where each session went in memory (`windows()`, `windowOfSession`, `closeWindowByPerson`), checking what the real one checks. The workspace side is `window-service.ts` in the main window: `openWindowOnSpace` (the workspace first, so the model decides, then the native window; a refusal takes the window out again), `moveItemToWindow` (the window takes the sessions first, then the tab moves, so a refusal leaves it where it was), `closeAppWindow`, and the ones of 04b below. The rest of this section is what the interface does with them.

**Dragging a tab out.** `TreeDnd` (`TreeDnd.tsx`) knows where a mouse drag ended: the point where the button was pressed plus how far the pointer travelled (`activatorEvent` and `delta` of dnd-kit). The browser goes on reporting the pointer to the page for as long as the button is held, wherever it goes, so a tab let go more than 8 px beyond a side of the page (`leavesWindow`) has left the window; the drag says so while it is under way ("Move to a new window.", read aloud too) and `onDragOut` takes the tab out. Only a tab is taken out (a group stays, and pinned tabs do not drag), and a keyboard drag never leaves the page. The palette has the same thing as the action `window.move-tab` ("Move tab to new window", no chord), for the tab on screen. Both end in `moveItemToNewWindow` (`window-service.ts`): the workspace first (`window/open-with-item`, so the model decides), then the native window (`openWindow`), then the sessions of the tab are handed to it (`moveTabToWindow`). A backend that refuses, or a window that does not answer, gives the tab back (`returnWindowTabs`: the sessions are attached to the main page again, the workspace takes the tab back, the native window is closed if it is there), so the two never disagree. A tab with a pane the window cannot draw, too many windows, a page that cannot show another window (a plain browser) and a refusal say so in a notice and leave the tab where it is. A space another window shows is not drawn by the main window (`App.tsx` leaves its layer out): a terminal mounted in two pages would take the output of its session back, since the output goes to the page that attached it last.

**Closing a window gives the tabs back.** A window the person closes is reported with `window-closed`; for a window made for a tab, `followWindowClosed` runs `returnWindowTabs`, which attaches the sessions of the window's tabs to the main page again first (this is what keeps them from being left with no page, finding 238: the route of a session sends to the page that attached it last, and that page is gone) and only then dispatches `window/return`, so the terminals the main window draws for the returned tabs find their output. A window on a space of the user keeps the space and the sessions have no page until a window shows the space again, as in 04a. When the app starts with windows in `state.json` (it was closed, or the page reloaded, with windows open), `bringUpWindows` opens the native window of each, hands it the sessions of its tabs (the restore started them with the rest, in the main page) and gives the tabs back if a window cannot be brought up; a page that cannot show windows at all (a plain browser opening a state saved by the app) returns every window's tabs at once (`releaseWindows`), so none is left in a space nobody shows. `startWindows` (called by `bootWorkspace`) starts these, the listening below and the following of closed windows.

**What the page of a window draws.** `WindowApp.tsx` draws the space its window shows: a title line, the sidebar of the space (the main window's own `SidebarTree` inside a `TreeDnd`, narrower: the pinned tabs first, then the tree, the tab on screen `aria-current`, the unread and bell marks, a menu with Close and the button New tab) and, for each tab, its layout with `SplitLayout`, the component of the main window, as nested resizable panels with a `TerminalView` in each leaf (the tabs that are not on screen stay mounted, hidden, so their terminals keep their screens). The page holds no workspace: the main window sends it the space as an event, `window-state` (`{ windowId, space }`, `followWindowPages` in `window-sync.ts`), when the page says it is ready (`window-ready`, said again once a second until the space arrives, since the main window may not have been listening yet) and each time that space changes (an unchanged space is not sent again). The page reads it like a saved state: the shape and the invariants of the model (`parseState`), so an event with anything else in it is ignored. A terminal is drawn for a pane only once the page took over the output of its session (`window-take-sessions`, as in 04a), because the stream exists after `attachSession`; until then the pane says it waits, and a pane with no session says it has no shell. The changes the page can make go back as `window-action` (`{ windowId, action }`): show another tab (`space/set-active-item`), focus a pane (`pane/focus`), resize a split (`pane/resize`), open a tab (`item/create`), close one (`item/close`) and put the tabs in order (`item/move`, which the drop of the sidebar tree makes). The main window checks each one (`actionOfWindowRequest`: a window of the workspace, a tab of the space that window shows, a new tab only in that space and only while it holds fewer than `MAX_WINDOW_TABS` (64), a place that is the pinned list or the tree, a group of that tree and a whole number, the fields of those actions and nothing else, made again from what was checked, so a request never names another space) and `runWindowAction` (`window-service.ts`) carries it out, so the state stays in one place, and writes it to `state.json` like any change. A new tab is made by the main window: `item/create` in the space of the window, then the shell of its pane is started there (`openTabInWindow`: the profile, folder and environment the space gives, the id of the pane, 80 x 24 until the terminal of the window fits it, because only the main window may start a shell: `session_create` is not in the capability of the windows), the pane is told its session, and the page takes the output of that shell over like for any tab moved there (`moveTabToWindow`); a shell that cannot start, or a window that does not answer, closes the tab again, which ends the shell. Closing a tab ends its shells (the store does for every pane an action drops) and, when it was the last tab, closes the window (`returnWindowTabs`: a window made for a tab goes away with the space made for it; one on a space of the user is closed and keeps the space). Moving a tab changes the order in the space of the window and starts or ends nothing. The panes of the page have no header, no drop zones and no menu; closing one pane of a split, zooming it, renaming a tab, pinning it and folding or ungrouping the groups of the sidebar are not asked of the main window by a window.

**Browser panes in a window.** A tab with a browser pane goes to a window like any other: `windowCanShowTab` (`windows.ts`) now says yes to every kind of pane there is, through a record that has to name each one, so a new kind of pane does not compile until someone says whether a window can draw it. The page of the window draws the very `BrowserPane` of the main window: the address bar and the area the web view is laid over. The web view is a native child of a window and not part of the page, and the page of a window can call no command about one (`capabilities/window.json` has no `browser_*`, and `browser_open` answers only to the main window, `windows::require_owner`), so the main window opens it for the window. The page measures its area and asks (`window-browser`: `{ windowId, request, op, itemId, paneId, url?, bounds? }`, `op` one of `open`, `navigate`, `bounds`, `close`) and waits for the answer (`window-browser-result`: `{ windowId, request, ok: true }` or `{ ..., failed }`, up to 30 s). `createWindowBrowsers` (`window-browser.ts`) is the page's side: the four calls of the backend the `BrowserPaneView` of the pane makes (`openBrowserPane`, `navigateBrowserPane`, `setBrowserPaneBounds`, `closeBrowserPane`), one object per pane, each a request waited for, so the same `BrowserPaneView` runs in the main window against the shell and in a window against the main window. `followWindowBrowsers` (started with the rest by `startWindows`) is the main window's side, and `browserAskOfWindowRequest` is what it checks before it calls the backend: the window is one of the workspace's, the tab is one of the space that window shows, the pane is in that tab and is a browser pane, the operation is one of the four, the bounds pass `browserBoundsProblem`, and the address passes `browserUrlProblem` and is the one the pane holds now; the call is made again from the pane, with the address taken from it, never from the event. A request that fails any of those gets no answer at all (an address that is valid but is no longer the pane's, because the pane was taken elsewhere while the call was on its way, is refused with a reason so the page does not wait), a window has at most 16 calls going at once, and the calls of one pane run one at a time in a queue that is shared with the main window's own view of that pane (`exclusive` in `browser-view.ts`, one queue per pane and per backend), so the close of the web view a tab had in the main window always lands before the open of its web view in the window, and the other way round when the tab comes back. The call is then `openBrowserPane(paneId, url, bounds, { windowId })` on the backend, which is `browser_open` with a `windowId` that must be a window the app opened (`WindowBook`) and exists: a web view can be a child of `main` or of such a window and of nothing else. An address typed in the bar of the window is a `window-action` `pane/set-url` (the main window checks it is a browser pane of that window and an address the pane may show, and the workspace takes it); the web view then goes there because the main window sees the pane's address change, not because the page said so. The web view keeps what it always had: no capability, no IPC, only `http` and `https`, no new window, no download, no permission. It leaves with the pane: `followWindowBrowsers` watches the workspace and closes the web view of a pane that is no longer in the space its window shows (the tab came back to the main window, was closed, or the window was closed), and `windows::close_window` and `destroy_all` close the web views that are children of a window before they destroy it (and look the window up as a `Window`: Tauri stops calling a window a webview window once a web view is a child of it, so `get_webview_window` would not find it). A tab that changes window reloads the page of the pane from the address it holds, because the main window closes its web view when the pane leaves and the window opens another. In `/?window-preview` a panel gets a backend that refuses the four calls as the real window does, and `FakeBackend` keeps the window each web view is a child of (`browserViews` in the test hook) and drops a window's web views when it closes.

**Preview and diff panes in a window.** A tab with a preview or a diff pane goes to a window like any other, and the page of the window draws those panes with the very `PreviewPane` and `DiffPane` of the main window. The page cannot read a file or run git (`capabilities/window.json` has no such command, and it did not grow for this), so the panes read through the main window: the page sends `window-read` (`{ windowId, request, kind, itemId, paneId, path }` for a preview, `cwd` in place of `path` for a diff) and the main window answers `window-read-result` (`{ windowId, request, kind: "preview", preview }`, `{ ..., kind: "diff", diff }`, or `{ windowId, request, failed }` when the read itself failed). `createWindowReads` (`window-sync.ts`) is the page's side: a reader per pane (the same object each time, so a pane does not read again by itself) with the two calls of the backend, `readFilePreview` and `readGitDiff`, each a request numbered by the page and waited for up to 30 s (`WINDOW_READ_TIMEOUT_MS`), four at a time at most; an answer counts only for the window of the page, a request it is waiting on and the kind it asked, and one that is not a proper answer (`previewFromWire`, `decodeGitDiff`: the same checks as an answer of the shell) is ignored, so a read nobody answers fails when it times out and the pane says it could not read. `followWindowReads` (started with the rest by `startWindows`) is the main window's side, and `readOfWindowRequest` is what it checks before it reads anything: the window is one of the workspace's, the tab is one of the space that window shows, the pane is in that tab and is a preview pane for a preview read or a diff pane for a diff read, and the path or folder the event carries is the one the pane holds. What is read is made again from the pane, never from the event; a request that fails any of those gets no answer at all, and a window has at most eight reads going at once (`MAX_WINDOW_READS`), so a page that is not ours cannot read a file the workspace does not show in a pane of its window, nor turn the main window into a git runner. The answer goes out with the window and the request number, and the pages of the other windows keep nothing of it; the event bus is the one of finding 246, so a page that listens to every event can still hear it (finding 251). A picture is bytes and an event carries JSON, so its bytes travel as base64 (`previewToWire`), checked on arrival by their first bytes and the limit of a picture; a 10 MiB picture is about 13 MiB of text through the event, which has not been tried in the real engine (finding 252). The diff pane reads while it is on screen in the window, and again when it comes back to the screen and when its refresh button is pressed, as in the main window; the preview reads when the pane first is drawn.

**The window as a panel in a browser.** A browser opened with `/?window-preview` draws each window as a panel next to the app (`WindowPreview.tsx`), with the very `WindowApp` on the same in-memory backend and the same in-memory events, as `?quick-preview` does for the quick terminal; a panel has a frame with a close button, which is the person closing the window (`closeWindowByPerson`). `WindowPreviewHost` (`window-preview-host.ts`) plays the Rust side that `windows.rs` plays in the app, registered on the `FakeBackend` with `setWindowHost`: it hears of each window opened and closed, waits for the page to say it is ready, asks it to take the sessions over (`window-take-sessions`) and waits for the answer of the same request, failing the move when the page refuses or does not answer in 10 s. `window.__norenWindows` gives the tests the open windows and the lines of their terminals. A browser without the flag has no other windows: `windowsAvailable()` is false, a drag out does nothing and the palette says the other windows need the desktop app. The tests of the web cannot say what the native window does (its capability, its order of steps, the real events), which is what `noren --smoke-window` is for.

**Moving a tab moves the output, not the process**, as promoting the quick terminal does (see [The quick terminal](#the-quick-terminal)): the shells are the same processes under the same ids, and `OutputRoute` puts another channel behind a session. A channel belongs to the page that made it, so the page of the window has to ask for it. `windows::move_sessions` (the function behind `window_move_tab`) checks that the window is open and every session is a live one, waits for the page to say it listens (`window-ready`), emits `window-take-sessions` (`{ windowId, request, ids }`) and waits for `window-sessions-taken` (`{ windowId, request, ok, ids, reason? }`; 15 s for each wait; an answer counts only for its own window and request). The page (`followTakes` in `window-events.ts`) calls `attachSession` for each id, one request at a time, draws a `TerminalView` for it and answers. What the shell prints meanwhile is held by the stream of the page for its first subscriber. The terminal of the window is a new one, so it would start blank: `followTakes` calls `attachSession(id, { replay: true })`, and for a session in the daemon `session_attach` has the output thread fetch what the daemon keeps of the session (up to a megabyte, `Sessions::replay` in `daemon_link.rs`) and puts it on the new channel ahead of everything the shell prints afterwards (`OutputRoute::replace_with_replay`), so the window shows what the shell had printed (finding 239). To leave nothing missing and nothing repeated the task that reads the connection detaches the session, empties the events already queued into the old channel, attaches again (the answer carries the buffer, and every event after it was sent after the buffer was taken) and only then moves the output; this needs no change of the protocol of the daemon (attaching and detaching are requests it already has). A shell that runs inside the app (no daemon) and a shell on another machine keep nothing, so their windows start blank as before. `returnWindowTabs` asks for the same when the sessions come back to the main window, whose terminals are new ones too, which also gives back what a shell printed between the closing of the window and the return (finding 238). The quick terminal promoted to a tab does not ask for it and starts empty.

**Native windows.** `windows.rs` makes the window `window-<id>` (letters, digits, `-` and `_`, at most 64, the same rule as `isWindowId`; no id can make the label `main`, `quick` or the web view of a pane), loading the page of the app, hidden and unfocused, and shows it only on a normal start (`WindowBook::new(!any_smoke)`: every smoke run keeps its windows hidden). A window the app closes (`close_window`) leaves the book first, so its destruction is not told as the person's; `lifecycle::on_window_event` reports one the person closed as `window-closed`, and destroying `main` destroys the others, like the quick window. The web view of a browser pane is a child of `main` or of one of these windows (`browser_pane::open_in`, `Parent`; see "Browser panes in a window" above). Not done: the tracker that reads the folder, the git branch and the commands from the output runs in the main page only, so the tabs of a window do not update them, get new unread marks or have their automatic titles; the scrollback of a window's tab is not saved when the app closes; the page of a window reads no settings, so it is always in English.

`noren --smoke-window` runs this in the real app with every window hidden and the files of the app in a folder of its own: a second window is made and its page comes up; from that page, sixteen commands that own or change the workspace (the state, the settings, starting or ending a shell, the windows, the four of a web view, a file) are each refused by the access control; a script that takes the page to a web page leaves it where it was; a running shell, standing for a tab of the main window, is moved to the window through `move_sessions`, and the run checks the session id, its route, the shell process (a child of `norend`), the counts of sessions and threads, that no `session-exit` came, that the old channel got nothing after the move, that a line typed afterwards reaches the channel of the page and that the page drew one terminal for it; the run then plays the main window and sends the page a space (`window-state`) with one tab and a pane holding that session: the page draws its sidebar with the tab, the title and the terminal, and a click on the tab, and one on New tab, reach the main window as a `window-action` with the right fields; the run also checks that the line the shell printed before the move reached the new channel (the replay, which only works because the shell runs in the daemon of the run); then, before the window is closed, a browser pane is opened as a child of that window (`browser_pane::open_in` with `Parent::Window`, what the main window does for the page of a window) on a page of a server of the run: the page loads, can call no command and emit no event (the access control names the window and the web view), stays on its page when it tries to go to `tauri.localhost`, its parent is `window-smoke-window-1` and that window is hidden, a move of its bounds takes effect, and the web view is gone when the app closes the window; then a window the app closes is gone with the shell untouched, and one the run closes the way the close button does is reported with `window-closed`. Then `SMOKE WINDOW OK`. What it cannot show is a window on screen, which no run opens (D19): that a visible window takes the keyboard, has a usable size and position, or paints the terminal.

## The quick terminal

A second window of the app, labelled `quick`: frameless, always on top, out of the taskbar, created hidden at the start (`src-tauri/src/quick.rs`) and placed against the top edge of the main screen, centered, 60% of its width and 45% of its height within limits (`top_bounds`, a pure function of the usable area and the scale). Three things show or hide it, described below: the global shortcut, the palette entry and the key inside the main window all call `quick::toggle_window`; Esc and the "Promote to tab" button hide it from its own page. It has a capability of its own (`capabilities/quick.json`: the commands to run one shell and to open a confirmed link, the three event permissions and `core:window:allow-hide`, nothing more; showing and placing it are done by the Rust side), and the window event handler (`lifecycle.rs`) leaves it alone: the close gate belongs to `main`, and destroying `main` destroys `quick` too, so the hidden window never keeps the app alive.

The window loads the same page as the main one, in a minimal form. `main.tsx` picks it from the label of the window (`windowKindOf`) and imports only that page, because importing `App` starts the workspace (the saved state, the settings, a shell for every tab) and a second copy of that would write over the first. `QuickApp.tsx` is one `TerminalView` with the default profile, a title line with the "Promote to tab" button, and nothing else; the window talks to the others through events (`quick.ts`, names repeated in `quick.rs`): `quick-ready` when it listens, `quick-open` (asks for a shell), `quick-session` (`{ id }`, the shell it started), `quick-promote` (`{ id }`, asks the main window to take that shell) and `quick-promoted` (`{ id, ok, itemId | reason }`, the answer).

**Promoting moves the output, not the process.** The output of a session leaves Rust through a `tauri::ipc::Channel`, which belongs to the page that made it. `create_session` therefore does not hand the channel to the threads of the session: they send through an `OutputRoute` (`route.rs`), kept in `AppState` by session id until the session ends, and the channel sits behind a mutex in it. The `session_attach` command (`attach_session`) replaces that channel; sending and replacing take the same lock, so every chunk goes to exactly one channel, the old one for what was sent before and the new one only after, and the shell, its pty and its id are never touched. In the page, `Backend.attachSession(id)` makes the new stream and asks for the move (the in-memory backends only check that the session is alive), `promoteQuickSession` (`quick-promote.ts`) calls it first and then the `adoptSession` method of the workspace store, which dispatches `item/create` with the `sessionId`: the new tab of the active space holds the existing session, and its `TerminalView` takes it over (`attach`) instead of starting one, then tells the session the size of its view. The reducer refuses a session some pane already holds, so one session is never in two tabs, and closing the tab ends the shell like any other tab. What the shell printed while the move was being made is held by the stream for the first subscriber. Not carried over yet: the lines the quick terminal had already drawn (the new terminal starts empty).

**The global shortcut.** `shortcut.rs` registers one system-wide shortcut with `tauri-plugin-global-shortcut` (2.4.1 over `global-hotkey` 0.8.0, Apache-2.0 OR MIT; only the Rust side is used, the plugin's own commands get no capability and there is no npm package). The default is `Ctrl+Backquote`, registered at start so it works before the page has loaded. The chord belongs to the interface: `quick.toggle` is an action of the shortcut registry (`keybindings.ts`), so it is listed in the shortcuts screen and in the palette, can be recorded anew, follows the preset, and the settings screen shows the chord in force and whether the system accepted it. `QuickShortcutSync` (`quick-shortcut.ts`) tells the Rust side (`quick_shortcut_set`, `Backend.setQuickShortcut`) each time the effective chord changes, one request at a time. `rebind` registers the new chord before releasing the old one, so a chord another program holds is an error with the reason (a notice in the app, the previous shortcut keeps working) and never takes the app down; a failure at start is one warning line in the log. The Rust side also refuses a chord without Ctrl or Alt, because the page could ask for any text. When the shortcut is pressed (or `quick_toggle` is called) `quick::toggle` runs against a `QuickWindow` trait, so the order of the steps is tested with a recording stand-in: a visible window is hidden; a hidden one is placed at the top of the screen, asked to open a shell (`quick-open`), shown and focused. Esc in the quick page hides the window (`core:window:allow-hide`), eating the key: the terminal of that window never sees Esc. "Promote to tab" sends `quick-promote`, waits for `quick-promoted` for its session (5 s) and hides the window only when the main window took the shell; a refusal is a notice under the title line and the window stays.

**No smoke mode registers it.** `QuickShortcut` is managed with `enabled` off in `--smoke`, `--smoke-deeplink` and `--smoke-quick`: `apply` then registers nothing, whatever the page asks (the page of the main window does ask at boot) and counts the refusals, and the setup skips the default registration. Each smoke run ends by asking the plugin itself what it holds (`shortcut::registered`) and fails if that is not zero; the line is `SMOKE global shortcut none registered`.

**The window as a panel in a browser.** A plain browser opened with `/?quick-preview` draws `QuickApp` as a panel next to the app (`QuickPreview.tsx`), on the same in-memory backend and an in-memory event bus (`memoryQuickEvents`), as the two windows share sessions and events in the real app. "Hiding" only marks the panel and counts the request. The e2e tests use it for Esc and for the promotion (same session id, same shell, a tab in the space on screen). The flag is false inside the app. What no test checks is the window actually appearing, taking the keyboard and answering the system's key: that needs a visible window.

`noren --smoke-quick` runs the whole thing in the real app with both windows hidden and the files of the app in a folder of its own: the quick window exists, hidden, frameless, always on top and at the top of the screen; its page loads and reports `quick-ready`; asked, it opens a shell (a real `session_create` from the hidden page); the shell answers; the main window promotes it; and the run checks that the session id, its route and the counts of sessions and threads are the same, that no `session-exit` came, that the output moved exactly once, and that a line typed afterwards is answered and reaches the main window's channel. Then `SMOKE QUICK OK`.

## The browser pane

A pane of type `browser` shows a web page of someone else. The model, the contract and the web view of the shell came first (NOR-F15-01a); the interface that draws the pane in a split with an address bar, opens it from a link of the output and keeps its web view in step with it is NOR-F15-01b ([In the interface](#in-the-interface-nor-f15-01b)). A `browser` pane starts no shell, however it was made or restored.

**In the model.** `Pane.type` is `"terminal" | "browser"` and `Pane.url` is the page. `createBrowserPane(id, url)` (`factories.ts`) makes one: no session, the default profile (so a terminal pane split from it starts the default shell), no folder. `browserUrlProblem` (`browser.ts`) says which addresses a pane may show: the rule of the links of the terminal (`externalLinkProblem`: only `http://` and `https://`, no blank, control character or backslash, a host, no user name before it) and no host that ends in `.localhost` or is written with `%` escapes (see the second wall below). `checkInvariants` adds three violations: `browser-url-invalid`, `browser-has-session` and `terminal-has-url`. `state.json` holds the pane as it is (`type` and `url`); `parseState` accepts both types and the invariants judge the address, so a file with a `file:` address is quarantined like any other broken file. `restoreWorkspace` starts a shell for the terminal panes only. The workspace store never gives a session to a browser pane (the shell offered is ended, as for a pane that is gone). The property test of the reducer also runs on workspaces where every third pane is a browser pane (`arbWorkspace({ browserPanes: true })`). Two actions make and move them: `pane/split` with a `url` splits a pane and the new pane is a browser pane at that address (an address `browserUrlProblem` refuses changes nothing; a split without `url` is a terminal, as before), and `pane/set-url { itemId, paneId, url }` points a browser pane at another page (an address refused, a terminal pane, an unknown pane or the page it already shows change nothing).

**The contract.** `Backend.openBrowserPane(paneId, url, bounds)`, `navigateBrowserPane(paneId, url)`, `setBrowserPaneBounds(paneId, bounds)` and `closeBrowserPane(paneId)`; `bounds` is a `BrowserBounds` (`x`, `y`, `width`, `height`, in CSS pixels from the top left corner of the page of the window). A pane id must be ASCII letters, digits, `-` and `_`, at most 64 (`isBrowserPaneId`), because it names the web view. Each call checks what the Rust side checks (`browserUrlProblem`, and `browserBoundsProblem`: finite numbers, no negative size, nothing beyond 32,768), a pane has one web view at a time, and closing a pane that has none is not an error. `FakeBackend` keeps the web views in memory (`browserPane(paneId)`, `browserPaneIds()`) and loads nothing; `TauriBackend` calls the commands `browser_open`, `browser_navigate`, `browser_set_bounds` and `browser_close`.

**In the shell.** `apps/desktop/src-tauri/src/browser_pane.rs` makes the web view a child of the `main` window (`Window::add_child`, behind the `unstable` feature of the `tauri` crate: a feature of a dependency the app already had, which adds no crate and changes no lockfile), named `browser-<pane id>`, so a pane can never name `main` or `quick`. The commands are `async` and build the view on a blocking thread, because `add_child` waits for the main thread and a command that ran on it would wait for itself. Three walls keep the page away from the app:

1. **No capability.** The capability files name the windows `main` and `quick` and no web view, and none has a `remote` origin. A web view of a pane is a child of `main`, which a capability for the window reaches by the window, so what keeps its page out is the origin: a page that is not the app's is a remote origin, and without a `remote` entry no capability grants it a command or an event. The test page's call to `fonts_list_monospace` is answered with `not allowed on window "main", webview "browser-...", URL: http://127.0.0.1:...`. `capabilities.rs` holds the files to this, and the mock-runtime tests of `browser_pane/tests.rs` call the commands from a web view of a pane at several addresses and get a refusal each time, with the page of the app asking from `main` as the control.
2. **No address of the app.** On Windows the pages of the app are served from `tauri.localhost` (and `ipc.localhost`, `asset.localhost`), and a page opened at one of them counts as the app's own and is granted its commands. `check_url` and `allows_navigation` therefore refuse every host that ends in `.localhost` (with or without a final dot, in any case, with the escapes the engine would read as dots) and everything that is not `http` or `https`: `file`, `javascript`, `data`, `blob`, `noren`, `tauri`, `ipc`, `about`. `localhost` itself and the numeric loopback addresses stay, since previewing what runs on this machine is the use. The rule holds for the address the interface asks for (`check_url`, which also applies `check_external_link` of `noren-core`) and for every navigation the page makes by itself (a link, a redirect, a script): the web view has its own navigation handler, and `navigation::guard`, the guard of every web view of the app, lets a web view called `browser-...` go to `allows_navigation` pages and every other one only to the pages of the app, as before.
3. **Nothing else it asks for.** A new window is refused, a download is cancelled, every permission request (camera, microphone, location, notifications) is denied, and the web view gets no initialization script, so it has none of the test hooks of the interface (`window.__norenTest` is page code of the app, not something the shell injects).

`noren --smoke` (`smoke_browser.rs`) proves it on the real app with the window hidden. A web server of a few lines on `127.0.0.1` and a free port (`std::net`, no crate) serves a page titled "Noren browser pane smoke". The run opens a browser pane on it with the same `browser_pane::open` the command uses and waits for the page-load event of that web view (`SMOKE browser pane loaded <url>`). The page is real code in the web view and reports back: its title, that `window.__norenTest` is not there, that a command of the app is refused and, after it tries to navigate to `http://tauri.localhost/`, that it is still the same page a moment later (`SMOKE browser pane stayed on its page`; with the refusal taken out of the code this check fails, which is how it was tried). The run then takes the pane to a second page, checks that `file`, `javascript`, `data`, `noren` and app addresses are refused, moves the pane, takes it to no area and back (the way the interface hides a pane that is out of view: the view reads back 0x0, then the size it was given, with no new load and the same address; `SMOKE browser pane hidden at no area and shown again`) and closes it, and the checks that follow still find the main window hidden (`SMOKE window hidden`). A navigation that is refused still ends with a load event for the page that stays; the run knows it and fails only on a load of another address.

### In the interface (NOR-F15-01b)

Three parts, none of which draws the page:

- **The pane** (`BrowserPane.tsx`, drawn by `renderPane` in `ItemView`). A group with an address bar (a text field named _Address_) above the area the web view is laid over (`data-nr-part="browser-view"`). Enter reads the text with `readAddress` (`browser-address.ts`: trimmed, then `browserUrlProblem`, the check the model and the shell make). A page the pane may show is dispatched as `pane/set-url`, so it reaches the model, `state.json` and, through the view below, the web view. An address it may not show leaves everything where it was and shows the reason under the bar (`role="alert"`; the field gets `aria-invalid` and `aria-describedby`), in the language in force: `addressProblemText` maps each reason of the model to a text of the dictionaries and shows an unknown one as it came. The field follows the model: when the pane goes to another page, the field shows it. The header and the pane list of the sidebar name the pane by the host of its page, and the tab keeps being named after its terminal (`speakingPane` in `pane-info.ts`: a browser pane has no folder, branch or command to give a tab).
- **Opening one from the output.** A click on an address of the output (a plain one or an OSC 8 link) asks first, as before. A click with Ctrl held (Cmd on a Mac) hands the address to `TerminalView.onOpenLink`. When it is an address a browser pane may show, `openBrowserBeside` (`App.tsx`) splits the pane the link was in (`pane/split` with the `url`, side by side, after it) and gives the keyboard back to the terminal, so the person goes on typing where they were. A tab with no room for another pane says so (`A tab holds at most 8 panes.`, or the limit of `terminal.maxPanes`) and opens nothing; an address the pane refuses (one of the app's own, say) falls back to the question every link asks. A link either goes to the pane or lands in `requestExternalLink`: there is no other way out of `activateLink` (`security-config.test.ts` reads the source for it).
- **The life of the web view** (`BrowserPaneView` in `browser-view.ts`, one per pane, made when the pane mounts). The pane tells it what it wants: the page, and the bounds of its area or _nothing_ while it is not in view. The view makes it so, one call at a time (each Tauri command is a task of its own and does not run in the order it was sent) and keeping only the last wish of a burst:
  - It opens the web view the first time the pane is in view and not before, so a tab nobody looked at costs nothing. It closes any view of that pane first, which also clears the one a reloaded page left behind.
  - It follows the bounds of the area, and goes to another page with `navigateBrowserPane`.
  - It closes the web view for good when the pane unmounts, which is what happens when the pane or its tab is closed, the space is deleted, or the tab is archived. A tab that is reopened, restored from the library or loaded from `state.json` mounts its pane again and the view opens on the page the model has.
  - The contract has no _hide_ call, and a view that was closed to hide it would lose its page, scroll and form. So a pane that is out of view keeps its web view at the same place with **no area** (`width` and `height` zero, `hiddenBounds`) and gets its bounds back when it returns.
  - A pane is out of view when its tab or its space is not on screen, another pane of its tab is zoomed, its area has no size, or a dialog, a menu or the tab switcher is over the window. The web view is native and sits over the page, so nothing of the page can be above it; `native-cover.ts` looks for `aria-modal="true"`, `role="menu"` and the switcher in the page with a `MutationObserver` that only runs while a browser pane is mounted, and a test holds every `role="dialog"` or `alertdialog` of the interface to saying `aria-modal`.
  - The bounds are those of the area in CSS pixels from the corner of the page. They are measured after every render, when a `ResizeObserver` says the area changed size, when the window resizes, and when `observeMove` (`observe-move.ts`, an `IntersectionObserver` whose root is shrunk to the rectangle of the area) says it moved without changing size. A panel beside it that grew, or the sidebar settling after a reload, moves the area and no resize observer sees it.
  - A web view the shell refuses (an address or bounds it checks) is not tried again until the wish changes, and the pane shows the reason of the shell under its bar.

`FakeBackend` keeps the web views in memory and the test hook shows them: `window.__norenTest.browserViews()` (the pane, its page and where the view is) and `browserCalls()` (every call about a web view, in order). `e2e/browser-pane.spec.ts` holds the pane to all of this on the `FakeBackend`:

- Ctrl+click opens the pane and a plain click still asks.
- The address bar goes to a page and refuses `file`, `javascript`, the app's own addresses and the rest, with their reasons, in both languages.
- The pane is back with its page after a reload.
- The view is where the area is, and follows a resize and a move.
- The view is out of sight (no area, same page, never closed or reopened) in another tab or space, under the zoom of another pane, a dialog, a menu and the settings.
- The view is closed when the pane, the tab or the space goes away or the tab is archived, and back when the tab is restored or reopened.
- axe finds no serious violation with the pane open.

Not there, or not verified:

- The address bar shows the page the pane was sent to, not where the person went from there: the shell does not tell the page which address the web view is at after a link was followed, so the model, the bar and `state.json` keep the address that was typed or opened. There is no back, forward, reload or stop button, and a bare name such as `example.com` is refused (the pane takes a full http or https address).
- The web view is native and is over everything on its area. A tooltip (the peek of a tab, a notice) drawn where a pane is shows under it, and a tab dragged over a browser pane does not see the drop zones of the pane. Dialogs and menus are handled (above); these two are not. A click inside the page does not move the focus of the tab to the pane, since the page of the app never sees it.
- The cookies and storage of the pages are those of the web view engine's profile of the app (the same folder as the page of the app, a different origin); there is no private mode. A page cannot read the storage of the app (a different origin), and the app does not read theirs.
- Pop-ups, downloads and permission requests are refused by handlers set on the web view, rather than handled; a link that asks for a new window does nothing. No test makes a page ask for one of them (that needs an engine prompt or a download dialog), so these three handlers are set but not exercised.
- Only Windows was run. The `unstable` multi-view support of Tauri on macOS and on Linux (where a window made from the configuration may need to be built differently to take a child) was not tried: the unit and mock-runtime tests run on every platform in CI, the smoke run does not.
- Not verified (D19): what a visible window shows, such as the stacking of the child over the page of the app, the page repainting when the pane is moved, and what a web view taken to zero size (how a pane out of view is hidden) draws. The smoke run does prove, with the window hidden, that the engine takes the zero size and gives the size back with the page and its address unchanged (`smoke_browser.rs`); that nothing is drawn needs a window on the desktop of the person running the checks (`open` and `set_bounds` in `browser_pane.rs` give `add_child`, `set_position` and `set_size` the position and size they are given, zero included, and the smoke run moves the view without an error). The e2e tests check that the interface asks for the right bounds at the right time, not what the engine then draws.

## The preview pane

A pane of type `preview` shows a file on this computer: markdown, JSON, plain text or a picture. This is NOR-F15-02a: the pane in the model, the contract, the command of the shell and the pane in the interface, restored from `state.json`. Opening one from a path in the output (Ctrl+click) is NOR-F15-02b, described at the end of this section. A `preview` pane starts no shell, however it was made or restored, and unlike a browser pane it is drawn by the page itself (no web view over it), so it stacks, scrolls and zooms like any other pane.

**In the model.** `Pane.type` is `"terminal" | "browser" | "preview"` and `Pane.path` is the file. `createPreviewPane(id, path)` (`factories.ts`) makes one: no session, the default profile (so a terminal pane split from it starts the default shell), no folder. `classifyPreviewPath` and `previewPathProblem` (`file-preview.ts`) say which paths a pane may hold: a full path, which is `/...` or a drive and a separator (`C:\...`, `C:/...`); not empty or longer than 4,096 units, no control character; and not a network or device path (`\\server\share`, `\\?\`, `\\.\`, `//host`), which is never opened because opening it would reach another machine. `checkInvariants` adds four violations: `preview-path-invalid`, `preview-has-session`, `preview-has-url` and `pane-has-path` (a terminal or browser pane with a `path`). `state.json` holds the pane as it is (`type` and `path`); `parseState` accepts the three types and the invariants judge the path, so a file with a relative path is quarantined like any other broken file. `restoreWorkspace` starts a shell for the terminal panes only and reads no file: the pane reads its own when it is drawn. The workspace store never gives a session to a preview pane. The property test of the reducer also runs on workspaces where every third pane is a preview pane, and on workspaces that have both kinds (`arbWorkspace({ previewPanes: true })`). `pane/split` with a `path` makes one beside the pane it splits (NOR-F15-02b); a path `previewPathProblem` refuses, or a `path` together with a `url`, changes nothing. Splitting a preview pane gives a terminal with the default profile, and `pane/set-url` leaves it alone.

**The contract.** `Backend.readFilePreview(path)` answers a `FilePreview`: `{ kind: "markdown" | "json" | "text", text }`, `{ kind: "image", mime, bytes }` (png, jpeg, gif or webp, told by the first bytes and never by the name) or `{ kind: "refused", reason }`. A file that cannot be shown is an answer, not an error, so the pane can say why; the call rejects only when the shell itself fails. The reasons (`PREVIEW_REFUSALS`): `relative` (not a full path), `network`, `invalid` (empty, too long, a control character), `directory`, `missing`, `binary` (a NUL byte in a file that is not a picture), `too-large` (text over 1 MiB or a picture over 10 MiB; carries the `size`) and `unreadable` (the system refused, or the path is not a regular file; carries what it said). The kind of text comes from the extension (`.md`, `.markdown`, `.mdown`, `.mkd` are markdown, `.json` is JSON, anything else is text), a UTF-8 byte order mark is dropped, and bytes that are not UTF-8 become U+FFFD. An SVG is text: nothing is drawn from its markup.

**In the shell.** `noren-core::preview` (`preview.rs`, no Tauri) is the one that opens the file: `read_file_preview(path)` checks the path again (the same rules as `classifyPreviewPath`, tested with the same cases, and then whether the system takes the path for absolute: `/home/me` is not a path on Windows and `C:\Users` is not one on Linux), refuses a name Windows keeps for a device (`CON`, `NUL`...), takes the metadata (a folder is refused; so is anything that is not a regular file, because a pipe or a device would wait for ever), reads the first 12 bytes to decide the limit (10 MiB for a picture, 1 MiB for the rest), reads one byte past the limit so that a file that grew since the metadata is still caught, and only then looks for the NUL byte. Nothing is written and nothing is fetched. The command `file_preview_read` (`bridge.rs`) runs it on a blocking thread and answers one raw frame (a picture is megabytes, and JSON would make a list of numbers of it): four bytes with the length of the header, a JSON header (`{"kind":"markdown"}`, `{"kind":"image","mime":"image/png"}`, `{"kind":"refused","reason":"too-large","size":2097152}`), and the body, which is the text or the file. `decodeFilePreview` reads it in the page, and does not take the shell's word for what a body is: the mime of a picture must be the one its bytes say. `TauriBackend.readFilePreview` calls the command; `FakeBackend` keeps files in memory (`setFile`, `setDirectory`, the `files` option) and classifies them with `previewOf`, the same rules in the same order; `WebBackend` keeps them in the browser storage under `noren.web.files` so a reload finds them. The command has a permission in the capability of `main` and none in the one of `quick`.

**In the interface.** `PreviewPane.tsx`, drawn by `renderPane` in `ItemView`. A group (`aria-label` _File preview_) with the path on top and the file under it in a region the keyboard can scroll (`tabindex="0"`). The pane reads the file when it is first drawn and again when its path changes, once each, and keeps no session. What it draws is decided apart from React (`preview-view.ts`, `contentOf`) and drawn as React elements only:

- **Markdown** goes through `Markdown.tsx` and the parser of the answers of the AI (`parseMarkdown`): headings, paragraphs, lists, emphasis, inline code and fenced code. A picture, a link or a tag in the file is not an element; it shows as the text it is, so nothing is loaded and nothing runs. The blocks of code have no button, since nothing here is typed into a terminal.
- **JSON** is written out with two spaces of indent (`formatJson`: only the white space between the tokens changes, so a number the page cannot hold exactly is not rounded and the keys keep their order). JSON that does not parse is shown as text with a warning above it.
- **Text** is a monospaced block with the line breaks as written.
- **A picture** is an `<img>` over a `blob:` address made from the bytes (`URL.createObjectURL`, let go of when the answer changes or the pane goes away). The policy of the app already lets `img-src` take `blob:` and nothing from the network (`tauri.conf.json` is not changed); an e2e test serves the page with that policy and finds no violation.
- **A refusal** is a sentence for each reason, in English and Portuguese, as an alert; so is an empty file ("This file is empty.") and a failure of the shell.

The header and the pane list of the sidebar name the pane by the name of its file and call it a _file preview_, and the tab keeps being named after its terminal (`speakingPane`). A tab made only of a preview pane is named after the file when its title is cleared by the person (`paneAutoTitle`); the shell events that rename the other tabs never come for it.

The test hook `window.__norenTest.previewReads()` lists the paths the backend was asked to read, in order. `e2e/preview-pane.spec.ts` restores a `state.json` with a preview pane of each kind (markdown, a picture, text, JSON that parses, JSON that does not, a binary file) and a split with a terminal on the `FakeBackend`, and holds the pane to:

- what each one shows, and that no shell is started for them, that each file is read once and that nothing the files hold is requested or run;
- the refusals (a missing file, a folder, a file too large, an empty one);
- the panes after a reload;
- the pane in a split: beside the terminal, on top where it is drawn (`elementFromPoint`), focused by a click, zoomed and restored, scrolled by keyboard;
- a picture and a markdown file under the policy of the app;
- axe on four of them, and the words in Portuguese.

Not there, or not verified:

- The file is read when the pane is drawn and not watched: a file that changes on disk is shown again only after a reload or when the path changes (no refresh button yet).
- A path with a drive letter is judged by its syntax alone in the page; the system has the last word in the shell (a `/path` pane in a state file saved on Linux is `relative` on Windows).
- Reading a file on a network drive that has a drive letter, a symbolic link or a file another program holds locked depends on the system; the first two read what the system gives, the last is `unreadable`.
- Only Windows was run, and the Rust tests of the pipe and device refusals only run on Unix.
- Not verified (D19): how the pane looks in a visible window (spacing, the colors of the text on the theme in use, a picture larger than the pane), since no window was opened. The e2e tests check what is in the page and where it is.

### Opening a preview from the output (NOR-F15-02b)

A file path in the output of a terminal is a link. With Ctrl held (Cmd on a Mac) a click opens a preview pane beside the terminal; the keyboard stays with the terminal. A click without Ctrl does nothing, and no click hands a path to another program.

**Finding the paths** (`output-paths.ts` in the model, pure). `findOutputPaths(line)` returns the paths in a line of text with where each starts and ends:

- Full paths are `C:\...` or `C:/...` (a drive letter and a separator only: `\\?\` and `\\server\share` are not links) and `/...`. A path of `/` and one name with no extension (`/s`, `/c`: the options of a Windows command) is not a link.
- Relative paths start at `./`, `.\`, `../` or `..\`, or are a folder, a separator and a name with an extension that has a letter in it (`src/main.rs`; `v1.2/3.4` is a version). `~` is not expanded.
- A path ends at white space, a quote, a bracket, a pipe, a wildcard or a colon, so a name with a blank in it is found only up to the blank. Quotes around it and the dots, commas, semicolons, bangs and ellipsis that end a sentence are left out. After `--file=` the path is what follows.
- A `:line` or `:line:column` after the path is part of the link but not of the path. The text of an address with a scheme (`https://host/a.md`) is blanked out before the line is read, so an address is never read as a path and the link of addresses keeps it.

`resolveOutputPath(path, cwd)` gives the full path the preview opens: a full path is written out without `.` and `..` (`..` at the root stays at the root), and a relative one is joined to the folder of the pane (`Pane.cwd`, which the shell reports at each prompt) with the same normalization and the separator of the folder (`\` after a drive, `/` otherwise). The result passes `previewPathProblem`, the check the pane itself is held to. Without a usable folder the answer is `no-folder` (the path is no link); a folder on the network gives `network` and a path that is too long `invalid`.

**Underlining them** (`terminal-paths.ts`, `TerminalView.tsx`). `TerminalView` registers an xterm link provider after the addresses (`WebLinksAddon` and the OSC 8 handler are untouched, and where two links meet the earlier provider wins). `pathLinksOfRow` rebuilds the text of the logical line from the buffer (a row that continues the one above is joined to it, up to eight rows each way), maps each UTF-16 unit back to its cell (a wide character takes two cells, so the range is in cells and not in characters), runs `findOutputPaths` on it, and keeps the links that touch the row asked about. Nothing reads a disk: what is underlined depends on the text on screen and the folder of the pane only. A relative path is a link only where the pane has a folder; one that resolves to a network path is a link too, so that the click can say why it opens nothing. `activate` calls `onOpenPath(path)` (the path as written) only when Ctrl or Cmd is held.

**Opening it** (`openPreviewBeside` in `App.tsx`). It resolves the path against the folder the pane is in at the click and, if the path is refused, says why in a notice (the same `pane-notice` the browser uses; `preview.open.*`, in English and Portuguese) and makes no pane. A tab already at its limit of panes (`terminal.maxPanes`, `DEFAULT_MAX_PANES` when the file says nothing) says so and makes no pane. Otherwise it dispatches `pane/split` (row, after) with the full `path` and gives the focus back to the pane the link was in. `pane/split` with a `path` makes a preview pane (`createPreviewPane`: no session, no folder, the default profile); it refuses a path `previewPathProblem` refuses, and a `path` together with a `url`. The file is not looked at until the pane is drawn, where the pane reads it once and shows a missing file, a folder or a binary as the reason it is refused.

A tab left with a preview pane as the one it speaks for (the terminal was closed or taken out) is named after the file, unless the person named the tab (closing finding 219).

`e2e/preview-output.spec.ts` holds this to the whole page on the `FakeBackend`, with the files of the fake computer seeded in the storage and a saved state of one terminal in a folder:

- the pointer over a path puts `xterm-cursor-pointer` on the screen of the terminal (xterm does that for a link under the pointer: the canvas cannot be read), and not over the words around it, a relative path with no folder, or plain words;
- Ctrl+click on an absolute path, a relative path (`./pixel.png`, `../log.txt` from a sub folder) and a path with `:12:5` opens the right file beside the terminal, with the full path in `state.json`, no session, no new shell, the file read once, nothing opened outside and the keyboard (`document.activeElement` and the focused pane) with the terminal;
- a click without Ctrl, hovering, a relative path in a pane with no folder, and an address in the output open nothing of this kind (an address with Ctrl still opens a browser pane, and without it still asks);
- a folder on the network and a full tab say why and make no pane and no read;
- the preview pane is there after a reload, with one shell;
- axe finds no serious violation with the preview and the notice, and the notices and the pane speak Portuguese.

Without the link provider 14 of the 17 tests fail (the three that stay are the ones about nothing opening); without the Ctrl check the test of the click without Ctrl fails.

Not there, or not verified:

- A path with a blank in it is found only up to the blank.
- xterm keeps the links of the row the pointer is on until the pointer moves to another row, so output that rewrites that row under a pointer that stays still shows the old underline until the next move. The link of addresses behaves the same.
- The line number is read and dropped: the preview does not scroll to it.
- Not verified (D19): the underline and the pointer cursor drawn on a real window, and the click in the real WebView2 engine. Both are xterm code that web mode runs in Chromium; the app only gives it a provider.

## The diff pane

A pane of type `diff` shows the `git diff` of a folder: the changes of the working tree and the index against `HEAD`, with the files that changed in a list and the one picked side by side. This is NOR-F15-03. A `diff` pane starts no shell, however it was made or restored, and unlike the browser pane it has no web view: the page draws everything itself, so it stacks, zooms and scrolls like any pane.

**In the model.** `Pane.type` is `"terminal" | "browser" | "preview" | "diff"` and the folder is `Pane.cwd`, the field a terminal pane already has for its folder; on a diff pane it is required, never moves (no shell reports a new one), and has to pass `previewPathProblem` (a full local path, not a network or device one). `createDiffPane(id, cwd)` (`factories.ts`) makes one: no session, the default profile (so a terminal pane split from it starts the default shell, in the same folder). The invariants add `diff-cwd-invalid`, `diff-has-session` and `diff-has-url` (and `pane-has-path` already covered a path on any pane but a preview); `state.json` accepts the type; `restoreWorkspace` starts nothing for it and runs no git. `pane/split` takes `diff: true`: the new pane is a diff pane on `cwd` (the folder of the split pane when no `cwd` is given), and a folder `previewPathProblem` refuses, none at all, or `diff` together with `url` or `path`, change nothing. The property test of the reducer runs sequences on workspaces whose every third pane is a diff pane.

**The contract.** `Backend.readGitDiff(cwd)` answers a `GitDiff`: `{ kind: "diff", text }` (the text `git diff` printed, empty when nothing changed) or `{ kind: "refused", reason, detail? }`. A folder git cannot be run in is an answer, not an error, so the pane can say why; the call rejects only when the shell itself fails. The reasons (`GIT_DIFF_REFUSALS`) are `relative`, `network` and `invalid` (the folder is not a full local path), `missing` (nothing there, or not a folder), `not-a-repository`, `git-missing` (`git` could not be started), `too-large` (more than `MAX_GIT_DIFF_BYTES`, 2 MiB) and `failed` (git ran and refused: `detail` is what it said, in English). `decodeGitDiff` reads the answer of the shell without taking its word for it. The `FakeBackend` answers from `gitDiffs` / `setGitDiff` (by the folder of a repository, any folder inside it gets the same answer; a fake repository with no entry has no changes; a folder in none is `not-a-repository`); the web backend keeps the diffs in the storage under `noren.web.git-diffs`, so a reload finds them.

**The parser** (`git-diff.ts` in the model, pure). `parseGitDiff(text)` reads the unified diff into files: path (and the old one for a rename or a copy), status (`modified`, `added`, `deleted`, `renamed`, `copied`), `binary`, similarity, modes, hunks with each line numbered on both sides, and how many lines were added and removed. A hunk is read by the counts in its header, so a deleted line that starts with `--` (it prints as `---`) is a line and not the header of a file; `\ No newline at end of file` marks the line before it; a name git quoted (`"caf\303\251.txt"`) is read back; a diff cut short gives what was read. It never throws. `sideBySideRows(file)` sets the lines side by side: a hunk row, a row for each line both files have, and for a run of deleted and added lines the first deleted line against the first added one and so on, the longer side going on alone. Tests are examples taken from real `git diff` output and a fast-check property: any files printed the way git prints them (names with spaces and non-ASCII characters, lines that look like headers or markers) read back as the same files, the left column is the old file and the right one the new file in order, any text at all reads without throwing, and a diff cut anywhere keeps the files before the cut.

**In the shell.** `noren-core::git_diff` (`git_diff.rs`, no Tauri) is the one that runs git: `GitCli::diff(folder)` (`read_git_diff` with the `git` of the system) checks the folder again (the same rules as the path of a preview, and that it is a folder), asks `git rev-parse --is-inside-work-tree` (a folder in no repository is `not-a-repository`; a repository another user owns is `failed` with what git said), picks `HEAD` or, when the repository has no commit yet, the empty tree of the repository (`git hash-object -t tree --stdin`, so a staged file shows as added), and runs `git -c core.quotePath=false -c core.fsmonitor=false diff --no-color --no-ext-diff --no-textconv -M --src-prefix=a/ --dst-prefix=b/ <HEAD or empty tree> --`. It goes through `GitCli` like the worktrees (`GitCli::command`: arguments one by one, never through a shell, stdin closed, `GIT_TERMINAL_PROMPT=0`, no window on Windows). It adds `GIT_OPTIONAL_LOCKS=0` and `LC_ALL=C` (what git says about a refusal is English), reads at most 2 MiB of the output and, at one byte more, kills git and answers `too-large`; the error stream is read on a thread so a full pipe never stops it. The command `git_diff_read(cwd)` (`bridge.rs`, with its entry in `build.rs` and the capability of the window `main`) answers the JSON of `GitDiff::to_json` and runs on `spawn_blocking`. The settings of the repository cannot change what comes back or run something: the prefixes, the renames, the colors and the quoting are fixed on the command line, `--no-ext-diff` and `--no-textconv` keep the programs the attributes name from running, and the file-system monitor hook (`core.fsmonitor`, a program a cloned repository can name) is turned off; a test makes a repository name one and checks it does not run. Files git does not track are not in `git diff`, so they are not listed. The index is not refreshed on disk: the commands are the ones that do not do that (`git status` does).

**In the interface.** `DiffPane.tsx`, drawn by `renderPane` in `ItemView`. A group (`aria-label` _Git diff_) with the folder on top beside a refresh button, and under it a list of the changed files (a button for each, with a letter, the path and `+n −m`, the picked one `aria-current`) and the lines of the picked file in a region the keyboard can scroll (`tabindex="0"`): a table with the old file (_Last commit_) on the left and the new one (_Working tree_) on the right, a line number and a sign (`-`, `+`) on each side, and the end-of-file marker where it applies. A binary file, a change of mode and a rename with no change say so in a line instead of a table. Every line is a text node in a table cell, so nothing a file holds becomes markup. A file of more than 2000 rows draws the first 2000 and a button for the rest. A pane too narrow for two columns puts the list above the lines (a container query). Deletion and addition are tinted with the muted color and the accent of the theme, which has no red and no green, and the sign and the empty cell on the other side carry the meaning. What it draws is decided apart from React (`diff-view.ts`, `contentOf`) and every refusal is a sentence in English and Portuguese, as an alert, with the folder and the refresh button still there.

The pane reads the diff when it is first on screen (its tab and its space shown and no other pane zoomed over it), again each time it comes back to the screen, when the folder changes and when the refresh button is pressed, and not before: a diff pane in a tab nobody opened runs no git. The answer of an earlier read is not drawn for a later folder.

**Opening one.** "Show git diff beside this pane" is an action of the registry (`diff.open`, no chord, in the palette). `openDiffBeside` (`App.tsx`) takes the folder of the focused pane of the tab on screen (the start folder of the space when the pane has none, as the worktrees do) and dispatches `pane/split` (row, after) with `diff: true` and that folder, then gives the focus back to the pane it came from, so the keyboard stays with the terminal. A pane with no known folder, a folder git is not run in (a network path) and a tab already at its limit of panes (`terminal.maxPanes`) say so in a notice (`diff.open.*`, in English and Portuguese, the same `pane-notice` the browser and the preview use) and make no pane. Nothing is read there; the pane asks git itself.

The header and the pane list of the sidebar name the pane _Changes in <folder>_ and call it a _git diff_, and the tab keeps being named after its terminal (`speakingPane`: the first terminal speaks for a tab whose focused pane is not one). A tab made only of a diff pane is named after the folder, unless the person named it (`paneAutoTitle`, and `retitle` when the terminal beside it is closed or taken out).

The test hooks `window.__norenTest.gitDiffReads()` (the folders the backend was asked to read, in order) and `setGitDiff(folder, text | refusal | null)` serve the e2e tests. `e2e/diff-pane.spec.ts` (26 tests) restores a `state.json` with diff panes on the `FakeBackend`, with the text of a real `git diff` as the fixture (`e2e/fixtures/diff/sample.diff`: a file with two hunks, an added, a deleted and a renamed file, a binary one, a change of mode, a file with no line break at the end and a name outside ASCII), and holds the pane to:

- the folder on top, the files in the order git printed them with their letters and counts, the first one side by side (the old file to the left of the new one on the same row), each kind of change as described above, the keyboard on the file list, and no shell started and nothing requested outside the app;
- a diff pane in a tab nobody opened reading nothing, reading again when its tab comes back, and the refresh button reading again, keeping the picked file while it is there;
- the palette opening the diff beside the terminal with the folder in `state.json`, no session, no new shell, the keyboard with the terminal and the pane there after a reload; the start folder of the space used when the pane has none; the notices for no folder, a network folder and a full tab (and no pane in those cases);
- the pane in a split: beside the terminal, on top where it is drawn (`elementFromPoint`), focused by a click, zoomed and restored, scrolled by keyboard, the cap of rows and the button for the rest, and the tab titled by its terminal while the diff has the keyboard;
- every refusal in words (not a repository, no git, too large, git refusing, a missing folder), a clean repository, axe on a diff, an added file, a binary file, a clean repository and a refusal, and all the words in Portuguese.

Without the branch for the diff pane in `renderPane` 20 of the 26 tests fail (the six that stay are the ones about no pane being made, in English and in Portuguese); without the `visible` check the test about a tab nobody opened fails, and without the `retitle` for a diff pane the test of the tab left with only the diff fails.

The real git is run by `crates/noren-core/tests/git_diff_real.rs` (13 tests against scratch repositories with a scratch home and a fixed identity): a clean repository, a change in the working tree, the index and the working tree together, a deleted, a renamed and a binary file, a subfolder, a repository with no commit, a folder in no repository, the inside of `.git`, a diff past the cap, the settings of the repository not changing the text, a name outside ASCII, the fsmonitor hook not running and the index not written. The command is run in the mock runtime of Tauri in `bridge.rs`.

Not there, or not verified:

## The AI client

`noren-core::ai` (`ai.rs`) talks to the AI providers. Only the Rust side does: the page never opens a connection to a provider. It knows two kinds, `openai-compatible` (`POST {base}/chat/completions`, `Authorization: Bearer`; covers Ollama, LM Studio, vLLM, OpenRouter, OpenAI and Groq) and `anthropic` (`POST {base}/v1/messages`, `x-api-key` and `anthropic-version`), both with the answer as a server-sent event stream. A `Provider` is an id, a kind, a base URL and a model; it does not hold the key.

Three layers, the first two without I/O:

- `SseDecoder` turns the bytes of a `text/event-stream` body into messages. The pieces come cut anywhere, inside a line or inside a character, and it keeps the rest until the line ends (`\n`, `\r\n` and a lone `\r` all end a line).
- `StreamParser` reads those messages in the format of the provider and yields `StreamEvent`s: `Delta(text)`, then exactly one `Done { output_tokens }` or `Error(AiError)`. For the chat completions format a delta is `choices[0].delta.content` and the end is `data: [DONE]`; for Anthropic it is `content_block_delta` (`delta.text`) and `message_stop`, and an `error` event ends the stream with its message. `output_tokens` is the count of tokens of the answer when the provider reported it, and `None` otherwise: the chat completions request asks for it with `stream_options: { include_usage: true }` and it is `usage.completion_tokens` of any chunk (the last one has no `choices`, which is neither an error nor a delta); for Anthropic it is `usage.output_tokens` of `message_delta` (or of `message_start`), the last valid one wins. A value that is absent, negative, fractional or not a number is `None`, never an error. A stream that stops before the provider said it was complete is an error, not a silent end.
- `AiClient::chat_stream(provider, api_key, messages, cancel, on_event)` sends the request and calls `on_event` as the answer arrives. The timeout bounds the connection, the wait for the headers and the silence between two pieces of the body, not the whole answer. A `CancellationToken` ends the request at once with `AiError::Cancelled` and drops the connection (the server sees it close). The client is async and runs on a runtime the caller owns (`tokio`); `reqwest` has the `native-tls` feature, so TLS and its certificate roots come from the system, and the default rustls with `aws-lc` is off because of its licenses.

**The key is a parameter.** `chat_stream` takes `Option<&str>`; this module never stores, reads or logs it (the system keychain is the job of the layer above). It goes in one header. Redirects are never followed, because `x-api-key` would go along to the other host. Every error text that leaves the client has the key replaced by `[key]`, as providers often echo it in a 401 message; an HTTP error carries a readable reason taken from the body (`error.message`), cleaned and limited in length. `AiError` tells the user what to do: rejected key (401/403), other HTTP status, unreachable, timeout, cancelled, error inside the stream.

**Ollama.** `AiClient::detect_ollama(base_url)` does `GET /api/tags` and returns `OllamaProbe::Found(models)` or `NotFound`. A closed port, a timeout (at most 3 s), a non-200 status and an answer that is not Ollama's are all `NotFound`: most machines do not have Ollama, so that is not an error. The pre-registered provider is `Provider::ollama(model)` (`http://localhost:11434/v1`, no key). `AiClient::ollama_memory(base_url, model)` does `GET /api/ps` with the same byte ceiling and short timeout and returns `Option<OllamaMemory { bytes, vram_bytes }>` from the `size` and `size_vram` of the entry whose `name` or `model` is the asked model (`llama3` is `llama3:latest`); a closed port, a timeout, a status that is not 2xx, a body that is not Ollama's, a model that is not loaded and a number that is not a whole number of 0 or more (or that a JavaScript number cannot hold exactly) are all `None`, never an error.

The tests run the client against a small HTTP server of their own on `127.0.0.1` at a port the system picks (a `TcpListener` per test, on threads): both formats streamed in pieces cut mid-line, the headers of each, a 401 whose body echoes the key, other statuses, a redirect that is not followed, silence before and in the middle of the stream, cancellation in the middle (and the closed connection), and Ollama present, empty and absent. Nothing reaches a host outside the machine.

## The key vault and the AI commands

**Where the keys live.** `noren-core::vault` (`vault.rs`) holds the `KeyVault` trait (`get`, `set`, `delete` by provider id). `KeyringVault` is the real one, on the `keyring` crate and the native store of each system (Credential Manager on Windows, the Keychain on macOS, the Secret Service over D-Bus on Linux; no backend that keeps a file is built in). The entry has the service `noren` and the provider id as user name. `MemoryVault` is the fake one for the tests (and for the smoke runs, so they cannot touch the keychain of the person). A key is never written to the config, the state or a log. The provider id is checked before it reaches the system (1 to 64 ASCII letters, digits, `-` or `_`, starting with a letter or digit), a key longer than 1024 characters is refused, and no error text of the vault holds a key.

**The commands.** `apps/desktop/src-tauri/src/ai.rs` keeps the logic in `AiState` (the vault, the providers, the `AiClient` and the requests in flight as a map from request id to `CancellationToken`), which needs no Tauri runtime; the commands only unpack the arguments:

- `ai_providers()` returns `[{ id, kind, baseUrl, model, hasKey }]`: the pre-defined Ollama first, then the providers handed over with `ai_configure`. It says whether a key is stored and never gives the key.
- `ai_configure(providers)` takes the providers of `ai.providers` in the settings, `[{ id, kind, baseUrl, model }]`, and replaces the ones it had. See the next section.
- `ai_ollama_models()` returns `{ found, models }`: the models the pre-defined Ollama has installed (`GET /api/tags`), or `found: false` when it does not answer.
- `ai_ollama_memory(model)` returns `{ bytes, vramBytes }` for a model the pre-defined Ollama has loaded (`GET /api/ps`), or `null` when there is nothing to report; it asks only the pre-defined Ollama, never a provider of the settings, and is for the main window only.
- `ai_test_connection(providerId)` returns `{ ok: true }`, or `{ ok: false, kind, message }`. See the next section.
- `hardware_read()` (in `bridge.rs`, over a `HardwareState` that holds the source: the app manages the real one, the tests a made-up one, so no test starts `nvidia-smi`) returns `{ ramBytes, vramBytes }`, the total RAM and the video memory in bytes, with `vramBytes: null` when it is not known (no `nvidia-smi`, no NVIDIA card, an answer that makes no sense), or `null` when the RAM is not known. `noren-core::hardware` reads the RAM with `sysinfo` and the VRAM from `nvidia-smi` (hidden, 3 s deadline) behind the `HardwareSource` trait; a value that is not a whole number of bytes from 1 to 2^53 - 1 is dropped, never an error. For the main window only. See [BENCH.md](BENCH.md#the-memory-of-the-machine).
- `ai_set_key(providerId, key)` stores the key, or removes it when it is empty. It is the only way a key enters the app, and nothing logs it.
- `ai_chat_stream(providerId, requestId, model?, messages, onEvent)` reads the key from the vault, runs `AiClient::chat_stream` and sends each event through the `Channel` as `{type: "delta", text}`, then one `{type: "done"}` (with `outputTokens` when the provider reported the count: `{type: "done", outputTokens: 42}`) or `{type: "error", kind, message}` (`kind` is `invalid-request`, `auth`, `http`, `network`, `timeout`, `cancelled`, `provider` or `protocol`). The page chooses `requestId`, so it can cancel before the first event; the request leaves the map when it ends, however it ends. A request that cannot even start (unknown provider, bad id, unknown role, an id already running, a vault that cannot be read) returns an error and sends no event. If the channel cannot be written to any more, the request is cancelled. Ollama needs no key, so a keychain that is not there does not stop it.
- `ai_cancel(requestId)` cancels the request and returns whether there was one; an unknown id does nothing.

The tests use `MemoryVault` and a fake provider on `127.0.0.1` at a port the system picks: both formats streamed with the key of the vault in the header, a 401 whose body echoes the key (the message the page gets does not hold it), cancellation in the middle (and the closed connection), a cancel for an unknown id, a bad provider id, and the commands called in the mock runtime of Tauri. Nothing touches the real keychain or a host outside the machine; the real keychain is the one thing the tests do not cover (it needs the desktop session of a person).

## The AI providers and their settings

The AI is off until the person turns it on, and every piece that decides that is in `packages/model` (pure TypeScript) or in the Rust state; the page only asks.

**Settings (`ai` in `config.jsonc`).** `ai.enabled` is `false` unless the file says `true`. `ai.providers` lists the providers of your own: `id` (lower case letters, digits, `-` and `_`, at most 64; it names the keychain entry), `kind` (`openai-compatible` or `anthropic`), `baseUrl` (`http` or `https` with a host, and no user name or password in it) and `model` (the default model of the provider). Ollama is always there with the id `ollama` and cannot be listed: that id is reserved, and an id used twice is an error, at the line of the second one. `ai.defaults` names a `{ provider, model }` for each function (`ask`, `explain`, `command`); `provider` has to be `ollama` or an id in `ai.providers`, which the schema checks. No key has a place in the file: a provider has exactly those four fields, and one with another (`apiKey`, say) is an unknown setting. The schema is `AiProviderSchema` and the `ai` object in `config.ts`, and `docs/config.schema.json` is generated from them like the rest.

**Off for one space.** `Space.aiEnabled` in `state.json` (on for a new space, and `true` for a state saved before the AI existed) is changed by the action `space/set-ai { spaceId, enabled }`. `aiIsOn(settings, space)` is the single answer to "is the AI on here": `ai.enabled` and `Space.aiEnabled` both have to be on. The rule for the interface that uses it (the providers screen and the Ask panel) is that when it is off nothing calls a provider and no AI entry shows.

**The `ai` member of `Backend`.** `ai.providers()` lists Ollama and then the configured providers with `hasKey`; `ai.configure(providers)` hands the providers of the settings over, replacing the ones the backend had (the providers screen calls it when the settings load and when they change; until then the backend knows Ollama only); `ai.setKey(providerId, key)` stores the key in the keychain (blank removes it) and is the only call that carries one; `ai.listOllamaModels()` answers `{ found: true, models }` or `{ found: false }`; `ai.ollamaMemory(model)` answers `{ bytes, vramBytes }` of a loaded model or `null` (the bench reads it, see [BENCH.md](BENCH.md#the-memory-of-the-model)); `ai.testConnection(providerId)` answers `{ ok: true }` or `{ ok: false, kind, message }`. `ai.chat(request, onEvent)` asks a question and `ai.cancel(requestId)` cancels it (next section). `TauriBackend` maps each to the command of the same name in `ai.rs`; `FakeBackend` has a fake Ollama (`ollamaModels`, `setOllamaModels`), a fake keychain whose keys `ai.providers` never shows (a test peeks with `storedAiKey`, and the recorded call `ai.setKey` holds the id only) and a connection test that is ok, or fails the way the real one does (Ollama that is not there, Anthropic without a key, or the answer a test chose with `setAiConnectionResult`).

**In Rust (`AiState`).** The pre-defined Ollama is built in; `configure` replaces the rest as a whole. It checks the list again, because the page's word is not taken: ids are 1 to 64 letters, digits, `-` or `_`; `ollama` is reserved and an id used twice is refused whatever the case (the keychain of Windows does not tell `Work` from `work`); the kind is one of the two; the address starts with `http://` or `https://`, names a host and holds no user name or password; at most 50 providers. A list with a problem is refused whole, with the number of the provider in the text, and the providers it had stay. The list a provider is given with has no room for a key (`deny_unknown_fields`): a field it does not know makes the command fail instead of the key being read. The key of a provider that leaves the list stays in the keychain, for when it comes back. Whether the AI is on is not known here: the switch of the settings and the one of the space are the page's, as the Ask panel is.

**The connection test.** `AiClient::check_connection` reads the list of models of the provider (`{base}/models`, or `{base}/v1/models` for `anthropic`) with the key of the keychain in the header its kind reads: a request that needs the key, costs nothing and needs no model, unlike a chat. Any success status is ok. The failure is an answer, `{ ok: false, kind, message }` (`kind` is one of `invalid-request`, `auth`, `http`, `network`, `timeout`): a rejected key (401 or 403) says so, another status gives the status and the reason in the body, an address that does not answer or a host that is not there is `network`, silence is `timeout` (at most 15 seconds), and `anthropic` with no key is `invalid-request` without any request being made. The key is taken out of every text, because providers often repeat it in a 401, and a redirect is not followed. The test can only fail to start (an `Err`) for a bad provider id, an unknown provider, or a keychain that cannot be read; Ollama needs no key, so a keychain that is not there does not stop it.

**Asking (`ai.chat` and `ai.cancel`).** `ai.chat({ requestId, providerId, model?, messages }, onEvent)` streams the answer as events: zero or more `{ type: "delta", text }`, then exactly one `{ type: "done", outputTokens? }` (`outputTokens`, a whole number of 0 or more, is there only when the provider reported the count of tokens of the answer) or `{ type: "error", kind, message }` (`kind` is one of `AI_ERROR_KINDS`; a cancelled request ends with `cancelled`), and it resolves once that last event has been handed over. It rejects, with no event, when the request could not start (a bad id, no such provider, a request id already running, an unreadable keychain). The caller picks `requestId` (1 to 64 letters, digits, `-` or `_`) so that `ai.cancel(requestId)` can name it before the first event; it resolves with whether such a request was running. The request has no key: the Rust side reads it from the keychain. `TauriBackend` calls `ai_chat_stream` with a `Channel` (events shaped as `AiStreamEvent` in `ai.rs`, `{"type":"delta","text"}`, `{"type":"done"}`, `{"type":"error","kind","message"}`) and `ai_cancel`; it hands over one end only, ignores whatever follows it, and if the command returns and no end arrives within `AI_END_GRACE_MS` it ends the request with a `protocol` error instead of hanging. `FakeBackend` has a fake provider (`aiReply`, `setAiReply`; `aiTokens`, `setAiTokens` for the count in `done`) that answers in deltas a word at a time and records the request (so a test reads the messages that were sent from `callsTo("ai.chat")`); it ends with an error where the connection test would fail. `holdAiAnswer(true)` makes every answer wait after its first piece (a `cancel` still ends it at once), so a test can press Stop while an answer is in the middle.

**What an Ask message is made of.** Two pure functions in `@noren/model` stand between the panel and `ai.chat`. `redactSecrets(text)` swaps secrets for markers (`[REDACTED:jwt]`) and says how many it swapped and of which kinds: PEM private keys (an unfinished block goes to the end of the text), AWS access keys, GitHub tokens, `sk-` and `sk-ant-` keys, Stripe keys, Google API keys, JWTs, chat tokens (`xox`), the password in a URL, `Authorization` headers, bare `Bearer` tokens, and the value of `password=`, `token=`, `api_key=`, `secret=` and kin. It leaves alone what only looks like one (git hashes, UUIDs, a bare word `password`, `sk-` with no token, text in Portuguese) and errs on the side of hiding. `buildAskMessages({ settings, space, question, chips })` takes the chips the person chose (`selection`, `lastOutput` with its command, `screen`, `tab` with its title and the text of that tab; their text is read by the caller), redacts every text, keeps each chip to `MAX_ASK_CHIP_CHARS` (a selection keeps its start, any other chip keeps its end, and a line in the text says how much was cut), and returns `messages` (the system prompt, then one user message: the chips in order, each under a heading in a fence, then the question) with `preview`, the same messages written out role by role, the count and kinds of redactions and the chips that were cut. It builds nothing and answers `ai-off` when `aiIsOn(settings, space)` is false, and refuses a blank question or one over `MAX_ASK_QUESTION_CHARS`. What goes to `ai.chat` is exactly `messages`.

Tests: the settings (valid, invalid, a repeated id, `ollama` refused, a key refused, a default naming a provider that is not there, the generated schema), `space/set-ai` and the state file, the fake backend, the mapping of `TauriBackend`, and in Rust the providers handed over, the models of Ollama (present, empty, absent), the connection test for both kinds (headers, 401 echoing the key, other statuses, a closed port, silence, a missing key) and the three commands in the mock runtime, all on `127.0.0.1` at a port the system picks, with `MemoryVault`.

## The Ask panel

The panel is `AskPanel.tsx`, a side column next to the terminal (on the side the sidebar is not), and it is made of three parts that can be tested apart: the pure rules (`ask-panel.ts`), the Markdown of the answer (`parseMarkdown` in `@noren/model`, drawn by `Markdown.tsx`), and the shell that reads the terminals and mounts it (`App.tsx`).

**Where it shows.** `ask.toggle` ("Ask the AI", category General) is an action of the shortcut registry, `Ctrl+Shift+A` in both presets, so the shortcuts screen lists it, records it anew and the palette runs it. The shell mounts the panel only when `aiIsOn(settings, space)` holds. When it does not, the panel is gone (a panel that was open goes away at the moment the switch is turned off, and does not come back by itself when it is turned on again), the key says why in the notice (`askOffNotice`: off in the settings, or off for this space) and the palette does not list the entry (`buildEntries` lists the actions of the AI only when it is given `aiOn`). Nothing in the panel runs without the panel, so with the AI off nothing can call `ai.chat`. Closing the panel (the button, Escape, the key again) cancels an answer that is still coming and gives the keyboard back to the terminal; the conversation is not kept.

**The chips.** Four places can be switched on, and the panel reads them only when the question is previewed, through `AskSources`, which the shell fills from the `TerminalHandle` of the pane in use: the selection (`selection()`), the output of the last command (`lastOutput()`, the rows between the shell's OSC 133 marks of F7-03, with the command line taken from the row of that command's prompt), the visible screen (`screen()`, the rows on screen with wrapped lines joined again) and other tabs added with `@ Tab` (`readLines()` of the focused pane of that tab, so a tab in the background is read from its terminal as it is). The tabs on offer are the other tabs of the space on screen. `readAskChips` keeps a fixed order (selection, last output, screen, then the tabs as they were added), leaves out a chip that was on and has nothing to read, and says so in the preview. `buildAskMessages` (see above) then redacts and cuts.

**Who answers.** `askTarget`: the provider and model `ai.defaults.ask` names; else the first provider of `ai.providers` with its own model; else the first model of the Ollama of the computer (asked only in that case, `askNeedsOllama`). When none of them exists the panel shows the steps to a first provider and no box to type in.

**Preview, then send.** Enter in the question box (or the Preview button) calls `buildAskMessages` and shows its `preview` as it is, in a box, with where it goes, a line with the number and kinds of secrets that were replaced (`secretsLine`), a line for each chip that was cut and each chip that had nothing. Nothing has been sent at that point; Edit (or Escape) goes back to the question. Send calls `ai.chat` with exactly the `messages` that were previewed (the same object, not a rebuilt one), after `aiProvidersSync.settled()` so the providers of the settings have reached the backend. A request id is made by `askRequestId`.

**The answer.** Each event goes through `applyAskEvent`: deltas are appended in order, the first `done` or `error` ends it and anything after is ignored; a `cancelled` end is a "Stopped." answer that keeps what had come, any other error is an alert with the sentence of the provider. While an answer is coming the question box is closed and Stop takes the place of Preview (it calls `ai.cancel`). The answer is drawn again as it grows.

**Markdown.** `parseMarkdown` reads what a chat answer is made of and nothing more: paragraphs, headings (`#` to `######`), lists (bullets and numbers, with a fenced block indented under an item kept in it), `**strong**`, `*emphasis*`, inline code between backticks and fenced code blocks (fenced with three backticks or with `~~~`, with a language when it is a plain name). Links, images, tables, quotes, HTML and underscores (so `snake_case` stays whole) are plain text, and a backslash is an escape only before `*` and before a backtick (so a Windows path such as `C:\Users` is safe). The result is a tree of data, never markup: `Markdown.tsx` turns each node into a React element with its text as a child, so React escapes whatever the model wrote, and there is no `dangerouslySetInnerHTML` and no link. It is made for answers that arrive in pieces: a block whose fence has not closed is `open`, a closing fence that has only partly come (two of the three backticks) is not shown as code, and a mark with no partner yet is plain text until the partner comes. A work budget in proportion to the size of the text bounds the formatting of a text built to be slow; the rest is shown as it is. The tests include fast-check properties: it never throws, the same text gives the same tree, text with no marks comes out equal, HTML ends up as text (every angle bracket typed is in the text shown), and the text of a fenced block is kept exactly.

**Insert in terminal.** Each code block has a button that hands its text to `TerminalHandle.insert`, which puts it at the prompt as a paste and gives the terminal the keyboard back. It never presses Enter: `insertableText` drops the line breaks at both ends and takes out every control character but tab and the line breaks (an answer is untrusted, and Escape, Ctrl+C or Ctrl+D typed into a shell by an answer would be key presses nobody made), and text of several lines goes through `decidePaste`, so the person is asked ("Paste N lines?", "Every line may run as a command.") before a line break reaches the shell. The button waits: it is off while the answer is still coming, while the block has not closed and for a block with only blanks. The text of a block is what `insert` is given, never HTML.

**What a test can do.** The e2e tests (`e2e/ask-panel.spec.ts`) run against the `FakeBackend`: `window.__norenTest` gives the questions the fake provider was sent (`aiChats`, with the messages exactly as they went), the requests cancelled (`aiCancels`), everything written to a session (`writes`), and sets or holds the answer (`setAiReply`, `holdAiAnswer`).

## Explain and `? text`

Two more ways into the AI, both through a preview that waits for the person's Send, both redacted, neither runs anything, and both gone where the AI is off.

**Who answers, by function.** `askTarget(config, ollama, fn)` and `askNeedsOllama(config, fn)` take the function (`ask`, `explain` or `command`, the keys of `ai.defaults`): the provider and model that function names; else the first provider of the file; else the first model of the Ollama of the computer. A provider named only for Ask does not answer Explain: the fallback is the same for all three. `useAskTarget` (`use-ask-target.ts`) wraps it for the panel and the dialog, asking the Ollama of the computer for its models only when the settings do not say.

**Explain.** The Explain button of a failed command (see [SHELL_INTEGRATION.md](SHELL_INTEGRATION.md#command-marks)) hands an `ExplainRequest` (the command line, its output, the exit code, whether the output was cut at the start) to `TerminalView.onExplain`, which `PaneTerminal` passes only when `aiIsOn(config, space)`, through a context the shell provides (`ExplainContext`). The shell opens the Ask panel with `explain={{ request, seq }}`. The panel puts a `command` chip first in the message (`AskChip` of kind `command`: heading "Output of a command", `Command:` line, `Exit code:` line, a note when the start of the output was gone, text cut from its start when it is too long), types the question `EXPLAIN_QUESTION` and opens the preview at once. Send is still the person's: the preview shows the exact messages, and Edit goes back to the question. The answer comes from `ai.defaults.explain`; the chip is spent with the question, so the next question is Ask's again. Each press replaces the one before. The code blocks of the answer have the same _Insert in terminal_ as any answer.

**`? text` in the palette.** See [PALETTE.md](PALETTE.md#-text-ask-for-a-command). The pure parts are in `@noren/model` (`command-ask.ts`): `commandRequestOf` reads the request out of the query, `buildCommandMessages` makes the two messages (instructions naming the shell and the system, then the request, every text through `redactSecrets`) and the exact preview, and `extractCommand` takes the one-line command out of the answer. The shell is the name of the profile of the focused pane (`shellNameOf`: the default profile when the pane names none) and the system comes from the user agent of the web view (`osNameOf`). Insert reuses `TerminalHandle.insert`.

**What a test can do.** `e2e/explain-command.spec.ts` runs both flows against the `FakeBackend` and checks, in the writes the backend recorded, that no `\r` or `\n` reached the session, that the messages the fake provider received are the text of the preview, and that with the AI off (settings or space) there is no button, no entry and no call.

What is not there yet: the questions of a conversation stand alone (earlier turns are shown but not sent again), a tab chip reads only the focused pane of that tab, and the panel has a fixed width.

## The local API

`noren_core::api` (`crates/noren-core/src/api/`) is the server that lets a program on the same machine, running as the same user, drive Noren the way a person does. This step (NOR-F17-01a) is the transport and the rules of the conversation; what a call does in the workspace is decided in `@noren/model` (NOR-F17-01b, below), the app starts the server and hands each call to the main window through an `ApiHandler` (NOR-F17-01c, [the bridge](#the-bridge-to-the-main-window) below), the `--smoke-api` check comes after it (NOR-F17-01d), then the events: the server side of them is [below](#events-on-the-server) (NOR-F17-01e) and the bridge and the page that publish them are next (NOR-F17-01f). The server itself needs no window.

- **Who can connect.** The endpoint is the one of the session daemon (`daemon::ipc`) under another name: `api_endpoint("default")` is `api-default` among the names `Endpoint::named` takes, never the daemon's `default`. On Windows it is a named pipe whose security descriptor grants the SID of the current user and nobody else, with remote clients rejected and the first instance created exclusively; on Unix it is a socket (0600) in a folder that belongs to the user (0700), and every accepted connection must come from the same user id. See [DAEMON.md](DAEMON.md) for how that is done.
- **The token.** The first message of every connection carries a token, 32 bytes from the random generator of the system (`getrandom`) written as 64 hexadecimal characters in a file the caller names (`load_or_create_token(path)`). A missing file is created, a file that holds no token (empty, cut, not hexadecimal, longer than 256 bytes, not a plain file, a link) is replaced, and a good one is reused (and tightened to 0600 on Unix). The new file is written next to the old one and moved over it, so a reader sees one token or the other and never half of one. The comparison (`ApiToken::matches`) takes the same time wherever the bytes differ, and `ApiToken` has no `==` and no `Debug` output of its bytes. A token goes nowhere but that file and the first message; an error never repeats it.
- **The conversation.** Frames are those of the daemon (`daemon::frame`: a 4-byte length, a limit of 2 MiB checked before anything is read); each payload is one JSON object. The client sends `{"type":"auth","version":1,"token":"…"}`; the server answers `{"type":"welcome","version":1}` and then, for each `{"id":7,"method":"spaces.list","params":{}}`, either `{"id":7,"result":…}` or `{"id":7,"error":{"code":"…","message":"…"}}`. The methods are a closed list, `ApiMethod`: `spaces.list`, `spaces.create`, `items.create`, `splits.create`, `terminal.send`, `terminal.read` and `notify` (NOR-F17-02a). Every field is checked in `api::protocol` before the handler is called (unknown field, wrong type, empty or too long text, a control character in a name, a number out of range, `terminal.send` with neither text nor keys): the handler receives an `ApiCall` and never a raw message, and an invalid message is an error answer and never a panic.
- **What closes the connection.** A first message that is not a good `auth` (a request before the authentication gets `unauthenticated`), a wrong token (`unauthorized`), another version (`unsupported_version`), no message within 5 s (`timeout`), a frame over the limit (`frame_too_large`) or a frame that is not one. In all of those the handler was not called. An invalid request after the authentication (bad JSON, unknown method, extra field, wrong parameters) gets its error and the connection stays open.
- **The server.** `ApiServer::start(endpoint, token, handler, config)` binds, runs on a thread of its own with a current-thread runtime (as `Daemon` does) and returns when the endpoint is ready. Connections run side by side (up to `max_connections`, 32 by default; one more is closed unanswered); one connection serves one request at a time. Each call runs in a task of its own under `request_timeout` (30 s), so a handler that panics, hangs or answers more than a frame can hold fails that request (`internal`, `timeout`) and nothing else. `shutdown()` (or dropping the server) stops accepting, closes every connection and removes the socket.
- **Not verified here (D19).** On Windows the token file keeps the access list it inherits from its folder (the caller should put it under the profile of the user; `load_or_create_token` sets no access list of its own), `crates/noren-core/src/api/token.rs:107`. The pipe and socket restrictions are those of `daemon::ipc`, tested there.

Tests: `crates/noren-core/tests/api.rs` (a real server on a real pipe or socket, a fake handler, a client made of `ipc::connect` and the daemon frames) and the unit tests of `api::protocol`, `api::events` and `api::token`.

### Events on the server

`api::events` (NOR-F17-01e) is how the server pushes to a client what happens in the sessions, with no Tauri and no terminal in it: whoever owns the sessions holds an `EventPublisher` (`ApiServer::publisher()`; cheap to clone, `Send + Sync`, usable from any thread, valid after the server stops and then does nothing) and calls `publish(ApiEvent)`. The app publishes through it since NOR-F17-01f (see "Events through the bridge").

- **A request the server answers itself.** `events.subscribe` is not an `ApiMethod` and the handler never sees it: `protocol::parse_client_request` returns a `ClientRequest`, either a `Call(ApiCall)` or a `Subscribe(EventFilter)`, and `parse_request` (calls only) is unchanged, so the closed list of methods that `@noren/model` holds to the Rust file did not change. The filter is checked like the parameters of a call: `types` (a list of `terminal.output` and `agent.state`, not empty, a kind once; absent means both) and `sessionId` (text of the same kind as the ids of a call, not empty; absent means every session); an unknown type, an empty list, an empty `sessionId` or an extra field is `invalid_params` with the id of the request, the connection stays open and the old subscription (if any) is not touched. The answer is `{ types, sessionId }`, the filter as it now stands.
- **Only the subscribed, only the authenticated.** `Hub` keeps one entry per connection, made when the connection subscribes and removed when its task ends, whatever the way (a `Registration` guard), so a connection that never subscribed has no entry and no event can reach it, and subscribing needs the authentication: before it, any message with `id` or `method` is `unauthenticated` and the connection closes (01a). Subscribing again swaps the entry: the new filter and a new, empty queue, and what the old queue held is not sent.
- **One writer.** After the authentication a connection runs two futures in its task: one reads requests and runs them one at a time (as before), one writes. Only the writer touches the stream for writing, so a frame is never cut by another. It takes the answers from a small channel and the events from the queue of the subscription, answers first (`biased`), so the answers keep the order of the requests and an event may come between a request and its answer. The answer to `events.subscribe` is queued only after the entry is made (an event published once the client has the answer is never missed) and the writer sends it before the first event of the new subscription.
- **A slow client.** Each subscription has a queue of `ApiConfig::event_queue` events (64). `publish` only does `try_send` under a short lock and counts what does not fit; it never waits, so a client that does not read holds back neither the publisher nor any other client (the test floods a client that does not read with 40 MB and another client hears at once). The connection is **not** closed for being slow: when the writer has sent the last queued event it sends `{"event":"events.dropped","data":{"count":N}}` with the number of events left out since the last warning, so the stream says where it has a hole. Events of a slow client are lost; its answers are not (they wait for the client, as before, and a request that is never read is the client's own).
- **The text of the output.** The `text` of `terminal.output` is what the publisher gave. Only the frame limit cuts it: a text longer than `MAX_OUTPUT_CHUNK_BYTES` (256 KiB, which JSON can at most multiply by six, so a piece always fits the 2 MiB frame) is published as several events in order, each ending at a character boundary, so the pieces make the text again. A session id too long to fit makes an event that is counted as missed and not sent.
- **The states.** `agent.state` carries `waiting`, `working` or `idle`, the three words of `AgentState` in `packages/model/src/agent-state.ts` (shown by the list of agents).

### Events through the bridge

`apps/desktop/src-tauri/src/api_events.rs` (NOR-F17-01f) is where the app uses the `EventPublisher`. `ApiState` keeps the publisher of the server it started (`None` when the server did not start, and then nothing below runs).

- **Output.** `bridge::route_session` is the one place where the bytes of every session (a shell in this process, in the daemon, on another machine, or taken over from an earlier run) go to the channel of the page. Right after `OutputRoute::send` handed a chunk to the channel, the same callback gives it to an `OutputEvents` of the session, which turns it into text and publishes `terminal.output`. The page is served first, and publishing never waits (`try_send` under a short lock; with nobody subscribed `push` returns before decoding), so output reaches the page at the same speed with or without a client. The channel is not touched: the page gets the same bytes as before.
- **Text.** `decode_utf8` keeps, per session, the bytes at the end of a chunk that start a character and do not finish it (at most 3) and prepends them to the next chunk, so a character cut between two chunks leaves whole; a byte that cannot belong to any character is U+FFFD (the same as `String::from_utf8_lossy`). With nobody subscribed the rest is dropped, so a client that comes later does not start in the middle of a character.
- **The id.** `sessionId` is `SessionId.0` as text, the string the page stores in `pane.sessionId` (`String(shellId)` in `api-dispatch.ts`). It exists only after the session started, and a fast shell can print before that, so `OutputEvents` holds what came meanwhile (at most 256 KiB) and `bind` publishes it first. Replayed output (a session taken over from the daemon) goes through the same callback and is published too.
- **Agent state.** The page tells changes with the command `api_agent_state(sessionId, state)`, granted to the main window only (capability `allow-api-agent-state`, `require_owner`, checked by a test of `capabilities.rs`). `agent-state-store.ts` calls a reporter set by the app (`setAgentStateReporter`) whenever a tracker changes, a pane loses its agent or its entry is forgotten; `agent-state-report.ts` calls the command only when the state differs from the last one it told for that session (idle until told otherwise), so a repeated state is never sent. The Rust side checks the state (`waiting`, `working`, `idle`) and the id (1 to 128 characters, no control character) and refuses anything else; with no server it accepts and does nothing.
- **Tests.** Real server on a real pipe or socket under a mock app (`api_events::test_support`): the output with the right id, two sessions, a character cut at every byte, output before the id is known, no subscriber, a client that never reads, the command from the main window and refused to other windows and to an invalid state; `route_session` driven with a fake start so the wiring is the real one. `--smoke-api` ends with a client that subscribes, makes a tab and hears the prompt of that shell.

Not verified here (D19): no window was shown; the states `waiting` and `working` of a real agent were not exercised in the app (no agent runs in a smoke), only the reporter of the page with a fake clock and the command with the real server.

### What a call does (`@noren/model`)

`dispatchApiCall(call, host)` (`packages/model/src/api-dispatch.ts`) is the pure side of the API: it takes an `ApiCall`, the request as it travels (`{ method, params }`, with the names, fields and limits of `api::protocol`; a test reads `protocol.rs` and fails if the methods, error codes, limits or parameters of the two drift apart), and gives back `{ result }` or `{ error: { code, message } }` with the same codes as the server (`invalid_params`, `not_found`, `failed`, `internal`...). It never throws or rejects. The call is checked again (`parseApiCall`), because it crosses from Rust to the page as JSON. Everything it touches comes in through `ApiHost`: the workspace (`workspace()`, `dispatch(action)`, `attachSession`), the `Backend` (`createSession`, `write`, `kill`) and a reader of the output (`readLines`, `TerminalTail` is one that strips the control sequences with `TerminalTextStripper`).

- **`spaces.list`** gives every space with its tabs (pinned first, then the tree) and their panes; a terminal is named by its pane id, the same id `items.create` and `splits.create` answer with, and carries its `session` (NOR-F17-02a): the id string the page keeps in `pane.sessionId` and the app publishes as `sessionId` in `terminal.output`, or `null` for a pane with no shell. It changes nothing.
- **`spaces.create`** runs `space/create` with `activate: false`: an automation does not take the view from the person.
- **`items.create`** finds the space (`not_found` before any shell is started; without a `space` in the call it is the destination of the first routing rule that matches, from `ApiHost.routing()` read at every call, else the active space, NOR-F17-03b (the choice is `destinationOfNewTab` of `routing.ts`, which `newTab` of the page's workspace store uses too, NOR-F17-03c), and the tab goes into the group the rule names, with `placement { to: "tree", groupId }`), starts the shell with the profile, folder and environment the call and the space name (the default profile is left to the backend, the git identity becomes the author and committer variables, as the app does) and then runs `item/create` with that session, so the tab shows the shell that is already running. The answer carries `session`, that shell's id as text (`String(shellId)`, the string events publish), so a client can subscribe to its output without watching sessions appear. A shell that does not start is `failed` and the workspace stays as it was; a shell that the workspace did not take (the space went away meanwhile) is ended.
- **`splits.create`** splits the pane in focus of the tab (`right` is a row, `down` a column, the new pane after) and gives the new pane a shell that starts where that pane is. A tab at its most panes is `failed` before a shell is started. The reducer's `pane/split` has no session, so the shell is handed over by `attachSession` in the same tick as the split. The answer carries that shell's `session` as `items.create` does.
- **`terminal.send`** writes `text` as given, then the bytes of `keys` (`keySequence`: `Enter`, `Tab`, `Escape`, `Backspace`, cursor, `Home`, `End`, `PageUp`, `F1`-`F12`, `Ctrl+C`, `Alt+b`, `Shift+Tab`, `Ctrl+Up`...), in one write. It adds nothing: no Enter, so a command runs only when the caller sent the line end (D8). A key name that is not known fails the whole send (`invalid_params`) before anything is written. A terminal id must be the pane of a shell that is running.
- **`terminal.read`** gives the last `lines` lines (1 to 10000, 100 by default) as plain text, oldest first; the answer keeps the newest lines within 1 MiB and says `truncated` when it dropped older ones.
- **`notify`** (NOR-F17-02a) checks the terminal first (`not_found` if the pane is not in the workspace, `failed` if it is not a terminal; the pane need not have a shell) and then hands `{ title, body?, paneId? }` to `ApiHost.notify`, the host's notifier, and answers `{ shown, terminal? }` with what it returned. The call never throws on the notifier: a notifier that is missing, throws or rejects is `shown: false`. In the app the host's notifier is `SystemNotifier.send` (`packages/model/src/notifications.ts`), wired in `apps/desktop/src/api-bridge.ts` with the same `SystemNotifier` the workspace store uses for bells and long commands. `send` is for a notification asked for on purpose: it reads the user's settings at every call (off means nothing reaches the backend), cuts the words as the others are cut (80 and 200 characters), and keeps the repeat guard (same words, same pane, 3 s), but it does not apply the focus rule of `report`, since nobody asked the bell for it. A call without a terminal counts as the pseudo-pane `api` for the guard. The limits (128 characters for the title, 1024 for the body) are those of `protocol.rs`, held to the dispatcher by the same test as the others.

The environment a new shell gets (`spaceSessionEnv`, `packages/model/src/session-env.ts`) is one rule for the interface and for this dispatcher.

Not verified here (D19): no window was opened. One thing is still open: the shell that `items.create` and `splits.create` start is not given the pane id (`CreateSessionOptions.paneId`, which the pane needs to survive the app with `sessions.keepOnClose`) because the pane does not exist yet when the shell must be started.

### The bridge to the main window

`apps/desktop/src-tauri/src/api_bridge.rs` (NOR-F17-01c) starts the server in `setup` and is its `ApiHandler`. The page of the main window runs the call; Rust only carries it.

- **The way there.** `ApiBridge::handle` gives the call an id of its own (a counter, unique in the process), emits the event `api-call` with `{ id, method, params }` to the window `main` and to no other (`emit_to`; a browser pane's web view or another window never hears it), and waits for the answer. With no main window the call fails at once (`failed`). The payload is rebuilt from the `ApiCall` the server validated, and a test reads it back through `parse_call`, so what the page gets is what the server accepted.
- **The way back.** The page answers with the command `api_respond(id, outcome)`, granted to the window `main` only (the capability `default.json`, held by `capabilities.rs`) and refused to any other window by the command itself (`windows::require_owner`). The first answer for an id wins; an id nobody waits for (never given, already answered, already timed out) is dropped without a word, so the page learns nothing about the calls in flight. The outcome must be exactly `{ result }` or `{ error: { code, message } }` with a code of the server's; anything else is an `internal` error.
- **Ready or not (NOR-F17-01d).** The window is up well before the page listens (the page still restores its shells and its settings), and an event sent to a page that has not registered its listener is lost. So the bridge starts _not ready_: a call that comes before the page said it listens is answered `failed` at once ("Noren is still starting: its window is not ready for API calls yet, try again in a moment", `STARTING_MESSAGE`), with nothing sent and nothing waiting, instead of waiting out the deadline. The page says it with the command `api_ready()` (main window only, like `api_respond`: the capability plus `require_owner`) once its `api-call` listener is registered, and not before. A page that starts loading again (`on_page_load` of the main window) makes the bridge not ready until it says so; a call already in flight can still be answered.
- **The deadline.** The bridge waits for the page `request_timeout` less 5 s (25 s by default), so the caller gets `timeout` from the bridge ("the window did not answer in time") and not the bare one of the server. A call the server drops (its own limit, shutdown) leaves nothing waiting.
- **The page.** `apps/desktop/src/api-bridge.ts` (`startLocalApi`, started by `boot.ts` only inside Tauri) hears the event, runs `dispatchApiCall` over the real workspace store, the backend and the tail, and calls `api_respond`. Calls run side by side; a run that rejects is answered as `internal`; an event with no usable id is dropped (the Rust side times that call out). A plain browser (web mode, e2e) starts nothing.
- **The output.** `TauriBackend` takes a `TerminalTail` (the main window gives it) and feeds it with everything every session prints, through `OutputStream.tap`: a tap hears what is held and what comes without being "the first subscriber", so the terminal view still gets the held output. A session that ends (exit or `kill`) is forgotten and takes nothing more.
- **Where the token is.** In a normal start, `<data folder of the app>/api/token` (on Windows `%APPDATA%\io.github.marllon.noren\api\token`), inside the profile of the user, the folder the state and the settings already live in; it inherits the access list of the profile, which is the user's own. A smoke run uses an endpoint named for the run (the name of its daemon: `api-smoke-<pid>-<time>`) and a token in a folder of its own in the temp folder, removed when the run ends, so it never meets the API of a Noren the user has open. The plain `--smoke` run checks that the server is listening on that endpoint (`SMOKE API listening on …`).
- **A server that cannot start** (the endpoint is taken, the token file cannot be written) is a line on stderr and an app without the API; it never stops the app. The bridge and the command are there either way.

Not verified here (D19): the event reaching a real web view and the page answering through the real IPC were not run with a window (the mock runtime tests the command, the window rule and the event routing; the page tests use a fake bridge); a call made by a real client to a running app is the `--smoke-api` below.

### The command line (`noren-cli`)

`crates/noren-cli` (NOR-F17-02b) is a console program with no Tauri in it: `noren-core` plus `serde_json` and a current-thread `tokio` runtime, no new crate. It is made of two layers.

- **The client, in `noren-core`** (`api::client`): `ApiClient::connect(&ApiTarget)` reads the token file **at every connect** (`read_token`, which never writes: a client must not make a token the server does not know), connects with `daemon::ipc`, sends the `auth` and waits for the `welcome`; `call(ApiMethod, params)` sends one request with a counter id and returns the `result`, skipping any event frame, or a `ClientError`. The errors tell the cases apart: `NotRunning` (the endpoint does not exist or refuses), `TokenMissing(path)`, `TokenUnusable`, `Api { code, message }` (the server's own error, `unauthorized` included) and so on; `is_unreachable()` is what the command turns into exit 3. `ApiTarget::standard()` is `api-default` and `default_token_file()`; `ApiTarget::named(name, token_file)` is for tests. The data folder is the one Tauri gives the app for its identifier, worked out without Tauri from `%APPDATA%`, `~/Library/Application Support` or `$XDG_DATA_HOME`/`~/.local/share` (`app_data_dir`), and a test keeps `APP_IDENTIFIER` equal to `identifier` in `tauri.conf.json`. `token_file_in(data_dir)` (`<data>/api/token`) is the one rule: the app (`api_bridge.rs`, `ApiSettings::normal` and `for_run`) and the client both call it.
- **The command** (`args.rs`, `run.rs`). Arguments are parsed by hand (a dozen options; a parser crate would be a dependency for nothing). The line is checked before any connection (a bad line is exit 2 and never reaches Noren). `--cwd` is made absolute against the folder the command runs in (`std::path::absolute`, which needs no existing folder and, on Windows, does not add the `\\?\` prefix `canonicalize` would). `new-tab --space` is an id first, then a name; a name two spaces share is refused and lists the ids, an unknown one lists the spaces, and in both cases no tab is made. `send` copies `--text` and `--key` into `terminal.send` untouched: there is no code anywhere that adds a line break or an Enter (D8), and a test with the real binary checks the call the handler sees. The result is printed with `serde_json` on one line; messages for a person go to standard error with the exit code (0 done, 1 Noren said no, 2 usage, 3 not reachable).
- **Why `noren-cli` and not `noren`.** The app package already produces `noren`/`noren.exe` in the same `target` folder (a second binary of that name would collide), and the release `noren.exe` is built for the Windows GUI subsystem (`apps/desktop/src-tauri/src/main.rs:2`), which has no console, so a command line could not be that file. The `noren` alias belongs to the packages (NOR-F20-03).

Tests: `crates/noren-cli/tests/cli.rs` runs the real binary as a process against a real `ApiServer` (own endpoint name and token folder per test) with a fake handler that records the calls: each command makes the right method and parameters and prints the result as one JSON line; an error of the API is exit 1; a wrong token is exit 3 and the handler is never reached; a missing or damaged token file, no server, every kind of wrong line (exit 2, nothing sent), `send` with no Enter added, `--space` by name, options over the environment, and the token found in the data folder of the app (the environment of the child points `APPDATA`, `XDG_DATA_HOME` and `HOME` at a test folder). Unit tests cover the argument parser, the space lookup and the data folder rules.

Not verified here (D19): no window was opened and no real Noren was driven by the command; the command was tested against the real server with a fake handler, and the real handler is the `--smoke-api` of the app, which does not run `noren-cli`. The default data folder was checked by its rule and by a test that points the environment at a test folder, not by a run next to an app a person had open.

### The smoke run of the API

`noren --smoke-api` (`smoke_api.rs`, NOR-F17-01d, run by `pnpm smoke`) is a client of the API against the real app, with its main window hidden (D19). The app starts as in every smoke mode (an endpoint and a token folder named for the run, a session daemon of its own) and keeps its files in a folder of its own, because the page saves the space the run makes. Once the page says `app-ready`, the run reads the token file (it must be the one the server made: `Reused`, never created by the client), connects to the endpoint with `noren_core::daemon::ipc` and the frames of the API, and checks: a wrong token is `unauthorized` and the connection closes; the right one is welcomed; `spaces.list` is answered by the page (a call told "still starting" is tried again every 100 ms, and the run prints how many were); `spaces.create` makes a space with the name asked; a second `spaces.list` has one space more, the new one among them. The second connection (the events one) takes the `session` that `items.create` answers instead of watching the daemon for a new session, requires `spaces.list` to give the same session to that terminal, and calls `notify` (NOR-F17-02a): the settings file in the folder of the run turns the notifications off, so the call must be answered `shown: false` and nothing is shown on the desktop of whoever runs the check (that a notification is shown when the settings allow it is covered by the unit tests, not by the run). Then the window is still hidden, no global shortcut or tray icon exists, the shell the page started runs in the daemon of the run, and the daemon stops with code 0. Any failure is `SMOKE FAILED: ...` and exit code 1; the run is cut at 50 s. No call types into a terminal, so no Enter is sent (D8). The contract a client sees is in [API.md](API.md).

## Plugins

Plugins are small JavaScript programs that add things to Noren without being part of it. They run apart from the page, with no power of their own: everything they can do is a request that the app answers after checking the permissions the plugin declared. This part of the design is the pure core, `packages/model/src/plugins.ts` (NOR-F18-01a), the loading of the `plugins/` folder (NOR-F18-01b) the host that runs each plugin in a Worker and shows its palette actions (NOR-F18-01c) and the plugin's own panel in a frame (NOR-F18-01d). The reference for people who write plugins is `docs/PLUGINS.md`.

- **The manifest** (`plugin.json`, `pluginManifestSchema`, `parsePluginManifest`): `id` (`a-z`, `0-9` and `-`, up to 32 characters), `name`, `version` (three numbers, like `1.2.0`), `apiVersion` (only `1` exists), `main` (the plugin's script, a path inside its folder: relative, no `..` segment, no drive, no leading slash or backslash, either separator) and `permissions`, a list without repeats of `terminal.read`, `tabs.create`, `palette.actions` and `panel`. A field that is not in the list is an error; the errors come back as one text each, starting with the path of the field (`permissions.2: ...`). A plugin that asks for nothing is valid and can do nothing.
- **The messages (protocol v1).** A request is `{ version: 1, id, method, params? }` with `id` text of 1 to 64 characters or a whole number; the answer is `{ version: 1, id, result }` or `{ version: 1, id, error: { code, message, permission? } }` with the same `id`, or `null` when the request had none that could be read. The error codes are those of the local API (`invalid_request`, `unsupported_version`, `unknown_method`, `invalid_params`, `not_found`, `failed`, `internal`) plus `permission_denied`, which carries the permission that was missing.
- **The broker** (`createPluginBroker(manifest, host)`, one per plugin) answers `handle(request)`, which never throws or rejects, and checks in this order, stopping at the first problem: the request is an object with a usable `id` (`invalid_request`); the `version` is 1 (`unsupported_version`, looked at before the other fields because a later version may add some); no field but `version`, `id`, `method` and `params`; the method is one of the four below (`unknown_method`: the other methods of the local API are not reachable); the manifest holds the permission of the method (`permission_denied`; nothing else is read, so the host is untouched and the parameters are not even looked at); the parameters fit (`invalid_params`).
- **The methods.** `terminal.read` (needs `terminal.read`) and `tabs.create` (needs `tabs.create`) go on to `dispatchApiCall` as `terminal.read` and `items.create`, over the `ApiHost` the app lent, so they have the limits, the routing rules and the errors of the local API. `palette.register` (`palette.actions`; `{ id, label }`, the id of `a-z`, `0-9`, `.`, `_` and `-`, at most 64 actions per plugin, the same id again changes the label) and `panel.open` (`panel`; `{ title, html? }`, the content up to `PLUGIN_LIMITS.panelHtmlChars` = 20,000 characters, kept as it came) are not done by the broker: it keeps them in the registry of the plugin (`broker.registry.actions()`, `broker.registry.panel()`, copies), which the host reads to show the action in the palette and to open the panel. The registry belongs to the broker, so two plugins never see each other's.
- **Loading the folder (NOR-F18-01b).** `noren-core::plugins` (`plugins.rs`, no Tauri, no watching) lists `plugins/` next to `config.jsonc` with `PluginStore::list`: one `PluginFolder` per folder, by name, with the text of `plugin.json` and of the file its `main` names exactly as they are, or a short sentence about why the folder is not a plugin (`plugin.json not found`, `plugin.json is not valid JSON`, `plugin.json has no main`, `main must not use ..`, `main file not found`, `main file is outside the plugin folder`, `plugin.json is larger than 256 KiB`, `main file is not UTF-8 text`). `main` must be a relative path: no `..` (checked on `/` and `\` both), no leading `/` or `\`, no `:` (so no drive and no stream of a file), no control character and no device name of Windows (`con`, `aux`, ...) in any part; and, after every link is followed (`canonicalize`), the file must still be inside the canonical folder of the plugin, so a link out of the folder is refused, for `main` and for `plugin.json` alike. Each file is at most 256 KiB (`MAX_PLUGIN_FILE_BYTES`, read one byte past the limit so a file that grows is caught), a file in `plugins/` and a name starting with a dot are left out, at most 50 folders (`MAX_PLUGINS`) are listed, and a folder that does not exist is no plugins and is never made. One bad folder does not hide the others. The Tauri command `plugins_list` (a read off the thread that answers the page; the store is only managed, never watched, also in the smoke runs) hands the list to `Backend.listPlugins`, which `FakeBackend` answers with the example plugin (`FAKE_PLUGINS`) or what `setPlugins` says (and `setPluginsListFailure`), and the web backend inherits.

- **Checking what was loaded.** `checkPluginFolders` (`plugins-load.ts`, pure) takes the list and answers `{ valid, invalid }`, both in the order they came: a folder the backend could not read is invalid with its sentence; the rest must hold JSON (a leading byte order mark is allowed) that `parsePluginManifest` accepts and whose `id` is the name of the folder, else it is invalid with the reason. A valid entry is `{ folder, manifest, main }` with the source text of the main file. The example is `examples/plugins/new-tab-action/` (`palette.actions` and `tabs.create`); `plugins-example.ts` holds the same text for `FakeBackend`, and a test holds the two to each other.

- **Running the plugins (NOR-F18-01c).** `apps/desktop/src/plugin-host.ts` (`PluginHost`) is started once from `boot.ts` (`startPlugins`, not awaited, after the store exists), lists the folder through `Backend.listPlugins`, sorts it with `checkPluginFolders` and, for each valid plugin, makes a `createPluginBroker(manifest, appApiHost(...))` (the same `ApiHost` the local API runs on, so `tabs.create` and `terminal.read` have its limits and its routing rules) and a classic Worker from a `blob:` address that holds the text of `main` (the address is revoked once the Worker has spoken, failed or ended). What the Worker posts goes to `broker.handle` of its own plugin and the answer is posted back to it; the Worker has no other way to reach the app and is given nothing of Tauri. `worker-src blob:` in the CSP is the one door; `docs/SECURITY_REVIEW.md` section 1 tells why nothing else opens. The host keeps a status per folder (`running`, `failed` with the reason, `invalid` with the reason): an invalid plugin, a Worker that cannot start, one that raises an error or one that cannot be posted to is recorded and ended, its actions leave the palette, and the others go on; no dialog is shown. The registry of a broker does not say when it changes, so the host looks at the actions after each answer and tells its subscribers (`subscribe`, `version`) only when the list or a status changed; the palette reads them with `usePluginActions` and builds one `plugin` entry per action (kind `plugin`, listed under `Plugins`, the label of the action as the title and `Plugin · <name>` as the detail, searched with no prefix and under `>`). Choosing an entry posts `{ event: "action", id }` to that plugin (only for an action it registered), which is the message `examples/plugins/new-tab-action/main.js` waits for. In the web build `FakeBackend.setPlugins` is seeded from `localStorage` (`noren.web.plugins`, `WebBackend`) and the test hook shows what each side said (`pluginTraffic`, `pluginStatus`), which is how `e2e/plugins.spec.ts` sees the answer a plugin got. jsdom has no Worker, so `plugin-host.test.ts` uses a stand-in and the real Worker is proved by the Playwright tests, also under the policy of the app (`e2e/csp.spec.ts`).
- **The panel (NOR-F18-01d).** When `panel.open` is answered with a result, `PluginHost` takes `broker.registry.panel()` as the one panel on screen (`panel()`, `closePanel()`; the last one opened wins; a request the broker refused, such as `permission_denied`, leaves it as it was). It is taken away when the person closes it, when its plugin fails or when the host stops. `PluginPanel.tsx` (`usePluginPanel`) draws it as a side panel next to the Ask panel: the title, `Plugin · <name>`, a close button (Escape too) and one `iframe` with `sandbox=""` and `srcDoc={panelDocument(html)}`, the only iframe the page makes (`security-config.test.ts` lists the file). `plugin-panel.ts` wraps the content in a page whose first element is a `<meta>` policy, `default-src 'none'; style-src 'unsafe-inline'`. The frame has an opaque origin, no scripts, no forms and no windows, and the content cannot reach the app or the network; the CSP of the app did not change (`frame-src` stays `'none'`, a `srcdoc` frame needs no source). The consequence is that the panel is static: a plugin redraws it by calling `panel.open` again (finding 277). jsdom has no frame, so `PluginPanel.test.tsx` checks the markup and `e2e/plugin-panel.spec.ts` and `e2e/csp.spec.ts` prove the frame, its opaque origin and what it cannot do in Chromium.
- **What is not here.** A panel with scripts or a way for it to talk to the broker (finding 277). The host puts no limit on the size or the rate of a message or on a plugin that never answers (finding 276), and whether a Worker can reach the IPC that the policy names was not tried in a real window (finding 275). D8 holds: `tabs.create` starts a shell and writes nothing into it, and there is no plugin method that types.

Not verified here (D19): a Worker made from a `blob:` address, and a `srcdoc` frame under `frame-src 'none'`, in the real WebView2 window (only the web build on Chromium ran them); that the real `plugins_list` reads the `plugins` folder of the app config folder on a real window (the Tauri command, `bridge.rs`) was not seen either, only the folder logic in `cargo test` and the smoke run.

## The gallery

The gallery is a list of themes and mods that other people made, published as one JSON file in a public repository (`noren-gallery`, made apart from this code; the address is `DEFAULT_INDEX_URL` in `crates/noren-core/src/gallery.rs`). This part of the design is the core (NOR-F18-02a): reading the index, downloading an item, checking its hash and installing it. The screen that shows the gallery comes in NOR-F18-02b.

- **The index** (`galleryIndexSchema`, `parseGalleryIndex` in `packages/model/src/gallery.ts`, and `parse_index` in `noren-core`, which applies the same rules): `{ "version": 1, "items": [...] }`, no other field. An item is `{ id, kind, name, version, url, sha256, size }`: `id` is a theme id (lower case words joined by hyphens, up to 64 characters, no device name of Windows), so it is a safe file name for both kinds and never a path; `kind` is `theme` or `mod`; `name` up to 60 characters; `version` three numbers with an optional `-pre` or `+build` suffix; `url` an `https` address with no user name; `sha256` 64 lower case hexadecimal digits; `size` a whole number from 1 to 256 KiB (the size of a theme file and of a mod file). An id listed twice is an error, whatever the kind, and so are more than 500 items.
- **Comparing with what is installed** (`compareWithInstalled`, pure) matches by kind and id and answers, in the order of the index, `new` (not installed), `update` (the index has a newer version) or `current` (the same, or a newer one installed). An installed item that left the index has no entry.
- **Downloading** (`Gallery` in `gallery.rs`): `reqwest` with the system TLS (already in the tree for the AI client), `https` only outside the tests, one deadline of 30 seconds for the whole request, no redirect followed (a redirect could leave `https`), and never more bytes than the ceiling it was given: 512 KiB for the index, and for an item the `size` the index declares for it (a longer body stops the read at once, and so does a `Content-Length` over the ceiling). The tests serve the index and the files from a `TcpListener` on `127.0.0.1`; none touches the network.
- **Installing** (`Gallery::install(id)`, the Tauri command `gallery_install`): it downloads the index again (so the address and the hash are the ones of the index now, not what the page remembers), finds the item, downloads its file, and only when the sha256 of the bytes (`sha2`, MIT OR Apache-2.0, already in the tree through Tauri) is the declared one, and the bytes are UTF-8 text, and a theme is a JSON object whose `id`, if it has one, is the id of the item, saves it: a theme with `ThemeStore::save` as `themes/<id>.json`, a mod with the new `ModStore::save` as `mods/<id>.css` (the same name and size rules as listing, atomic write). Any failure before the save writes nothing, the record included; a wrong hash is `HashMismatch` and leaves the version that was installed as it was. A running watch of `mods/` reports the new mod like a file put there by hand.
- **The record** is `gallery.json` next to `config.jsonc`: `{ "version": 1, "installed": [{ id, kind, version, sha256 }] }`, one entry per kind and id, in the order of the first installation, replaced on an update. A missing or unreadable record reads as empty (the files are intact, and installing again brings the record back).
- **The commands** `gallery_index` (the text of the index as served, after `noren-core` checked it), `gallery_installed` and `gallery_install` are in the four places a command lives (`bridge.rs`, `main.rs`, `build.rs`, `capabilities/default.json`) and reach the interface as `Backend.galleryIndex` (checked again with `parseGalleryIndex`), `Backend.galleryInstalled` and `Backend.galleryInstall`. `FakeBackend` serves a fixture gallery (`FAKE_GALLERY_INDEX`: two themes, a mod, and a theme whose declared hash is not the hash of its file), `setGalleryIndex(index, downloads)` serves another, and the web backend can be seeded under `noren.web.gallery`. The smoke run reads nothing from the gallery and installs nothing (`GalleryState::without_installing`).
- **The screen** (NOR-F18-02b) is the Gallery section of the settings screen, between Mods and Import (`GalleryPanel.tsx`, drawn by `SettingsDialog.tsx`; the rows are `galleryRows` in `settings-gallery.ts`, pure and tested). It reads `Backend.galleryIndex` and `Backend.galleryInstalled` when the screen opens and sets them against each other with `compareWithInstalled`: a new item has an Install button, one the index has a newer version of has Update, one that is up to date has none, and each row shows the version of the index and the version installed. While the index loads, or when it cannot be loaded, a line with `role="status"` says so. A click calls `Backend.galleryInstall`; a download or a hash that fails is said on the row of the item (`role="status"`) and the row stays as it was. After an install the panel reads `galleryInstalled` again and refreshes what the app uses the way the existing flows do: the themes (`listUserThemes` through `parseUserThemes` into `setUserThemes`, as an import does) or the mods (`listMods` into `setModFiles`, which the watcher also feeds). The core installs a theme once its hash matches, without reading what is in it (finding 279), so after installing a theme the panel holds the file to the whole schema (`installedThemeProblem`: `parseTheme`, and the ids of the built-in themes) and, when it is not a usable theme, says why on the row; the file stays in the themes folder and stays out of the list, as with any file placed there by hand. The web build takes an optional `installed` list in the `noren.web.gallery` seed, next to `index` and `downloads`, so a test can start with an item already installed.
- **What is not here.** A gallery other than the official one, and a signature on the index: the hash proves the file is the one the index names, and the index is trusted because it is fetched over `https` from the repository of the project.

Not verified here (D19): the real `gallery_index` and `gallery_install` against the official address from a real window (the repository does not exist yet, NOR-F21-08), and the TLS handshake of the system stack with a real server (`bridge.rs` `gallery_index`); `cargo test` runs the whole path against a local `http` server.

## The file of a space

A space can be written to a file, `.noren-space.json`, and read back as a new space, to send it to someone or keep it in a repository. The pure core is in `packages/model/src/space-file.ts` (NOR-F18-03a); the palette commands "Export space" and "Import space..." (NOR-F18-03b) are the interface around it, described last in this section.

- **The format** (`SpaceFileSchema`): `{ "format": "noren-space", "version": 1, "space": {...}, "profiles": [...] }`, and no other field anywhere (a field the format does not have is an error, with its path). `space` has the name, icon, color, theme, mods (mod file names, no repeats), the AI and scrollback switches, the defaults (profile, folder, environment, git identity), `pinned` (ids of items), `tree` (items by id, and groups; a live group keeps its source), `items` (a list: each tab has `id`, the `title` if the user locked one, `focusedPaneId`, `origin`, `liveKey` and its `layout`, whose splits keep their sizes and whose panes have `id`, `type`, `profileId`, `cwd`, `url` and `path`) and `activeItemId`. Left out, because they only mean something on this run or on this computer: sessions, the running command, the last command, the scrollback and its file, the git branch, the unread and bell marks, when a tab was last used, the zoomed pane, the picture behind the terminals (a path of this computer), and a title a program asked for.
- **Ids in the file are its own.** `exportSpace` numbers the items `i1`, the groups `g1` and the panes `p1` in the order it meets them (pinned first, then the tree), so a file never carries the ids of the workspace it came from, and exporting a space that was imported gives the same text.
- **Secrets stay out.** An environment variable of the space is left out when its name says token, secret, password, API key, access key, private key or credential, or when `redactSecrets` changes its value (or `NAME=value`); the names left out are listed in `removed.env`. The command an origin returns to is dropped the same way when it holds a secret (`removed.commands`, by tab id), a profile whose program or arguments hold one is not put in the file (`removed.profiles`), and a page address that holds a secret makes the export fail, since a page cannot be left out of its tab. A profile of the user has no environment of its own today, so there is none to strip there. The profiles in the file are those the space uses (its default, a pane, an origin) among the ones `exportSpace` is given; a shell of the machine is only named by its id.
- **Reading a file** (`parseSpaceFile(text)`, `validateSpaceFile(value)`): both answer `{ ok: true, file }` or `{ ok: false, error }` with a short sentence, and never throw. A text over 1 MiB, one that is not JSON, or whose brackets nest deeper than 64 is refused first. Then come the `format` and `version` (a version this build does not read is named), the schema, an id used twice anywhere (items, groups and panes share one namespace, as in the workspace), the profiles (`profilesProblem`, the rules of the settings file) and the structure of the space under `checkInvariants` itself, run on a workspace made of that one space: split sizes, the focused pane, the page and path of browser, preview and diff panes, every item placed once, groups two levels deep, live sources, at most `maxPanes` panes to a tab. The reason is the message of the first violation.
- **Importing** is the action `space/import` (`{ file, activate? }`). The reducer checks the file again with `spaceFromFile` and the `maxPanes` of the context, makes the space with a fresh id for the space and for every item, group and pane (drawn from the pool that skips the ids the workspace already has; the same id of the file always gets the same new id, so the references hold), dates every tab with the clock, starts every pane idle with no session, and adds the space at the end. It becomes the active space unless `activate` is `false`. A file that is not valid, or has a tab over the limit, changes nothing. A space with tabs and no `activeItemId` gets its first tab, as any space does.
- **Profiles** (`planProfiles(file, existing, takenIds)`) are not part of the workspace. For each profile of the file: one you already have with the same id and the same content is `reused`; one with the same id and other content is a `conflict` of reason `different` (yours is never replaced, and the space keeps using the profile of that id); an id that is a shell of the machine is a `conflict` of reason `taken`; anything else is `add`. A profile is compared by value, with the kind `shell` implied.
- **Tests** (`space-file.test.ts`): the round trip (export, parse, import, export again gives the same text, with the ids of the workspace offered first to the reducer so that every one collides) on generated workspaces with every kind of pane; seeded secrets (by name, by value, in an origin command, in profile arguments, in a page address) never in the text; refused files (version, extra field, id used twice, broken layout, missing or unplaced items, too many panes, too deep, too big); and `space/import` in the property test of the reducer, which checks that it adds exactly one space with ids nobody had and that exporting it gives the file again.
- **The palette commands** (NOR-F18-03b, `apps/desktop/src/space-file-io.ts`, wired in `App.tsx`; no new `Backend` method and no Rust). _Export space_ runs `exportSpace` on the active space with the profiles of `config.jsonc`, and hands the text to the system as a download: a Blob behind an anchor with the `download` attribute (`download-text.ts`), named after the space (`exportFileName`: what a file name cannot hold becomes `-`, a Windows reserved name or an empty name becomes `space`) plus `.noren-space.json`. The notice names what the export left out (variables, tab return commands, profiles); a failed export (a page address with a secret) is a notice and no download. _Import space..._ clicks a hidden `input type="file"` (`data-nr-part="space-file"`, like the color scheme one); `readSpaceFile` refuses a file over 1 MiB, reads it, runs `parseSpaceFile` and `planProfiles` against the profiles of the user and every id the window knows (`takenProfileIds`), and a file that is not a space file is a notice with the short reason and changes nothing. `commitSpaceImport` then appends `plan.add` to `profiles` in `config.jsonc` with `settings.update([{ path: ["profiles"], append }])` (comments stay), waits for the backend to take the profiles (so the first pane can start one at once), and only then dispatches `space/import`; if the settings cannot be written nothing is imported. Reused profiles are not written again, and the ones in conflict are named in the notice ("the space keeps using the profile with that id"). The e2e (`e2e/space-file.spec.ts`) captures the download, imports the same file back and checks the new ids, the profiles written to the file and the refused files.

## Sync through git

The settings of one computer can travel to another through a git repository the person owns (NOR-F19-01). This part of the design is the core (NOR-F19-01a): the module `crates/noren-core/src/sync.rs`, the commands and the `Backend` methods. The settings section and the palette commands (NOR-F19-01b) and the spaces in the sync (NOR-F19-01c) and the push on close (NOR-F19-01d) are described last.

- **A clone next to the config.** `SyncRepo` keeps a clone of the remote in `sync/` inside the config folder. The config folder is not a repository: files are copied between the two, and the copy is limited by a closed list (`is_syncable`, mirrored by `isSyncablePath` in `packages/model/src/sync.ts`): `config.jsonc`, `themes/<id>.json`, `mods/<name>.css` and `spaces/<name>.noren-space.json`. Nothing else is copied in (`state.json`, the scrollback, `gallery.json`, `plugins/`, a stray file, a dotfile), and nothing else is copied out of the clone, whatever the repository holds. API keys live in the keychain, not in these files. A file larger than 1 MiB is refused (`FileTooLarge`) before anything is copied, and more than 500 files is `TooManyFiles`.
- **Running git.** The `git` of the system, through the existing `GitCli` (`worktree.rs`: the program is replaceable, `GIT_TERMINAL_PROMPT=0`, no window on Windows, no input), with `GCM_INTERACTIVE=never`, `LC_ALL=C` and `GIT_ALLOW_PROTOCOL=https:ssh:file`. Separate arguments, never a shell; the address comes after `--`. Every command carries settings that make it independent of the person's git config: no line-ending conversion, no hooks, no file monitor, symbolic links as plain files, no signing, and a commit identity of its own (`Noren sync <sync@noren.invalid>`). One deadline for the whole command (120 s) and a ceiling on what it prints (1 MiB, 64 KiB of error text), as in `git_diff.rs`. A missing `git` is `GitMissing`, with a sentence that says to install it.
- **The address of the remote** (`validate_remote_url`, `syncRemoteProblem`): `https://host/path` with no user name, `ssh://[user@]host/path`, `file:///path`, `[user@]host:path` or a full local path. Refused: a password anywhere, a user name in an `https` address (it would stay in the clone in plain text), a value that starts with `-`, a helper transport (`ext::`, `fd::` and every `name::`), plain `http`, any other scheme, a space or control character. The check runs before git starts. Credentials come from the credential manager of git, never from the address.
- **Connect** clones the remote into `sync/` (an empty repository is fine) or, if a clone exists, points it at the new address. It copies nothing into the config folder.
- **Push** copies the allowed files of the config folder into the clone, commits what changed, and pushes. A remote with commits this clone does not have refuses the push (`Rejected`, "pull first"). Two cases would replace the remote's files without any merge to see it, so push refuses them too: a clone with no commit when the remote has a branch by now, and a first push from a computer that never pulled when one of its files differs from the remote's.
- **Pull** commits the local state the same way first (so a local edit is one side of the merge and never lost), fetches, and merges. On a conflict the merge is aborted (`merge --abort`), nothing is written to the config folder, and the paths in conflict come back (`PullOutcome::Conflicts`); the clone is back where it was, with no marker in a file. Only a clean merge delivers files: the allowed ones that changed since the last delivery (the ref `refs/noren/applied` in the clone; every file of the first pull) and that differ from the config folder, each written through a temporary file and a rename. A computer that never pulled and has a file that differs from the remote's gets a conflict on that path instead of a silent replacement.
- **Nothing is deleted.** A file removed on one side is not removed on the other, and a pull never removes a file of the config folder. Deletions do not travel in this version.
- **Status** needs no network: whether a clone exists, its remote and branch, the files of the config folder the clone does not hold yet (added or modified), and how far ahead and behind the remote the clone is as of the last fetch.
- **The commands** `sync_status`, `sync_connect`, `sync_pull` and `sync_push` are in the four places a command lives and reach the interface as `Backend.syncStatus`, `syncConnect`, `syncPull` and `syncPush`. The answers are JSON the model checks with zod (`syncStatusSchema`, `syncPullSchema`, `syncPushSchema`; a path that is not on the list is refused in the answer too). `SyncState` takes one step at a time; the smoke run can read the status and refuses to connect, pull and push (`without_syncing`). `FakeBackend` keeps a remote in memory and merges by file against the last state both sides agreed on, so a test can make a conflict with `setSyncLocalFile` and `setSyncRemoteFile`, and `setSyncFailure` stands for a missing git. The web backend is the fake one.
- **The screen** (NOR-F19-01b, no Rust and no new `Backend` method). The **Sync** section of the settings screen (`SyncPanel.tsx`, like the gallery one) holds the address of the remote, Connect, Pull and Push, the status and the files a push would carry, and one `status` region for the answer of the last step. The words and the checks are pure (`settings-sync.ts`): `checkRemote` trims the address and runs `syncRemoteProblem` before `syncConnect` is called, so a refused address shows its reason and connects nothing; `statusText` says not connected, up to date, N files to send, saved here and not sent, or that the remote has changes to pull; `pullMessage` says nothing came, the files written, or (a warning) the paths in conflict with the sentence that nothing changed on this computer; `pushMessage` the files sent. A failure of the backend is shown with its own text (`Could not pull: <text>`). Connecting also tells the person that all of `config.jsonc` travels (nothing secret should be in it) and that the app cannot ask for a password or an ssh passphrase, so git must already work with the remote in a terminal. `sync-run.ts` runs a pull or a push and never rejects; after a pull that wrote themes it reads `listUserThemes` again and sets the list (nothing watches `themes/`), and the mods the same way (the folder is watched too, a list equal to the one held changes nothing). `config.jsonc` needs no call: the config manager watches the file, so a pulled config reaches the app as an edit by another program does. The palette commands _Pull settings_ and _Push settings_ (`sync.pull` and `sync.push`, kinds `sync-pull` and `sync-push`, category General) read the status first: with no remote the notice says to connect one in Settings, in the Sync section; otherwise they run `runPull` or `runPush` and the notice is the sentence. One command runs at a time. In the web build `WebBackend.syncPull` also writes the files a pull delivers into the stores the app reads (the config text, the theme files, the mod files), and the seed `noren.web.sync` (`{ localFiles, remoteFiles, failure }`) sets what this computer and the remote hold. `e2e/settings-sync.spec.ts` covers connecting, a refused address, a push, a pull (themes in use at once, the config read by the settings screen), a conflict (config untouched), a failure of git and the two commands.
- **Spaces in the sync** (NOR-F19-01c). A space travels as `spaces/<name>.noren-space.json`, one file per space made by `exportSpace` (see [The file of a space](#the-file-of-a-space)), so it carries no session, no scrollback and no secret that looked like one.
  - _The files_ (`noren-core/src/sync_spaces.rs`, `SpaceFiles`) list, read and write the files of `spaces/` in the config folder. Only names `is_syncable` accepts get in (a name with a folder, a dot in front, a device name or another ending is `NotSyncable`), a file may hold 1 MiB and there may be 500 of them; a batch with one refused name, size or id writes nothing, and a file that already holds the same bytes is not touched. The listing gives each file's sha256 and also the names the clone holds, so a new file does not take a name the remote already has.
  - _The record_ `sync-spaces.json` sits next to `config.jsonc` and says, for each file name, which space (by id) the file stands for and the sha256 of the file when it was tied to it. It is local to the computer (space ids mean nothing on another one) and is not on the closed list, so it never reaches the clone or the remote; a test pushes with it present and pulls on a second computer. A record that cannot be read is an error and not an empty record, because an empty one would make every file a second space. Entries of files that are gone are dropped when it is saved.
  - _The commands_ `sync_spaces_list`, `sync_spaces_read`, `sync_spaces_write` and `sync_spaces_link` (the four places a command lives) reach the interface as `Backend.syncSpaceFiles`, `syncReadSpaceFile`, `syncWriteSpaceFiles` and `syncLinkSpaceFiles`; the answer is checked with `syncSpaceFolderSchema` and the batch to write with `syncSpaceWriteProblem` before it is sent. `SyncState` takes the same turn as a pull or a push, and the smoke run can list and read but refuses to write and link. `FakeBackend` keeps the files with the other local files of the sync (so a push carries them) and the record in a map, with the same sha256 (`sha256.ts`).
  - _Push_ first writes the spaces (`planSpacePush` in `sync-spaces.ts`, run by `space-sync.ts`): a space that has a file keeps its name, even when it is renamed (the file changes, not its name); a space without one gets `exportFileName` of its name, with `-2`, `-3`... when the name (compared without case) is taken by a file in the folder or in the clone. `exportFileName` never returns a name the sync would skip (no leading dot, no device name, no control character), and the plan checks each name with `isSyncablePath` anyway. A space that cannot be exported (a page address holding a secret) or whose file would pass 1 MiB is not written and is named in the answer, and the others go; what an export left out because it looked like a secret is named too. A space whose file says the same, apart from where you were looking, is not written again (see below).
  - _Pull_ first writes the spaces that already have a file (so what was changed here is one side of the merge; a space with no file yet is left out, so the first pull on a new computer cannot clash with a space of the same name on the remote), pulls, and, unless the pull conflicted, looks at every file in `spaces/`: a file the record ties to a space with the same sha256 is nothing to do; a file with no link becomes a new space (`space/import` with `activate: false`: the pull does not take the person to it); a file the record knows whose bytes changed makes the linked space again in its place (`space/reimport`); a file that is not a valid space file is skipped with the reason (`parseSpaceFile`) and looked at again by the next pull. Every space made is tied to its file (`syncLinkSpaceFiles`), so the next pull does not make it twice, and a space this computer exported is already tied, so it does not come back as a second one. The profiles a file counts on are written to `config.jsonc` the way Import space does it, after `config.jsonc` is read again.
  - _`space/reimport`_ (`{ spaceId, file }`) is the action a changed file needs: the space keeps its id, its place in the list, whether it is the active one, the window that shows it and its picture, and takes the rest from the file with fresh ids for tabs, groups and panes; the tabs it had go to the closed stack (so they can be reopened) and their sessions end. A space that does not exist or a file that is not valid changes nothing. It is in the property test of the reducer.
  - _Where you were looking is not part of a space._ `spaceFileSignature` is the file without the tab a space shows, the pane a tab has focused and whether a group is folded. A file whose signature is the one of the space it is tied to is not written again by a push and does not replace the space on a pull (only the record is renewed), so switching tabs on one computer neither closes the tabs of the same space on another nor makes a file that two computers both edit.
  - _What does not travel._ **Removing a space does not remove its file** (nothing is deleted by the sync): the file stays in the folder and in the remote, the space does not come back on the computer that removed it while the file is as it was, and a change of that file made on another computer brings the space back. Two computers that each make a space with the same name before they sync make the same file name with different content, which is a conflict at that path (`Pull stopped`), and the first sync of two computers that both have an untouched default space ends with that space twice on each, as spaces have no identity across computers other than their file.
- **Push on close** (NOR-F19-01d, no Rust command and no new `Backend` method). `sync.pushOnClose` (`syncSchema` in `config.ts`, off unless the file says `true`; `pushOnCloseAllowed` and the default are in `packages/model/src/sync-close.ts`) makes closing the app push first, with the same steps as the Push of the screen. It hangs on the close that already exists: the Rust side holds the close and tells the page (`close-requested`), and the save of the page (`closeSave` in `boot.ts`) writes the scrollback snapshots and the state first and only then runs `runPushOnClose` (`sync-run.ts`). That function reads the option when the close happens and does nothing, asking the backend for nothing, when it is off; reads the status (no network) and does nothing without a connected remote; writes the spaces as files (`writeSpaceFiles`, so the push carries them); then `closePushDecision` (pure, in the model) says push only when a file of the config folder differs from the clone, a commit waits to be sent or a space file was just written, and `Backend.syncPush` runs. It never rejects and never runs past `CLOSE_PUSH_LIMIT_MS` (4 s): an error of git (a remote that moved on included) or a push that is too slow is recorded (`console.warn` and the list the test hook of the web build returns) and the close goes on. A push cut short may still end in the background until the process is gone; git leaves the remote as it was if it is killed mid-push. The page limit grows with the option (`closeLimitMs`: 2 s for the saves, 6 s with the push on, read when the close is asked), and `CLOSE_WAIT` in `lifecycle.rs` went from 4 s to 8 s so the window still waits longer than the page (a test reads the Rust constant). Hiding the window in the tray (`tray::close_outcome`) does not close the app, so it never pushes. The switch **Push when Noren closes** is in the Sync section and writes the key with `ConfigManager.update`, at once. The web build has no window to close: `window.__norenClose.run()` runs the same save with the same limit and answers what the push did and what it recorded.
- **Sync through a gist** (NOR-F19-02a, the core only: no screen, no palette command and no push on close for it yet, which are NOR-F19-02b). The same closed list of files can travel through a secret GitHub Gist instead of a git repository: the module `crates/noren-core/src/sync_gist.rs` (`GistSync`), six commands (`sync_gist_status`, `sync_gist_set_token`, `sync_gist_clear_token`, `sync_gist_connect`, `sync_gist_pull`, `sync_gist_push`, in the four places a command lives) and the `Backend` methods `syncGistStatus`, `syncGistSetToken`, `syncGistClearToken`, `syncGistConnect`, `syncGistPull` and `syncGistPush`. The sync through git is not changed; the one thing they share is the scan of the closed list (`syncable_files_in` in `sync.rs`), so both read the config folder the same way, and the types of the results (`PendingChange`, `PullOutcome`, `PushOutcome`; `syncPullSchema` and `syncPushSchema` on the model side, where for a gist `committed` and `pushed` are both true when a new revision was made).
  - _What travels_ is exactly `is_syncable` and nothing else. A gist has no folders, so a path is sent as one flat name: the first `/` becomes `--` (`themes/x.json` is `themes--x.json`, `config.jsonc` stays; `gist_file_name`/`gistFileName`). The mapping is one to one and checked on the way back (`path_of_gist_file`/`pathOfGistFile`): a name is read only when it maps to a path of the list and that path maps to exactly that name, so a file someone else put in the gist (`README.md`, `state.json`, `sync-gist.json`) or a name made to look like a path (`themes--../x.json`) is ignored and never written, and the file of this module's record cannot come in. An empty file is left out (a gist cannot hold one), a file over 1 MiB is refused, and a file the API cut short (`truncated`) is refused too. The same cases are tested in Rust and in Vitest.
  - _The token_ is a personal access token with the gist permission. It lives in the system keychain through `KeyVault` under the entry `sync:gist-token` (`SYNC_GIST_TOKEN_ENTRY`), a name no AI provider can have: provider ids are letters, digits, `-` and `_` (`is_valid_provider_id`) and a `:` is not one, so `AiState::configure` refuses it and no provider ever reads it as its key (which would send it to the address of that provider); the vault accepts that name through `is_app_entry` and no other with a colon, and `AiState::set_key` refuses every name that is not a provider id, so the commands for provider keys can neither replace nor remove the token. `set_token` checks it (one run of visible ASCII, at most 1024 characters) and drops the blanks of a paste; nothing returns it: `sync_gist_status` says only `hasToken`. It goes out only as the `Authorization` header of a request to the fixed address, never in a URL, a file, a log or an error: the text a server sends back has the token taken out of it (`[token]`), and a reqwest error is written without its address. The `FakeBackend` does not record the token with the call.
  - _The requests_ go to `https://api.github.com` and to nothing else (`GIST_API_BASE`; a test, and only a test, may use `http://127.0.0.1:<port>`): each has a deadline of 30 s for the whole request, a ceiling on the bytes read (16 MiB; 64 KiB for the message of an error), follows no redirect (the token goes with the request) and asks nothing of the person. A push sends at most 8 MiB of file content. The id of a gist is checked (1 to 64 letters or digits) before it is put in a path. The three calls are `GET /gists/{id}`, `POST /gists` (a secret gist) and `PATCH /gists/{id}`; the answers are read as untyped JSON and a gist that is not one (no id, files not an object, another id than the one asked, more files than the API lists) is an error.
  - _The record_ `sync-gist.json` sits next to `config.jsonc` and holds the id of the gist, whether it is public and the sha256 of each file as the gist held it when this computer last synced. It is not on the closed list, so it never travels, and it holds no token. A record that cannot be read is an error and not an empty one (an empty one would make every file of the gist look new). After a push the record takes the hash of what the answer says the gist holds for the files it sent (the bytes it was given if the answer has none), so a gist that rewrote a line ending would not make every later push look like a change by someone else.
  - _The steps._ **Connect** with an id reads that gist and copies nothing (the first pull brings its files); with no id it makes a secret gist of the files of this computer and needs at least one. Connecting again to the same gist keeps what the record knows. The status says whether the gist is public, because the whole of `config.jsonc` travels. **Status** has no network: the files whose bytes differ from the record. **Push** reads the gist first and refuses (`Changed`, "pull first, then push again", with the paths) when any file of it is not as this computer last saw it, including one taken out of it, and sends nothing then; otherwise it sends, in one request, the files that changed here. The API has no conditional update, so the check and the request are two calls and a change between them is not seen. **Pull** compares file by file with the record: a file the gist did not change is left alone (a local edit stays pending); a file it changed is written when this computer did not change it or already holds the same bytes, and is a conflict when both changed to different bytes. With any conflict nothing is written and the record does not move (`PullOutcome::Conflicts` with the paths); a clean pull writes the files and sets the record to what the gist holds, which is also how a push refused for a file taken out of the gist is settled. Nothing is deleted on either side. One step runs at a time (`GistSync` holds a turn); the smoke run can read the status (over a vault in memory) and refuses to store a token, connect, pull and push.
  - _Tests._ `noren-core` runs a fake of the Gist API on `127.0.0.1:0` (gists in memory, every request logged, forced failures) with a `MemoryVault` and a temporary config folder: the mapping both ways, the address rules, the token (stored under its own name, never given back, refused when it is not one), connect with and without an id, a push of only what changed, a push refused when the gist changed with no request after the read, a clean pull, a conflict that writes nothing, names off the list never written, an HTTP error whose message echoes the token, no server, a redirect, a timeout, a ceiling, a gist the API cut short and two computers going back and forth. The model has the same name cases (`sync-gist.test.ts`), the `FakeBackend` keeps a GitHub in memory with the same rules (`fake-sync-gist.ts`, `putSyncGist`, `setSyncGistFile` and `setSyncGistFailure` for a test) and the web backend lands a pulled file where the app reads it, as the pull through git does. What is not verified: the real API of GitHub (that it keeps the bytes it is given, accepts these flat names and answers as the fake does) and the real keychain, which no test touches.
- **The screen of the sync through a gist** (NOR-F19-02b, no Rust and no new `Backend` method: the six `syncGist*` calls were made by NOR-F19-02a). The choice between the two ways to sync is `sync.method` of `config.jsonc` (`"git"`, the default, or `"gist"`; `SYNC_METHODS`, `DEFAULT_SYNC_METHOD` and `syncMethodOf` in `packages/model/src/sync-method.ts`). The **Sync** section starts with the list **Sync through** (written to the file like the switch of the push on close, comments kept) and shows the part of the method chosen: `GitSync`, the section as NOR-F19-01b made it, or `GistSync` in `SyncPanel.tsx`. The two methods keep their own connection, so switching does not disconnect the other.
  - _`GistSync`_ has the token box (`type="password"`, never completed): **Save token** checks it with `syncGistTokenProblem` (`checkGistToken`; the sentence of a refusal never repeats it), hands it to `Backend.syncGistSetToken` and empties the box as soon as the call returns, whatever the answer, so the page holds the token only while it is typed; **Remove token** calls `syncGistClearToken`. The section only says whether a token is stored (`hasToken` of the status): no call returns the token and no test finds it in the page, in the browser storage or in the calls the fake recorded. **Connect** takes the id of a gist (`checkGistId`, the same rule as `isSyncGistId`, so a pasted address is refused with the words for it before anything is sent) and **Make a secret gist** connects with no id; making a gist is its own button so it never happens by a stray Enter or a blank box. The status line is `gistStatusText` (not connected, or the gist with up to date or N files to send; no "behind", because a gist has nothing to compare with before the network: Pull is what finds out), the files a push would carry are listed like the ones of git, and every answer is a sentence in a `status` region.
  - _What the screen says that a screen of git does not._ A gist that is public (`status.public`) gets a warning of its own that stays as long as that gist is the one connected (`gistPublicWarning`: anyone can find and read `config.jsonc` and the other files; make a secret gist instead), and is repeated when connecting to it. A gist the app has just made says it is secret and what that does and does not mean: not listed or searchable, but open to whoever has the link, so nothing secret belongs in the settings (`gistConnectedMessage`). A conflict names the paths, says nothing changed and says how to settle it for a gist (make the file the same on both sides, here or on the page of the gist), not "in the repository" (`pullMessage` takes the method). A status that cannot be read (a file of the config folder over 1 MiB, the keychain locked) is shown in the place of the status with the text the backend gave, and the method list, the token box, the id box and the buttons stay: the rest of the section does not hide behind it.
  - _The commands and the close follow the method._ `runPull`, `runPush`, `runSyncCommand` and `runPushOnClose` (`sync-run.ts`) take the method (`syncMethodOf(config.sync)`, read when the command runs or the close happens, so a change of the list takes effect with no restart) and call `syncPull`/`syncPush` or `syncGistPull`/`syncGistPush` and the matching status; the spaces are written before a push and made after a pull the same way for both. The palette says where to connect when no remote (git) or gist is connected and, for a gist, that a token is missing (`notConnectedMessage`) before it asks anything else. The push on close reads the status of the method (`closePushDecision` takes either: a gist status has no `ahead`) and records a failure of the gist push the same way as one of git.
  - _`sync.method` travels with `config.jsonc`._ The file is sent whole, so a pull that brings a `config.jsonc` with another `sync.method` (or none, which is git) changes the method of this computer once the pull has written it; the Sync section and the palette follow the file as for every setting.
  - _The web build_ seeds the gists under `noren.web.sync` (`gists`: gist id to `{ public?, files }` with the files by flat name, and `gistFailure`), next to the files of this computer that both methods share; a pull through the gist lands the config, themes and mods where the app reads them, like the pull through git. The in-memory GitHub plays with the test hooks `putSyncGist`, `setSyncGistFile`, `syncGistFiles`, `syncGistIds` and `failSyncGist` of `window.__norenTest`. `e2e/sync-gist.spec.ts` covers the choice, the token, connect, push, a clean pull, a conflict, the public warning, an unreadable status, the palette commands and the push on close through the gist; the git specs stay green with the default method.
- **Tests.** `noren-core` tests build a bare repository in a temporary folder (`git init --bare`) and give git a scratch `HOME`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM`, so the person's git config is never read and nothing touches a network: clone, push then pull into a second computer, the closed list in both directions, a conflict (paths listed, config folder and clone untouched), the two refused replacements, the address rules, a missing git, the deadline; `sync_spaces.rs` tests in a temporary folder (a name off the list refused, the ceilings, write and read back, the record, a damaged record), and a push and pull of space files with the record that stays on the computer. ## The update of the app

The app can find out that a newer version exists and install it (NOR-F20-02a: the core, the commands and the `Backend` methods; NOR-F20-02b: the screen, the palette command and the notice of a new version, in the last bullets of this section). Nothing runs by itself: no check at start, no download the person did not ask for, and `update_install` is the only way an installer starts. The layers:

- **`noren-core::update`** (`crates/noren-core/src/update.rs`, no Tauri) gets the bytes. `Fetcher` fetches the feed (`feed`) and the package (`package`) over `https` only, with a deadline (30 s for the feed, 15 min for the package), a ceiling on the size (1 MiB, 512 MiB; a length announced over it fails before a byte is read, and a body that outgrows it while it is read fails too), no credential in the address, at most five redirects (the assets of a GitHub release are served from another host) and never a redirect to an address it would not have fetched itself. The one exception is a feed whose own address is `http://127.0.0.1:<port>`, which a test uses: then the package and the redirects may be on `127.0.0.1` too. The feed is returned as the JSON object it is: reading it is the plugin's job, so the format cannot drift from what the release tooling writes. `endpoint_of` and `key_is_set` read `plugins > updater` of `tauri.conf.json`; `UpdateInfo::new` cleans the release notes for a screen (no control character but the line break and the tab, at most 8000 characters); `UpdateError` has a sentence for every way a step ends.
- **`tauri-plugin-updater`** decides about those bytes, in `src-tauri/src/update.rs`: `Updater::restore_update` reads the feed in the format of the Tauri updater (a `platforms` map of `<os>-<arch>[-<installer>]` to a `url` and a `signature`, or one `url` and `signature` for the dynamic format), picks the entry of this platform and says whether the version is newer; `Update::verify` checks the minisign signature of the downloaded package against the public key; `Update::install` checks it once more and runs the installer of the system (on Windows it starts the installer and the app exits, on Linux it replaces the AppImage or installs the package, on macOS it replaces the bundle). The plugin makes no request of its own here: its own `check` and `download` have no ceiling and no deadline, so `noren-core` gets the bytes and hands them over. The plugin is registered by `update::plugin()` with one rule of its own: a version is newer only by its precedence in semver, which leaves out the build metadata (`0.1.0+5` is `0.1.0`), as the specification says and the `Ord` of the semver crate does not. Its own commands (`check`, `download`, `install`, `download_and_install`) get no capability, so the page cannot call them. Production features: `native-tls` only (no second TLS stack, no `zip` for the format of Tauri 1).
- **The signature must say which version it was made for** (`requireSignedVersion: true` in the plugin configuration). The feed is not signed, only the package is, so without it a feed could announce version 9.9.9 with the `url` and `signature` of an older release that is genuine and validly signed and make the app install the old build. The Tauri CLI (`tauri build`, or `tauri signer sign --app-version <v>`) writes the version in the trusted comment of the signature, which the signature covers, and the app refuses a package whose signed version is not the one the feed announces, and one whose signature carries none.
- **`UpdateState`** (`src-tauri/src/update.rs`) is the managed state: the fetcher of the first endpoint of the configuration, whether a key is set, the version that runs and the update the last check found (kept for the install), and one step at a time (a check or an install while one runs is refused, "another step of the update is still running"). `check` gets the feed and keeps the update it announces when it is newer and has a package for this platform (a newer release with no entry for this platform is refused, an equal or older one is "no update"); the signature is not looked at yet, because the package is not in hand. `install` downloads the package of that update, checks the signature (`Update::verify`, the refusal that says why) and only then hands the bytes to the installer; a package that is not the file the signature was made for, or was signed with another key, or for another version, is never installed. The installer is behind `PackageInstaller` so a test can see what would be installed (`SystemInstaller` is the plugin's).
- **The commands** `update_status` (no network: whether this build can update, the version that runs, the update found), `update_check` (the update found or `null`) and `update_install` are in the four places a command lives (`main.rs`, `build.rs`, `capabilities/default.json` for the main window only, and the `capabilities.rs` tests that keep them the same); the two that reach out also check in Rust that the window is the main one (`require_owner`). The progress of the download is the event `update-progress` (`{ downloaded, total }`, at most one for every 256 KiB, the first piece and the last), sent to the main window. A smoke run builds the state with updating off: `check` and `install` are refused before anything reaches the network, and `--smoke` checks that (`SMOKE update off`) and that the plugin took the configuration of `tauri.conf.json`.
- **`Backend`**: `updateStatus`, `updateCheck`, `updateInstall` and `onUpdateProgress`, on the Tauri backend (answers checked with zod: `updateStatusSchema`, `updateInfoSchema`, `updateProgressSchema`; a progress event that is not one is dropped), the web backend and the `FakeBackend`. The fake (`fake-update.ts`) keeps a release feed in memory (`setUpdateRelease`: a version, notes, a date, the size of the package and a `refusal` for a package whose signature does not match), the version that runs (`setUpdateCurrentVersion`), whether the build has a key (`setUpdateConfigured`) and an unreachable server (`setUpdateFailure`), with the same sentences and the same order of steps, and orders versions with `compareVersions` (semver 2.0, the same table as the Rust test). The web build seeds all of it under `noren.web.update`.
- **The key** is `plugins > updater > pubkey` of `tauri.conf.json`, the only place it is written, and it holds the placeholder `PUBKEY_NOT_SET` until the maintainer puts the real public key there (NOR-F21-07). While it does, `key_is_set` is false, `update_status` says `configured: false` and a check or an install is refused ("this build has no update key yet"): an update is never trusted without a key to check it against. The private key is the maintainer's and is never in the repository; the tests use keys made for them, whose private halves were thrown away. To set the real one (NOR-F21-07): `tauri signer generate -w <file>` (from `apps/desktop`, with `pnpm exec`), put the public key it prints in `plugins > updater > pubkey`, keep the private key and its password out of the repository as `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` for the build that makes the installers. The feed is the asset `latest.json` of the latest release (`https://github.com/marllon/noren/releases/latest/download/latest.json`); making the release tooling write it, and sign the installers (`bundle.createUpdaterArtifacts`, which needs the private key in the environment of the build), is not part of this task.
- **Tests.** `noren-core` runs a server on `127.0.0.1:0` that plays the feed and the package (a redirect, a slow answer, a body that is too large or cut short): the address rules, the endpoint and the key of the configuration, the feed, the package with its progress, the ceilings and the deadlines, the redirects, and the cleaning of the notes. The app runs the real plugin in the mock runtime of Tauri, with the configuration it would have, against the same kind of server and a package signed with a key made for the test (`PACKAGE` and three signatures, whose fixtures say how to make new ones with the Tauri CLI): the valid update is found, downloaded, checked and handed to a recorder in place of the installer; a wrong key, a package changed by one byte at the start, the middle or the end, a package shorter or longer, a signature that is not one, a signature for another version (the downgrade replay) or with none, a version that is equal or older, a release with no entry for this platform, a feed in the wrong format, a package address that is not `https`, a package over the ceiling, no key, a smoke run and a second step while one runs are all refused with nothing installed; the same flow through the three commands in the shape the page reads, and only from the main window. The model tests the shapes, the order of versions (examples of the specification and properties) and the fake; the backends test the Tauri commands with a bridge that answers and the seed of the web build. Besides the screen (the last bullets of this section), `e2e/update.spec.ts` holds two things in the built web page (through the test hooks `updateCalls`, `installedUpdates` and `updateStep`): the page, used the way a person uses it, with a newer release seeded, never calls the update by itself (no check at start, no install) — the test the screen of NOR-F20-02b has to keep true for the install, whatever it allows for the check — and the seed under `noren.web.update` reaches the backend of the page, where a check keeps only a newer release, an install needs one found and a refused package installs nothing.
- **The screen of the update (NOR-F20-02b).** The person checks and installs from the **Updates** section of the settings (`UpdatePanel.tsx`, after Sync) or with the palette command **Check for updates** (`app.check-updates`, category General, no key by default; the `update-check` action). Nothing is checked, downloaded or installed by itself: opening the settings makes no call to the backend (`e2e/update.spec.ts` still holds that), the check is a click or the palette command, and the install is another click on a found update. The palette command opens the settings, scrolls the section into view (`UpdateController.requestReveal` and `takeReveal`, run on the next frame because the settings screen puts the focus on its first control when it opens) and starts the check; the result is read in the section and not as a notice, because a new version has notes and a button.
- **The pure part** is `update-screen.ts`: the phase of the screen (`idle`, `checking`, `current`, `available`, `saving`, `downloading`, `installed`, `failed`) and `nextPhase`, which moves it by events and ignores an event that does not belong to the phase it finds (a late progress event after the install ended, a second check while a step runs, an install on anything but a found update); `classifyUpdateFailure`, which reads the English sentence of `UpdateError` (and of the refusals of the plugin) into a kind (`no-key`, `signature`, `signed-version`, `no-package`, `unreachable`, `timeout`, `server`, `too-large`, `feed`, `busy`, `install`, `other` and the rest); `failureText`, the sentence of each kind in English and Brazilian Portuguese (the refusal of a package ends with "Nothing was installed."; an `install` or `other` failure keeps the words of the backend); `progressView` (a whole share, rounded down and never over 100, or none while the size is unknown) and `publishedText` (the date in the language in force). The backend keeps one set of English sentences and the screen translates them.
- **The steps** are `UpdateController` (`update-controller.ts`), one for the window, created in `App` and shared by the section and the palette so a check started from the palette goes on while the settings open: `check()` calls `updateCheck` (and `updateStatus` only to say the version that runs when nothing newer was found), and `install()` runs only on a found update, listens to `onUpdateProgress` for the length of the install and ends in `installed` or in a `failed` phase with the refusal. After a refusal the person can check again; nothing is retried by itself.
- **Saved before the installer** (finding 302). On Windows `Update::install` starts the installer and ends the process, so the close of the window (the page saving the scrollback snapshots and the state, then `RunEvent::Exit`) may never run. `install()` therefore first runs the same save the close runs: `boot.ts` registers it with `setExitSave` as `saveWithin(closeSave, realClock, closeLimit())` (`exit-save.ts`), where `closeSave` is the one `followWindowClose` and the web test hook `__norenClose` run (the snapshots, then the state, then the push of `sync.pushOnClose` only when that setting is on), with the same limit, and `updateInstall` is called only after it ended (the phase is `saving`, "Saving your tabs before the update..."). A save that fails or is slow does not stop the update, as it does not stop a close. `e2e/update-screen.spec.ts` changes the workspace and clicks Install in the same turn and reads the order of the backend calls: the state is written before `updateInstall`, and taking the save out fails it. What the real installer does with the running shells (the installer hooks stop the session daemon) is not verified (D19).
- **The download** is a `<progress>` named "Download of the update" with the share, and the line "25% (12.0 MiB of 48.0 MiB)"; it is indeterminate until the size is known. The `FakeBackend` can hold an install a quarter of the way (`holdUpdateInstall`; the test hooks `holdUpdateInstall` and `releaseUpdateInstall`), so a test sees the bar on screen, and the hook `backendCalls` gives the order of the calls for the save-first test.
- **Tests of the screen.** Vitest: `update-screen.test.ts` (every sentence of the Rust errors into a kind and a text in both languages, the phases and the events that must be ignored, the progress, the date) and `update-controller.test.ts` (save, then install; nothing happens until asked; the progress, a check during an install, the refusals). `e2e/update-screen.spec.ts` with the `FakeBackend` seeded under `noren.web.update`: nothing new, a new version with its notes, the install only on a click (also after the settings are closed and opened), the progress bar, the refusal by signature, no key, a server down and the other refusals, the palette command, the save before the install, and the section in Brazilian Portuguese; each state is also run through axe (any impact, no rule off), and the Updates section is one more of the sections of `accessibility-settings.spec.ts`. What axe found in Portuguese and was fixed: the visible text of the test buttons of the AI section ("Testar conexão") was not the start of their accessible name ("Testar a conexão com...").
- **Not verified (D19).** The installers themselves: no test starts one, because that opens a window and replaces the program (`SystemInstaller` is one line, `Update::install`, the code of the plugin; on Windows `src-tauri/installer/hooks.nsh` and `stop-norend.wix.xml` already stop the session daemon before the files are replaced). The real GitHub release, the TLS of the real host and an update from a signed installer built by the release tooling are not tested either: there is no release yet and the private key is not here.

## Screen reader support

Two things serve a screen reader, and neither needs the other (NOR-F20-01a; the axe checks of the screens, menus and dialogs are NOR-F20-01b, and of the panels and panes NOR-F20-01c, below; the manual script with a real screen reader is [ACCESSIBILITY.md](ACCESSIBILITY.md)).

- **The screen reader mode of the terminal.** `terminal.screenReaderMode` (`terminalSchema`, default `false`, in `docs/config.schema.json`; `DEFAULT_SCREEN_READER_MODE` in `terminal-options.ts`) is a field of `TerminalOptions`, so it follows the same path as the font and the cursor: `terminal-options-store.ts` compares it with the others to hand out a new object, `TerminalView` gives it to xterm when the terminal is made and writes `term.options.screenReaderMode` when the options change. xterm builds (or removes) its accessibility tree, the `.xterm-accessibility` element, when that option changes, so the switch is live: the session, the buffer and the WebGL renderer are not touched. The settings screen has a switch for it (`TerminalValues.screenReaderMode`, written with the rest of the Terminal section) and the palette has **Toggle screen reader mode** (`terminal.screen-reader`, the `screen-reader` command): `screen-reader-action.ts` flips the setting through `ConfigManager.update`, like the layout actions, and answers the sentence the notice shows.
- **The announcer.** `announcer.ts` is pure: the sentences (`navigationAnnouncement`, `commandAnnouncement`, `bellAnnouncement`, `sessionEndedAnnouncement`, `syncAnnouncement`, all through `t()`, so English and Brazilian Portuguese) and the `Announcer` class that holds the text of two regions and the rule against bursts. `AnnouncerRegion.tsx` draws them once, in the app shell (`data-nr-part="announcer"`, visually hidden): a part with `aria-live="polite"` and a part with `aria-live="assertive"`, without a `role`, so the notice line stays the only `role="status"` of the page (that line says the other notices of the window by itself, as it always did). Assertive is for errors only: a command that ended with a code other than 0, a shell that ended with one, a Pull or a Push whose message is an alert (`SyncMessage.alert`); everything else is polite. The same announcement (same text, same urgency) is not said again for `ANNOUNCE_BURST_MS` (2 s), so fifty bells say it once; once the window is over the text gets a trailing no-break space, so the region reports a change and says it again. A region is emptied `ANNOUNCE_CLEAR_MS` (10 s) after its last announcement so no stale sentence is left to read by hand.
- **Where each announcement comes from.** The tab or space switched to: `App` compares the space and tab on screen with the last ones (`NavigationPoint`), and a rename or a first draw says nothing. A command that ended and the bell: the callbacks the `PaneLocationTracker` already has (`onCommand` with `kind: "end"`, `onAttention` with `kind: "bell"`); the tab is found by the pane (`tabNameOfPane`). A shell that ended: the new `onExit` prop of `TerminalView`, called with the code beside the "Process exited" line. Pull and Push: `runSync` announces the `SyncMessage` it gets. The notice line shows the sync message too, but `showNotice(text, true)` draws it inside an `aria-hidden` span, so the line does not say it and the announcer says it once, with its own urgency.
- **The axe checks (NOR-F20-01b).** `e2e/axe-fixture.ts` holds one helper, `expectNoAxeViolations(page, surface)`: it runs every default rule of axe-core on the whole page and fails with the rule, the nodes and the reason of each violation, of any impact (critical, serious, moderate or minor). It disables no rule and excludes nothing: a surface that cannot pass is fixed in its component. `accessibility.spec.ts` (the five screens), `accessibility-settings.spec.ts` (each section of the settings, the Profiles section with a new profile, the AI section with the form to add a provider) and `accessibility-overlays.spec.ts` (the menus of a tab, a group, a space, a pane and a tab in the top bar; the dialogs of a space, its picture, its deletion, a paste, a link, a command asked of the AI, a profile import, a worktree, a project action; the palette, the search over the tabs, the Ctrl+Tab switcher, the space switcher, the peek, the quick terminal panel, and the notice of a broken settings file) open each surface the way a user does and run it. What axe found: a terminal region is named `Terminal` when it is alone in its tab and `Terminal 2 of 3` when it is not (`TerminalView` takes a `label`; the quick window names its own), and the Terminal section of the settings is named `Terminal options`, so no two landmarks share a name; the title of the window is a level-one heading; a dialog is a `div` with the role and the form inside it (a `form` may not carry `role="dialog"`); a button whose visible text is "Store key" or "Remove key" is named by words that start with them; the muted text on the active and the selected rows is pulled toward the text color, as the tab already did; the peek is drawn inside the `main` landmark. What axe cannot say (what a screen reader reads, the order of a reading) is left to the manual script, [ACCESSIBILITY.md](ACCESSIBILITY.md).
- **The axe checks of the panels and panes (NOR-F20-01c).** The same helper runs on the Ask panel (empty, with the list of tabs to add, the preview, the answer drawn as Markdown, a failure, no provider), the Agents panel (empty and with a waiting, a working and an idle agent), the bench scoreboard, the recommended models (and the install question), the providers (Ollama, the file's providers with their notes and key states, the steps, the add form with its refusals), the gallery, the Sync section (git and Gist, each with its notes, conflict and failure), the plugin panel, the Library (archive, closed, no match, the delete question), the browser, diff and preview panes (every kind of file and refusal), the Favorites grid, the project actions header (idle, running, with a notice), the live groups (worktrees, containers, SSH hosts, with an error), the quick terminal window and a window of its own with its sidebar, a preview, a diff, a missing file and a browser pane; each test sits in the spec of its surface and opens it the way a user does. The helper waits for the animations that end (a list sliding in is not read half way) and has one option, `sandboxedFrame`, for the plugin panel: the frame allows no script, so axe cannot enter it, and the test runs axe in its legacy mode with a short frame wait (no rule is changed, nothing is excluded; the frame element is checked and its inside is reported "not tested"). What axe found, fixed in the components: the headings of a Markdown answer start at level 3 and never skip a level (`headingLevels` in `Markdown.tsx`), the path on top of a preview pane is a level-two heading, the question of the recommended models takes the level of its section (`ConfirmDialog` `titleLevel`); the names of an Agents row and of a Library row start with the text they show, in the same order (a flex row has a space text node between its parts so a tool does not run the words together); the muted text on a hovered or focused agent row, a selected library row, the New tab button of a window and the exit code of a selected tab is pulled toward the text color, and the state word of an agent is a little darker; a window's own sidebar is "Window sidebar" and its terminals "Window terminal" (or "Window terminal 2 of 3"), so they differ from the main window's when both are on one page. The preview page of the windows draws every window beside the app, so each window test opens one.
- **Tests.** `announcer.test.ts` (sentences, urgency, burst, clear, reset, languages), `screen-reader-action.test.ts`, `screen-reader-config.test.ts` in the model, and `e2e/screen-reader.spec.ts` (the tree appears and goes away with the setting in the same session, the palette command, the announcements in the region, axe with the mode on). ## Security

The page is treated as code that can be tricked, because it draws text that programs wrote. Four layers keep that from reaching the machine, and [SECURITY_REVIEW.md](SECURITY_REVIEW.md) lists what was checked in each, with the evidence:

- **Content Security Policy** (`tauri.conf.json`): scripts only from the app itself, no `eval`, no remote content; `connect-src` is the IPC and nothing else. Inline styles are the one relaxation (the terminal library and the mods write `<style>` elements).
- **Capabilities** (`capabilities/`): the app commands are declared in `build.rs`, so each window gets only the ones it names; no `core:default` set is granted. The tests in `src/capabilities.rs` keep `main.rs`, `build.rs`, the capabilities and the policy in step.
- **Links** (`link-prompt.ts`, `link.rs`): a click on a link asks first and only `http` and `https` addresses are opened, checked again on the Rust side (a click with Ctrl on an address a browser pane may show opens it in a pane beside the terminal instead, with no page of the pane given any command, see [The browser pane](#the-browser-pane)); a navigation away from the app pages is refused (`navigation.rs`).
- **Names that become files** (mods, themes, scrollback snapshots, background pictures, `noren://` folders): validated in TypeScript and again in `noren-core`, with tests that hand them `..`, absolute paths, drives, streams and device names.
