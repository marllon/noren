# Shell integration

A shell that Noren starts can tell the terminal where it is and what it is doing, using escape sequences (OSC) that are written into its output. Nothing is run on behalf of the user: the script only prints these sequences, and the interface reads them.

This page describes what exists today (tasks NOR-F7-01a, NOR-F7-01b, NOR-F7-02a, NOR-F7-02b, NOR-F7-03, NOR-F7-04a and NOR-F7-04b): the OSC parser, the scripts for PowerShell, bash, zsh and cmd, the folder and git branch of each pane and its last command in the sidebar, the automatic tab title, the command marks in the terminal, the unread and bell marks of tabs, groups and spaces, and the notifications of the system.

| Shell                               | Folder  | Prompt `A`/`B` | `C`, `D` with exit code | `E` command line |
| ----------------------------------- | ------- | -------------- | ----------------------- | ---------------- |
| PowerShell 7 and Windows PowerShell | OSC 7   | yes            | yes (needs PSReadLine)  | yes              |
| bash (Git Bash, Linux, macOS)       | OSC 7   | yes            | yes                     | yes              |
| zsh                                 | OSC 7   | yes            | yes                     | yes              |
| cmd                                 | OSC 9;9 | yes            | no (see below)          | no               |

## What the shell reports

| Sequence                     | Event           | Meaning                                                        |
| ---------------------------- | --------------- | -------------------------------------------------------------- |
| `OSC 7 ; file://host/path`   | `cwd`           | The folder the shell is in (sent at every prompt).             |
| `OSC 9 ; 9 ; path`           | `cwd`           | The same, in the form cmd can write (see the cmd section).     |
| `OSC 133 ; A`                | `prompt-start`  | The prompt starts.                                             |
| `OSC 133 ; B`                | `prompt-end`    | The prompt ended; the user types the command.                  |
| `OSC 133 ; C`                | `command-start` | The command line was accepted and the command starts running.  |
| `OSC 133 ; D [; code]`       | `command-end`   | The command ended, with its exit code when the shell knows it. |
| `OSC 633 ; E ; command line` | `command-line`  | The text of the command, escaped (see below).                  |

The scripts send the rows above. A program that runs in the shell can also ask for attention, with no script involved; the parser reads these too:

| Sequence                          | Event          | Meaning                                       |
| --------------------------------- | -------------- | --------------------------------------------- |
| BEL (`0x07`) outside a sequence   | `bell`         | The terminal bell.                            |
| `OSC 9 ; text`                    | `notification` | A notification with a body (the iTerm2 form). |
| `OSC 777 ; notify ; title ; body` | `notification` | A notification with a title and a body.       |

`OSC` is `ESC ]`. A sequence ends with BEL (`0x07`) or ST (`ESC \`). The scripts use BEL.

One command gives this order: `A`, the prompt text, `B`, the user types, `E`, `C`, the output of the command, `D;code`, then `7` and `A` of the next prompt. The first prompt has no `D`, and an empty line has none either.

The command line in `OSC 633;E` is limited to its first 2000 characters, and three kinds of characters are written as escapes so that the sequence stays well formed: a backslash is `\\`, and a `;` or a control character (including a new line) is `\xNN` with the hexadecimal character code.

## The parser

`ShellIntegrationParser` in `@noren/model` (`packages/model/src/shell-integration.ts`) turns the output of a session into events. It is pure: no DOM, no Tauri, no timers.

```ts
const parser = new ShellIntegrationParser();
for (const chunk of outputChunks) {
  for (const event of parser.feed(chunk)) {
    // { kind: "cwd", path } | { kind: "prompt-start" } | { kind: "prompt-end" }
    // | { kind: "command-start" } | { kind: "command-end", exitCode } | { kind: "command-line", text }
    // | { kind: "bell" } | { kind: "notification", title?, body }
  }
}
```

- `feed` takes bytes (`Uint8Array`) or text and returns the events that finished in that chunk, in order.
- It reads bytes, so a sequence cut anywhere between two chunks (even inside a multi-byte character) gives the same events as the same bytes in one piece. A property test checks that any way of cutting the stream gives the same events.
- The only thing it keeps between calls is the beginning of a sequence that has not ended. That is capped at `maxOscBytes` (default 8192). A longer sequence is dropped up to its end and the parser carries on with the next one.
- Any OSC that is not one of the above (window title, ...) is ignored. An ESC that is not followed by `\` inside a sequence, or a CAN or SUB byte, abandons the sequence.
- `OSC 9` has three uses. `9;9;path` is the folder as cmd reports it, taken only when the path is absolute (a drive letter, or a leading `/` or `\`), has no control character, is at most 4096 characters, and may be in double quotes; backslashes become `/`, so `C:\Users\me` is `C:/Users/me`, like an `OSC 7` path. `9;<number>` or `9;<number>;...` (`9;4` is a progress bar, and ConEmu has more) belongs to another terminal and gives no event. Any other `9;text` is a notification whose body is the text.
- `OSC 777;notify;title;body` is a notification; the body may hold `;`, and either part may be empty but not both. Other `OSC 777` commands give no event.
- The text of a notification comes from a program and is plain: control characters become spaces, the ends are trimmed, and each of title and body is cut at 500 characters (`MAX_NOTIFICATION_CHARS`). A notification with nothing to say gives no event.
- A BEL that ends an OSC is its terminator, not a bell. A BEL anywhere else in the stream (also one that follows a cancelled or too long sequence) is a `bell` event.
- Text in a sequence comes from a program in the terminal and is not trusted: an `OSC 7` that is not a plain `file:` URL with a path (or whose path has a control character or is longer than 4096 characters) gives no event, and `133;D` takes only a plain integer as code.
- `pathFromFileUri` is the same reading of an `OSC 7` URL that `apps/desktop/src/osc7.ts` does for the recent folders of the palette. The two are kept apart for now: the recent folders still come from the OSC 7 handler of xterm.js, and the folder and branch of a pane (next section) come from the parser; a later task makes the app use the shared one.

## Folder and git branch of a pane

Each pane of the app has one `PaneLocationTracker` (`packages/model/src/pane-location.ts`), made once when the pane's view is created, and it owns the `ShellIntegrationParser` of that pane's session. `TerminalView` hands it every chunk of the session's output (the same bytes it writes to xterm.js), so the parser never lives in a React render. The tracker turns the events into the `pane/set-location` action of the reducer, which sets the pane's `cwd` and `gitBranch` together and changes nothing when the pane already has both.

- **When the branch is read.** The folder comes from `OSC 7` (or `OSC 9;9` in cmd). The branch of that folder is read again at every `OSC 133;A` (the prompt starts), every `OSC 133;D` (a command ended) and every folder report, because a command such as `git switch` changes the branch without changing the folder. A chunk with several of these, which is what a prompt sends, gives one lookup, and only one lookup is in flight at a time (requests that come meanwhile are replaced by the newest).
- **How it is read.** `Backend.gitInfo(cwd)` returns `{ branch, detached }` or `null`. The Tauri backend calls the `git_info` command, which runs `read_head` of `noren-core` (`crates/noren-core/src/git.rs`) on a blocking thread. It never runs `git`: it walks up from the folder to the first one with a `.git` that holds a usable `HEAD`.
  - `.git` is a folder: its `HEAD` is read.
  - `.git` is a file (a linked worktree, a submodule): its `gitdir:` line names the folder with the real `HEAD`, absolute or relative to the file.
  - `HEAD` is `ref: refs/heads/<name>`: the branch is `<name>` (slashes kept). `HEAD` is a 40 or 64 digit commit id: it is detached and the branch is shown as its first 7 characters.
  - A repository in the `reftable` format keeps the stub `ref: refs/heads/.invalid` in `HEAD` and its real branch in files this module does not read, so it shows no branch.
  - A `.git` that cannot be used (no `HEAD`, a `HEAD` that is neither of the above, a `gitdir:` that points nowhere) is skipped, as `git` does, so a stray `.git` does not hide the repository above it. The result is `null` outside any repository, and for a path that is not absolute.
  - The folder comes from terminal output, so nothing in it is trusted: only a `.git` entry and a `HEAD` are read, at most 4096 bytes of each, never a pipe or device, and a branch name with a control character or over 1024 characters is not used.
- **A failed lookup** (the bridge fails) counts as no branch: the folder is still recorded, and a wrong branch in the sidebar would be worse than none.
- **The folder a shell starts in.** A pane that has no folder (a new tab in a space without a start folder) starts in the folder of the user (`USERPROFILE` on Windows, `HOME` elsewhere), not in the folder the app was started from. The first folder the shell reports is not recorded as the pane's folder, because the pane would look the same restored without one; its branch is still read. The tab is named after it all the same (`Pane.shellCwd`, below). From the moment the shell leaves that folder the folder is recorded, and it is recorded when the shell comes back to it too. A pane that has a folder (restored, or started in one) records every report.
- **Saved.** `cwd` and `gitBranch` are part of the saved state, so a restored pane starts its new shell in the last folder it reported, and its branch is read again at the first prompt (and removed when the repository is gone).
- **Shells without integration** (fish, `wsl.exe`, a profile with `inject_integration` off) report nothing, so their panes keep the folder they had.
- **Web mode and tests.** `FakeBackend` takes `gitRepos` (a folder to `{ branch, detached }`) and `setGitRepo`; a folder is in the repository of the nearest folder above it that has one. The web build reads its repositories from the browser storage key `noren.web.git`, a JSON object from the folder that holds a repository to its branch (`{ "/proj": "main" }`) or to `{ "branch": "0123abc", "detached": true }`; the key is read at every lookup, so a test can change the branch while the page runs.

## Last command, running command and tab title

The same tracker follows the commands of the shell and tells `onCommand`; the app turns that into the `pane/command-start` and `pane/command-end` actions through `store.setPaneCommand`.

- **The events.** `OSC 633;E` carries the command line and arrives before the command runs; `OSC 133;C` is the start; `OSC 133;D;<code>` is the end. The tracker keeps the line until `C` takes it, remembers when `C` came, and at `D` reports the end with the exit code and the duration (the time between the two on its clock; tests inject one, the app uses the wall clock, and web mode uses the clock of the fake shell).
- **Odd streams.** A `D` with no `E` and no `C` before it (the first prompt of some shells) is not a command and reports nothing. A prompt (`133;A`) that comes while a command is running ends it without an exit code, so a command whose `D` was lost cannot stay "running". An `E` and a `D` with no `C` is reported at the end, without a duration. Shells that send no `633;E` (cmd, which sends no `C` or `D` either) show nothing.
- **In the pane.** `Pane.runningCommand` (`{ text? }`) is set from `C` and cleared at the end or when the shell exits; `Pane.lastCommand` (`{ text?, exitCode?, durationMs? }`, which the model already had) is set at the end, from the line that was running when the end does not repeat it. `Pane.status` stays the state of the session (`running`, `idle`, `exited`). The text is trimmed and cut at 500 characters; an exit code is kept when it is a whole number and a duration when it is not negative. Both actions change nothing when the pane already has the result. `lastCommand` is saved with the tab; `runningCommand` belongs to a shell that is gone, so a restored pane starts without it.
- **In the sidebar.** A tab with one pane shows a line under the folder and branch: the command line (cut by the stylesheet, the full text in its tooltip), then `exit N` and how long it took (`<1s`, `2.5s`, `12s`, `3m 05s`, `1h 02m`), or `running` while it runs. The line of a failed command (a code other than 0) is marked. A split tab shows the line of each pane in its pane list, and on the tab itself only when that list is folded (then it is the focused pane's). A tab with a command running gets the running mark. The words for assistive technology say `Running <command>` or `Last command <command>, exit N, <time>`.
- **The name of a tab.** One rule, `tabLabel` (`packages/model/src/tab-label.ts`), gives the name every part of the window shows: the sidebar, the bar of the top tabs, the favorites, the breadcrumb of the dense window, the palette, the search, the switcher and what a screen reader says. In this order, the first that has something to say wins: **(1)** the title the person typed (`titleLocked`), whatever the shell does; **(2)** the title the shell last asked for, which the app keeps equal to the automatic one below (a rename with the source `process`, never locked); **(3)** the automatic one worked out from the focused pane when the tab has no title yet; **(4)** the placeholder of the interface (`Tab 3`, `Aba 3`, counted in the order of the space) while no folder and no program are known.
- **The automatic title.** A tab whose title the user did not choose is named after its focused pane: the **name of its folder** (the last part of the path, whichever separator it uses and with or without a slash at the end: `C:\Users\ada\proj`, `/home/ada/proj/` and `\\wsl$\Ubuntu\home\ada\proj` are all `proj`; `~` for the home folder; a root, `/` or `C:/`, as it is) and, **while a command runs, `·` and its program after it** (`api · npm`; for `npm run build` the program is `npm`; a path, a Windows extension, quotes and leading `NAME=value` words are dropped). With no folder known yet the program alone is the name, and with neither the tab keeps its number. The folder comes first because it says what the tab is for while the program only says what it is doing now, and so it is the part the column keeps when an ellipsis cuts the name. The **window title a program sets (OSC 0 and 2) is not read at all**: it can not name a tab, so a program can not rename one the person named or one the shell named. The folder is the one the shell reported last (`Pane.shellCwd`, set at once by `pane/set-shell-folder` from OSC 7 and OSC 9;9, even the folder the shell started in, which the pane does not keep as its own, see above), else the one the pane has. The rule is `autoTabTitle` in the model and `autoTitleAction` in `apps/desktop/src/auto-title.ts`; it dispatches `item/rename` with the source `process`, which the reducer ignores while the title is locked, and the store applies it after every folder, location or command report and right after the user clears a title. A title the user typed is locked and never changes; leaving the box of the name as it was shown (Enter with the text of the tab) does not lock it. `Pane.shellCwd` belongs to a shell that is gone: a restored or reopened pane starts without it.
- **Tests that are not about names.** Every fresh fake shell starts in the same folder and reports it, so tabs nobody named would all read `~`. `FakeBackend` takes `reportFolder: false` (the web build reads it from the key `noren.web.folder-report` set to `off`), a shell that never tells its folder, as cmd does: its tabs keep their numbers (`e2e/numbered-tabs.ts`, used by the specs that tell tabs apart by name and are about something else). The names themselves are tested in `e2e/tab-names.spec.ts` and `e2e/command-meta.spec.ts`.

## Command marks

Every command a shell reports gets a mark in the terminal: a dot at its prompt, a bar in red when it failed, a red mark in the ruler beside the scrollbar, steps between prompts on Ctrl+Up and Ctrl+Down, and a way to select or copy the output of a command. The pure logic is `CommandMarks` in `@noren/model` (`packages/model/src/command-marks.ts`); `apps/desktop/src/command-marks-view.ts` gives it the cursor of an xterm.js terminal and draws the result; `TerminalView` makes one per terminal.

- **Where the events are read.** xterm.js reads `OSC 133` itself (`term.parser.registerOscHandler(133, ...)`), and the payload goes through the same `parseOsc` the pane tracker uses. This is not a second `ShellIntegrationParser`: the tracker still owns the only one of a session. The reason is position. Only the terminal knows which row its cursor is on at the moment a sequence is parsed, and it parses what it was written in its own time, later than the moment the bytes reach the pane tracker. A marker made then follows its row while the scrollback is trimmed and when the terminal reflows. A sequence cut anywhere between two writes reaches the handler whole, so the marks do not depend on how the output is chunked (a test cuts a transcript at every byte). `OSC 133` on the alternate screen (a program that is not the shell) is ignored.
- **What a mark holds.** Three rows, each an xterm.js marker: the _prompt_ row (where `A` was read), the _output_ row (where `C` was read: the line after the typed command) and the _end_ row (where `D` was read), plus the exit code and whether the cursor was in the middle of its row at the end (then that row is the last row of the output; otherwise the output ends on the row above).
- **Which events make a mark.** `A` opens a mark in the `prompt` state; `C` makes it a command (`running`) and `D` ends it (`done`) with its exit code. A prompt with no command (an empty line) is replaced by the next prompt and never gets a mark. A `D` with no command running is not a command (the first prompt of some shells) and is ignored. A `C` with no prompt before it (the terminal came up after the prompt was shown) takes the row above as its prompt, which is the line that was typed. A prompt that shows while a command runs ends it without an exit code (a lost `D`), and a second `C` ends the first. cmd sends no `C` or `D`, so it has no marks.
- **In the terminal.** Each command has a decoration on its prompt row (`data-nr-part="command-mark"`, with `data-nr-state` `running`, `done` or `failed`): a ring while it runs, a dot when it ended, a bar when the exit code is not 0. The color is the terminal theme's yellow, green or red (`markColors`, set as `--nr-mark-color`), so a theme changes it, and the shape does not depend on the color. A command that failed also gets an `overviewRulerOptions` mark in the same red, which xterm.js draws in the ruler over the scrollbar (the terminal sets `overviewRuler.width` to 14, the width xterm.js uses for the scrollbar anyway, so the columns do not change; the ruler has no border line of its own). A command whose exit code the shell did not report did not fail and has no ruler mark. The prompt Ctrl+Up or Ctrl+Down stepped to is flagged `data-nr-current="true"` and gets a faint band across its row, for as long as the view stays on it.
- **Explain button.** Where the AI is on for the space (the settings and the space menu both say so), the mark of a command that failed also holds a small **Explain** button at the right end of its row (`data-nr-part="explain-button"`, in the decoration xterm.js lays on that row; the stylesheet lets the pointer through the decoration and takes it back for the button). It reads that command, not the last one: the rows from its prompt to where its output starts (a long command that wrapped is joined again) and its output rows (`TerminalCommandMarks.explainRequest`), with the exit code and whether the start of the output was already gone from the scrollback. Pressing it opens the Ask panel on that command (see [ARCHITECTURE.md](ARCHITECTURE.md#explain-and--text)). With the AI off the decoration is hidden from assistive technology as before and has no button; turning the AI on or off redraws the failed marks at once (`setExplain`).
- **Moving between prompts.** Ctrl+Up and Ctrl+Down (actions `terminal.prompt-previous` and `terminal.prompt-next`, the same in both presets, `TerminalHandle.jumpToPrompt`) scroll so the prompt is at the top of the view. From the live end the previous prompt is the last command's, and past the last prompt the next step goes back to the live end. After the user scrolled, the step is relative to the top of the view (the nearest prompt above or below it). A prompt too close to the end to reach the top counts as reached when the view is at the end. The rule is `CommandMarks.step`. At the first prompt the key does nothing, but it is still taken.
- **When the keys are ours.** Only when a terminal has the keyboard, has at least one command mark and is not showing the alternate screen. With no mark (a shell without integration, a fresh tab, a program such as an editor on the alternate screen) the key is not taken and reaches the shell exactly as before. The palette entries for the same actions say "No command prompts in this pane yet" when there is nothing to go to.
- **Output of a command.** The output of a command is the rows from its output row to its end row. `TerminalHandle.lastOutput` joins them into text (a long line the terminal wrapped is joined again, the empty cells at the end of a row are dropped, no trailing line break) and `selectOutput` selects them (`term.selectLines`), scrolling to the first row if it is not on screen. _Select command output_ acts on the prompt stepped to when the view is still on it and that command ended, otherwise on the last command that ended; _Copy last command output_ always uses the last command that ended. A command still running is never used. A command that printed nothing selects and copies nothing and says so in the notice. If the scrollback dropped the start of the output, the text is what is left and the notice says the start is past the scrollback limit.
- **Where the actions are.** Both are registry actions (`terminal.select-output`, `terminal.copy-output`) with no chord in either preset, so they show as _None_ in the shortcuts screen and can be recorded; they are listed in the palette; the pane header has a _Pane menu_ button (shown with the pane headers, which are off by default) with both; and the tab menu of the sidebar and of the top bar has both for the focused pane of that tab (selecting also shows the tab). The notices: "Copied the output of the last command", "Copied the end of the output: the start is past the scrollback limit", "The last command printed no output", "No command has finished in this pane yet", "No finished command with output to select in this pane".
- **Cleared terminals.** A reset (`ESC c`) drops every mark; `CSI 3 J` and a trimmed scrollback drop the marks whose rows are gone (xterm.js disposes their markers). A `clear` homes the cursor and erases the screen without disposing the markers on it, so a prompt that shows on a row that older commands occupy drops those commands: they are not on screen any more, and the marks stay in the order of their rows. A command that is still running when its rows scroll past the whole scrollback keeps its place and still ends. Marks are not saved: a restored tab starts a new shell and a new terminal. A split gives the existing panes back empty in web mode, so a pane that was split has no marks until its shell shows a prompt again.
- **Test hook.** In web mode `window.__norenTest.marks()` returns, for the active terminal, every command: `row`, `text` (the prompt row), `state`, `exitCode`, `failed`, `ruler`, `current` and `outputRows`.

## PowerShell

`apps/desktop/src-tauri/resources/shell-integration/noren.ps1` works in PowerShell 7 (`pwsh`) and in Windows PowerShell 5.1.

- It is loaded **after** the user's profile, so the profile runs as usual. The `prompt` function that exists at that point (the user's own, or the default one) is wrapped, not replaced: the script adds the sequences around its output, and gives it the same `$?` it would have had without the wrapper.
- The exit code of `OSC 133;D` is `0` when the command succeeded, the value of `$LASTEXITCODE` when it failed and that is a non-zero number, and `1` for any other failure (a cmdlet error). `$LASTEXITCODE` is not reset by Noren, so a cmdlet error that follows a native command that failed earlier can report that older code.
- `C` and `E` are written when PSReadLine returns the accepted line, by wrapping the `PSConsoleHostReadLine` function (it needs PSReadLine, which every interactive PowerShell console loads). Without PSReadLine the shell still sends `OSC 7`, `A` and `B`, but no `C`, `D` or `E`.
- It changes no setting, writes nothing to disk and starts no process. A second load in the same session does nothing.

## bash

`apps/desktop/src-tauri/resources/shell-integration/noren.bash` works in bash 3.2 and newer (Git for Windows ships 5.x). Keep it ASCII with LF line ends (`.gitattributes` forces LF).

- Bash reads no startup file when it is given `--rcfile`, and it ignores `--rcfile` in a login shell. So Noren starts bash as `bash --rcfile <script> <profile arguments> -i`, and the script first loads what the user would have got without it:
  - a login profile (the Git Bash profile is `--login -i`): `/etc/profile`, then the first of `~/.bash_profile`, `~/.bash_login` and `~/.profile`. Noren takes `--login` / `-l` out of the arguments and sets `NOREN_BASH_LOGIN=1` for the script (which unsets it);
  - any other profile: `/etc/bash.bashrc` when it exists, then `~/.bashrc`.
- The user's `PS1` and `PROMPT_COMMAND` stay. `PS1` is wrapped with `A` and `B` (again whenever a prompt command of the user rebuilds it). `PROMPT_COMMAND`, a string or an array (bash 5.1+), gets one function before the user's commands, which reads `$?` and writes `D` and `OSC 7`, and one after them, which wraps `PS1`. They hand `$?` on unchanged.
- `C` and `E` come from a `DEBUG` trap, which bash runs before each simple command; the first one of a line writes `E` (from `history 1`, so a line the history does not keep, with `HISTCONTROL=ignorespace` or `ignoredups`, has `C` and `D` but no `E`) and `C`. The trap does not see a line that starts with a subshell, such as `(exit 3)`. For that the function before the user's commands checks, at the next prompt, whether the history moved since the last one: if it did, it writes `E` and `C` just before `D`.
- If the files of the user already set a `DEBUG` trap (bash-preexec and some prompt frameworks do), Noren leaves it alone. Every command is then reported when it ends, with `E`, `C` and `D` together before the next prompt.
- On Windows (Git Bash) the folder is written as a Windows path: `/c/Users/me` becomes `C:/Users/me`, and other places, such as `/usr/bin`, go through `cygpath -m`. The `bash.exe` in the Windows system folder is the launcher of the Windows Subsystem for Linux, not a bash, and is never touched; WSL profiles (`wsl.exe -d ...`) are not touched either.

## zsh

`apps/desktop/src-tauri/resources/shell-integration/zsh/` holds `.zshenv`, `.zprofile`, `.zshrc` and `noren.zsh`.

- Noren starts zsh with `ZDOTDIR` pointing at that folder, and `NOREN_USER_ZDOTDIR` holding the user's own `ZDOTDIR` (empty when there is none). zsh reads the dotfiles of the folder; each one loads the user's file of the same name, with `ZDOTDIR` set to the user's folder while it runs (a `ZDOTDIR` the user sets in `.zshenv` is followed). `.zshrc` loads the user's `.zshrc`, then gives `ZDOTDIR` back to the user for good (unset when there was none, so `.zlogin`, `.zlogout` and the programs started from the shell see what they would have seen), then loads `noren.zsh`.
- `noren.zsh` wraps `PROMPT` (with `%{ %}` around `A` and `B`, again whenever a hook of the user rebuilds it) and puts one hook first and one last in `precmd_functions`: the first reads `$?` and writes `D` and `OSC 7`, the last wraps the prompt. A `preexec` hook writes `E` (the line as typed) and `C`. Every function starts with `emulate -L zsh`, so options such as `KSH_ARRAYS` do not change it.
- A `precmd` function the user defined by name (not through `precmd_functions`) runs before these hooks and may change `$?` for them.
- Nested interactive zsh shells started from inside the session read the user's files only, since `ZDOTDIR` was given back.

## cmd

cmd has no startup file and no hook, only the `PROMPT` environment variable, so that is all Noren changes. It sets `PROMPT` for the session to:

```
$E]9;9;$P$E\$E]133;A$E\<the user's PROMPT, or $P$G>$E]133;B$E\
```

`$E` is ESC and `$P` the current folder. cmd has no code for BEL, so the sequences end with ST (`ESC \`), which the parser reads. The folder travels as `OSC 9;9` (a plain path, `C:\Users\me`), which is why the parser reads that sequence; it is sent at each prompt, so `cd` is followed.

What cmd cannot give: the exit code and the command line. `%ERRORLEVEL%` in a prompt is read when the prompt is set, not when it is shown, and cmd does not tell the prompt which command ran. So cmd sends no `OSC 133;D`, `C` or `633;E`: only the folder and the prompt start and end. If the user's `PROMPT` variable already holds `$E]133;A`, Noren leaves it as it is. A `prompt` command typed in the session replaces the variable and ends the integration for that session.

## How it is injected

`Profile::spawn_spec_with_integration` in `noren-core` (`crates/noren-core/src/integration.rs`, no Tauri dependency) builds the `SpawnSpec` of a profile. The shell is recognised from the program name (`pwsh`, `powershell`, `bash`, `zsh`, `cmd`, with or without `.exe`).

| Shell                | What the spec gets                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pwsh`, `powershell` | `-NoLogo -NoExit -Command ". ([scriptblock]::Create([System.IO.File]::ReadAllText('<path>\noren.ps1')))"` appended                                |
| `bash`               | `--rcfile <path>/noren.bash`, then the profile's arguments without `--login`/`-l`, then `-i` if missing; `NOREN_BASH_LOGIN=1` for a login profile |
| `zsh`                | environment `ZDOTDIR=<folder>/zsh` and `NOREN_USER_ZDOTDIR=<the user's ZDOTDIR or empty>`; arguments unchanged                                    |
| `cmd`                | environment `PROMPT=...` as above; arguments unchanged                                                                                            |

PowerShell's script text is compiled by PowerShell itself, so the execution policy of the machine (which only checks script files) does not stop it and is not changed.

The spec is the plain one, without any of this, when:

- the profile has `inject_integration` set to `false` (it is `true` for every detected profile);
- the shell is none of the above (fish, `wsl.exe`, the `bash.exe` of the Windows system folder, ...);
- the script is not in the folder with the scripts (`noren.ps1`, `noren.bash`, `zsh/.zshrc`), or the folder is not known. cmd needs no script and does not look at the folder;
- the arguments of the profile already choose what the shell runs: for PowerShell `-Command`, `-File`, `-EncodedCommand`; for bash and zsh `-c` (also joined, as in `-lc`), a script file, `-`; for cmd `/c`, `/k`, `/r`. For bash also `--rcfile`, `--init-file`, `--norc` and `--noprofile`, and for zsh `-f` and `--no-rcs`, because the user turned the startup files off.

The profile's own arguments stay, so `-NoProfile` or `-MTA` (PowerShell), `-o vi` (bash) or `-l` (zsh) keep their effect. There is no screen to change `inject_integration` yet; the field is what that setting will write.

The folder comes from the app: the scripts are bundle resources (`bundle.resources` in `tauri.conf.json`, installed as `resources/shell-integration/` in the resource folder; the zsh dotfiles have their own pattern because `*` does not go into folders), and `bridge.rs` resolves that folder with Tauri's resource path and hands it to `noren-core`. `noren --smoke` fails when a PowerShell session does not print `OSC 133;A`, and when any of the scripts, including the zsh dotfiles, is missing from the resource folder, which is how a missing resource is caught in a build.

## Unread and bell marks

The same tracker reports the bell and the notifications to `onAttention`; the app turns each into the `pane/notify` action through `store.notifyPane` (a bell sets `bell: true`, a notification only marks the pane).

- **What is marked.** `Pane.unread` and `Pane.bell`, which the model already had, and the new `Pane.unreadAt` (the time the pane became unread, on the clock of the reducer). A bell sets both marks, `OSC 9` and `OSC 777` set `unread`. The text of the notification is not kept in the pane; it goes to the system notification (see below).
- **Only what the user did not see.** A pane that is on screen is never marked: it is in the tab the active space shows and zoom does not hide it (every pane of a split that is not zoomed counts as on screen). `isPaneVisible` in `packages/model/src/unread.ts` is the rule. The action changes nothing when the pane already has the marks, and a program that keeps ringing does not change the saved file at every bell: `unreadAt` is the time of the first mark, and a bell after a plain notification only adds `bell`.
- **Viewing clears.** After every action that changed the workspace, the reducer clears the marks of the panes on screen, so showing the tab (a click, a shortcut, the palette, the search, the switcher), showing the space, or bringing back a pane that zoom hid reads it. A pane that zoom hides stays marked until it is shown. `pane/clear-unread` clears a pane (or all panes of a tab) without showing it.
- **Where it shows.** The tab in the sidebar and in the tab bar gets the unread dot and the bell (`data-nr-indicator="unread"` and `"bell"`), as before. A group shows the marks of the tabs inside it at any depth, also when it is folded (`groupMarks`), and each space in the switcher shows them for all its tabs, pinned ones included, on the corner of its icon (`spaceMarks`, `data-nr-part="space-marks"`). Group and space buttons keep their name; the words (`Unread output`, `Bell`) are their description for assistive technology.
- **Last unread.** `lastUnread` (pure, in the model) is the marked pane with the greatest `unreadAt`, in any space; panes with the same time (and panes saved before `unreadAt` existed) go in space order, then sidebar order, then layout order. Ctrl+Shift+U (`tab.last-unread`, see [KEYBINDINGS.md](KEYBINDINGS.md)) shows it: the tab is chosen, the pane focused and the space shown, in that order, so the pane is the one that is read. A second press goes to the next most recent one; with nothing unread the notice says `Nothing unread`.
- **Saved.** The marks are part of the saved state, so a tab that rang while the app was closed still shows it after a restart (`unreadAt` is optional in the file, so older files load).
- **Web mode and tests.** `FakeBackend.sendOutput(sessionId, text)` writes anything to a session as if its program had printed it, and the test hook has `sendOutput(paneId, text)` for a pane of any tab. The fake shell itself never rings.
- **Not here.** A terminal of a tab that is not on screen stays mounted, so its output reaches the parser; a tab that is closed is not marked.

## System notifications

When something happens that the user may not have seen, Noren asks the system for a notification. The rule is pure and lives in `packages/model/src/notifications.ts` (`decideNotification`); the store hands it each bell, notification and command end, and `SystemNotifier` asks the backend whether the window has the focus, decides, and calls `Backend.notify`.

| Event                                                | Notifies when                                                                                                 |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| The bell, `OSC 9` text, `OSC 777;notify`             | the window of the app does not have the keyboard focus (with the focus, the unread marks are enough)          |
| A command that ran for more than the limit and ended | its pane is not on screen (another tab, another space, hidden by zoom), or the window does not have the focus |

- **Words.** A bell says `Bell` under the title of the tab (`Noren` when the tab has none). A notification of a program uses its own title (the tab title, then `Noren`, when it sent none) and its text. A long command says `Command finished` or `Command failed`, followed by `in <tab>`, with `<line> finished after 31s` or `<line> failed (exit 2) after 1m 35s`; without the command line it says `A command`. Text is plain, cut to 80 and 200 characters, and control characters become spaces; the Rust side cuts it again before the system sees it.
- **The limit is more than 30 s**: 30 s exactly does not notify, 31 s does. A command whose duration is unknown (the shell sent `OSC 633;E` and `OSC 133;D` but never `OSC 133;C`) never notifies.
- **No repeats.** The same words for the same pane are sent once per 3 seconds, so a program that rings in a loop, or an event reported twice, gives one notification. Another pane or other words are other events. A notification the system refused is not held against the next one.
- **Settings.** `notifications.enabled` and `notifications.longCommandSeconds` in `config.jsonc` (see [CONFIG.md](CONFIG.md)): `{"notifications": {"enabled": false}}` turns it all off and `{"notifications": {"longCommandSeconds": 60}}` changes the limit. What the file does not say is the default (on, 30 s). Both are in the **Notifications** section of the settings screen, which writes them into the file. The browser storage key `noren.ui.notifications`, which held them before the screen existed, is no longer read: what it held is moved into the file once at the first start. The value is read at every event, so a saved file applies at once.
- **The calls.** `Backend.isWindowFocused()` and `Backend.notify(title, body)`. In the desktop app they are the Tauri commands `window_is_focused` (the focus of the `main` window; false when it is hidden or minimized) and `notify_show` (`apps/desktop/src-tauri/src/notify.rs`), which uses `tauri-plugin-notification` from Rust only: the JavaScript package is not installed and the plugin's own commands have no capability, so the page can show a notification only through `notify_show`. `FakeBackend` (and so the web build, whose backend extends it) records the calls in `notifications` and answers the focus given to `setWindowFocused`; it never shows anything.
- **Not done yet.** Clicking a notification does not bring the tab up, and there is no screen for the settings above (NOR-F8-01b).

## Tests

- `cargo test -p noren-core` covers the spec for every shell (integration on and off, the user's profile arguments kept, login and non-login bash, the `ZDOTDIR` of the user handed over, the `PROMPT` of the user kept, profiles that choose what runs left alone) and runs real shells in a PTY with the scripts, without a window:
  - PowerShell (`pwsh`, or Windows PowerShell when that is all there is) types `cmd /c exit 3` and the output must have `OSC 133;D;3`, with `E` and `C` before it; a user prompt defined before the script is kept and sees the right `$?`;
  - bash (Git Bash on Windows, `/bin/bash` elsewhere; never the WSL launcher), once as a login shell and once as a plain one, in a scratch `HOME` (the real one is never read) and with the script copied to a folder whose name has a space: it types `(exit 3)` and the output must have `OSC 133;D;3` with `E` and `C` before it, then a successful line with a `;`, then an empty line (no `E`, `C` or `D`); a `PS1` and a `PROMPT_COMMAND` written to the user's file are kept, and the command sees the right `$?`; a `DEBUG` trap of the user is left alone;
